Sequences and Identity Management

1. Introduction​

PostgreSQL provides sequences to generate unique numeric values, commonly used for primary keys and auto-incrementing identifiers.

For example, when inserting a new customer, you generally do not want to manually calculate the next customer_id.

PostgreSQL can generate it automatically.

Two common approaches are:

  1. SERIAL — traditional PostgreSQL auto-increment shorthand.
  2. IDENTITY columns — modern SQL-standard approach.

Both use PostgreSQL sequences internally.

This chapter covers:

  • Sequence fundamentals.
  • Creating and managing sequences.
  • SERIAL vs IDENTITY.
  • GENERATED ALWAYS and GENERATED BY DEFAULT.
  • nextval(), currval() and setval().
  • Sequence configuration.
  • Sequence gaps and concurrency.
  • Sequence ownership and dependencies.
  • Resetting sequences safely.
  • Practical Node.js usage.

2. What Is a Sequence?​

A sequence is a special database object that generates numeric values.

Example:

CREATE SEQUENCE customer_id_seq;

Generate a value:

SELECT nextval('customer_id_seq');

Possible output:

1

Call it again:

SELECT nextval('customer_id_seq');

Output:

2

Again:

SELECT nextval('customer_id_seq');

Output:

3

PostgreSQL generates a new sequence value whenever nextval() is called.

Common use cases​

  • Customer IDs.
  • Order IDs.
  • Payment IDs.
  • Employee IDs.
  • Invoice numbers.
  • Other automatically generated numeric identifiers.

Important: A sequence generates numbers, but it does not automatically enforce uniqueness in a table. Use a PRIMARY KEY or UNIQUE constraint for that.

3. Creating a Sequence​

Basic syntax​

CREATE SEQUENCE sequence_name;

Example:

CREATE SEQUENCE order_id_seq;

By default, a sequence generally starts at 1 and increments by 1.

Specify sequence properties​

CREATE SEQUENCE order_id_seq
START WITH 1000
INCREMENT BY 1
MINVALUE 1
MAXVALUE 999999
CACHE 1;

Explanation​

OptionMeaning
START WITHInitial value to generate
INCREMENT BYDifference between consecutive values
MINVALUEMinimum permitted sequence value
MAXVALUEMaximum permitted sequence value
CACHENumber of sequence values preallocated for a session

Descending sequence​

CREATE SEQUENCE reverse_seq
START WITH 100
INCREMENT BY -1
MINVALUE 1
MAXVALUE 100;

Generated values:

100, 99, 98, 97, ...

4. Using nextval()​

nextval() retrieves the next value from a sequence and advances it.

Syntax​

SELECT nextval('sequence_name');

Example:

SELECT nextval('order_id_seq');

Every call obtains another sequence value.

Use it during INSERT​

Suppose you have a table:

CREATE TABLE orders_demo (
    order_id INTEGER PRIMARY KEY,
    customer_name VARCHAR(100)
);

Insert a row:

INSERT INTO orders_demo (
    order_id,
    customer_name
)
VALUES (
    nextval('order_id_seq'),
    'Rahul'
);

The sequence generates the ID automatically for this insert.

Important​

nextval() is atomic and safe for concurrent sessions.

Two transactions calling nextval() on the same sequence receive distinct values.

However, sequence values are not transactional in the same way as ordinary table updates. Rolling back a transaction does not return a consumed sequence value.

5. currval()​

currval() returns the most recent value obtained by nextval() for a particular sequence in the current database session.

Syntax​

SELECT currval('sequence_name');

Example:

SELECT nextval('order_id_seq');

SELECT currval('order_id_seq');

If nextval() returned 1000, currval() returns 1000.

Important​

currval() works only after the current session has called nextval() for that sequence.

Calling it before that produces an error.

It is session-specific, not a global way to retrieve the latest value generated by every connection.

6. lastval()​

lastval() returns the most recent value returned by nextval() for any sequence in the current session.

Example:

SELECT nextval('order_id_seq');

SELECT lastval();

If the last sequence call generated 1001, lastval() returns 1001.

Difference​

FunctionPurpose
nextval()Generates and returns the next sequence value
currval()Returns the last value generated from a specified sequence in this session
lastval()Returns the last value generated from any sequence in this session

Recommendation: For INSERT operations, prefer INSERT ... RETURNING instead of relying on a separate currval() or lastval() call.

7. setval()​

setval() changes a sequence's current state.

It is commonly used when synchronizing a sequence with existing table data.

Syntax​

SELECT setval('sequence_name', value);

Example:

SELECT setval('order_id_seq', 500);

With the default third argument behavior, the next nextval() returns 501 for an increment-by-1 sequence.

Three-argument version​

SELECT setval('order_id_seq', 500, true);

The third argument controls whether the supplied value is considered already used.

Third argumentNext nextval()
trueAdvances according to the increment; 501 for increment 1
falseReturns the supplied value, 500

Example:

SELECT setval('order_id_seq', 500, false);

SELECT nextval('order_id_seq');

Result:

500

Important​

setval() changes sequence state immediately. Its effects are not rolled back like ordinary table changes.

Use it carefully when other sessions may be generating values concurrently.

8. SERIAL Data Type​

SERIAL is a PostgreSQL-specific shorthand for creating an integer column backed by a sequence.

Example​

CREATE TABLE customers_demo (
    customer_id SERIAL PRIMARY KEY,
    customer_name VARCHAR(100) NOT NULL
);

PostgreSQL effectively creates:

  • An INTEGER column.
  • A sequence.
  • A default expression using nextval().
  • An ownership dependency between the sequence and column.

Insert without specifying ID​

INSERT INTO customers_demo (customer_name)
VALUES ('Rahul');

PostgreSQL generates the ID automatically.

Insert multiple rows​

INSERT INTO customers_demo (customer_name)
VALUES
    ('Rahul'),
    ('Amit'),
    ('Priya');

Possible result:

customer_idcustomer_name
1Rahul
2Amit
3Priya

SERIAL variants​

TypeUnderlying integer type
SMALLSERIALSMALLINT
SERIALINTEGER
BIGSERIALBIGINT

Choose based on the expected identifier range.

Important: SERIAL is not a true data type. It is shorthand for a column, sequence and default expression.

9. IDENTITY Columns​

PostgreSQL supports SQL-standard identity columns.

They automatically generate values using an associated sequence.

GENERATED ALWAYS AS IDENTITY​

CREATE TABLE products_demo (
    product_id INTEGER
        GENERATED ALWAYS AS IDENTITY
        PRIMARY KEY,
    product_name VARCHAR(100) NOT NULL
);

Insert:

INSERT INTO products_demo (product_name)
VALUES ('Keyboard');

PostgreSQL generates product_id.

What does ALWAYS mean?​

PostgreSQL normally rejects an explicitly supplied value for an ALWAYS identity column.

Example:

INSERT INTO products_demo (
    product_id,
    product_name
)
VALUES (
    100,
    'Mouse'
);

This produces an error unless you explicitly override the identity behavior.

Override system value​

INSERT INTO products_demo (
    product_id,
    product_name
)
OVERRIDING SYSTEM VALUE
VALUES (
    100,
    'Mouse'
);

This allows an explicitly supplied identity value.

10. GENERATED BY DEFAULT AS IDENTITY​

Unlike ALWAYS, BY DEFAULT allows explicitly supplied values.

CREATE TABLE employees_demo (
    employee_id INTEGER
        GENERATED BY DEFAULT AS IDENTITY
        PRIMARY KEY,
    employee_name VARCHAR(100) NOT NULL
);

Normal insert:

INSERT INTO employees_demo (employee_name)
VALUES ('Rahul');

Explicit ID:

INSERT INTO employees_demo (
    employee_id,
    employee_name
)
VALUES (
    100,
    'Amit'
);

Both are allowed.

Comparison​

FeatureGENERATED ALWAYSGENERATED BY DEFAULT
Generates IDs automaticallyYesYes
Explicit ID accepted normallyNoYes
Explicit override requiredYesNo
Suitable when automatic generation should be enforcedYesLess strict

Recommendation: Use GENERATED ALWAYS when application code should not normally provide IDs. Use BY DEFAULT when explicit IDs are a legitimate requirement.

11. SERIAL vs IDENTITY​

FeatureSERIALIDENTITY
PostgreSQL supportYesYes
SQL-standard featureNoYes
Uses a sequenceYesYes
Auto-generates IDsYesYes
Explicit valuesGenerally acceptedDepends on ALWAYS/BY DEFAULT
Sequence ownershipCreated with ownership dependencyManaged as an identity sequence
Modern recommendationExisting code compatibilityPreferred for new designs

Example using SERIAL​

CREATE TABLE orders_old (
    order_id SERIAL PRIMARY KEY,
    total_amount NUMERIC(12, 2)
);

Example using IDENTITY​

CREATE TABLE orders_new (
    order_id BIGINT
        GENERATED ALWAYS AS IDENTITY
        PRIMARY KEY,
    total_amount NUMERIC(12, 2)
);

For new PostgreSQL schemas, IDENTITY is generally preferable.

12. Modifying an Identity Column​

You can modify the generation behavior of an identity column.

Change ALWAYS to BY DEFAULT​

ALTER TABLE products_demo
ALTER COLUMN product_id
SET GENERATED BY DEFAULT;

Change BY DEFAULT to ALWAYS​

ALTER TABLE products_demo
ALTER COLUMN product_id
SET GENERATED ALWAYS;

Restart identity sequence​

ALTER TABLE products_demo
ALTER COLUMN product_id
RESTART WITH 1000;

This changes the identity sequence's next generated value.

Important: Restarting a sequence while concurrent inserts are occurring can create conflicts or unexpected behavior. Perform administrative sequence changes with appropriate coordination.

13. ALTER SEQUENCE​

PostgreSQL allows you to modify sequence properties.

Syntax​

ALTER SEQUENCE sequence_name
INCREMENT BY 1
MINVALUE 1
MAXVALUE 1000000
CACHE 10;

Change increment​

ALTER SEQUENCE order_id_seq
INCREMENT BY 5;

Next values advance by 5.

Change maximum value​

ALTER SEQUENCE order_id_seq
MAXVALUE 1000000;

Change cache​

ALTER SEQUENCE order_id_seq
CACHE 20;

This preallocates values for a session.

Restart sequence​

ALTER SEQUENCE order_id_seq
RESTART WITH 1000;

The next generated value will be 1000.

14. Dropping a Sequence​

Use:

DROP SEQUENCE order_id_seq;

If a table column depends on the sequence, PostgreSQL may prevent dropping it.

You can inspect dependencies before attempting removal.

CASCADE​

DROP SEQUENCE order_id_seq CASCADE;

This also removes dependent objects.

Warning: CASCADE can remove more than the sequence itself. Inspect dependencies before using it.

For identity columns, PostgreSQL manages the associated sequence as part of the identity column dependency.

15. Sequence Gaps — Very Important​

A common misconception is that auto-increment IDs must be continuous.

They do not.

PostgreSQL sequences are designed to generate distinct values efficiently, not gap-free numbering.

Example​

BEGIN;

INSERT INTO customers_demo (customer_name)
VALUES ('Rahul');

ROLLBACK;

The inserted row is rolled back, but the sequence value is consumed.

The next insert may receive the next number rather than reusing the rolled-back number.

Other reasons for gaps​

  • Failed INSERT statements.
  • Transaction rollbacks.
  • ON CONFLICT operations.
  • Cached sequence values lost after a session or server interruption.
  • Manual sequence changes.

Important​

Do not use ordinary sequences when a business requirement demands legally or operationally gap-free document numbering.

Such numbering requires a separate transactional design, careful concurrency control and an explicit understanding of rollback and deletion behavior.

16. Sequence Caching and Concurrency​

PostgreSQL supports sequence caching.

Example:

CREATE SEQUENCE invoice_seq
START WITH 1
INCREMENT BY 1
CACHE 10;

PostgreSQL can reserve multiple values for a session.

Benefits​

  • Reduces sequence-related overhead.
  • Improves performance under concurrent workloads.

Trade-off​

Cached values can be lost when a session ends unexpectedly.

This can create gaps.

Also, values obtained from different sessions are not guaranteed to be observed in the same order as transaction commits.

Important: Sequence values are not transactional and do not guarantee gap-free or commit-order numbering.

17. Finding the Sequence Associated with a Column​

PostgreSQL provides:

SELECT pg_get_serial_sequence(
    'customers_demo',
    'customer_id'
);

Possible result:

public.customers_demo_customer_id_seq

Despite the function name, pg_get_serial_sequence() can also identify the sequence associated with an identity column.

Why is this useful?​

You may need to:

  • Inspect an associated sequence.
  • Synchronize a sequence after importing data.
  • Reset an automatically generated ID.
  • Investigate sequence ownership.

18. Resetting a Sequence Based on Existing Table Data​

Suppose you manually imported records with IDs up to 5000.

But the associated sequence still generates values starting near 1.

The next insert may conflict with an existing primary key.

You need to synchronize the sequence.

Find the associated sequence​

SELECT pg_get_serial_sequence(
    'customers_demo',
    'customer_id'
);

Synchronize it​

For a positive increment-by-1 sequence:

SELECT setval(
    pg_get_serial_sequence(
        'customers_demo',
        'customer_id'
    ),
    COALESCE(
        (SELECT MAX(customer_id) FROM customers_demo),
        1
    ),
    EXISTS (
        SELECT 1
        FROM customers_demo
    )
);

This handles both cases:

  • Table contains rows: next value advances beyond the maximum existing ID.
  • Table is empty: the next generated value starts at 1.

Important: This example assumes the sequence uses an increment of 1 and is intended to generate positive IDs. Run it when concurrent inserts are stopped or appropriately coordinated.

19. TRUNCATE and RESTART IDENTITY​

PostgreSQL allows sequences owned by columns in a table to be reset when truncating the table.

Example​

TRUNCATE TABLE customers_demo
RESTART IDENTITY;

This:

  • Removes all rows.
  • Restarts sequences owned by columns of the truncated table.

Without RESTART IDENTITY​

TRUNCATE TABLE customers_demo;

The sequence continues from its existing state.

Comparison​

CommandEffect on owned sequences
TRUNCATE TABLE table_nameContinues existing sequence values
TRUNCATE TABLE table_name RESTART IDENTITYRestarts owned sequences

Important​

TRUNCATE ... RESTART IDENTITY is transactional in PostgreSQL. A rollback can undo both the truncation and the associated sequence restart.

This differs from calling nextval() or setval() directly, whose effects are not rolled back.

20. INSERT ... RETURNING​

For backend applications, this is one of the most useful PostgreSQL features.

Instead of inserting a row and then separately asking for its generated ID, use RETURNING.

Example​

INSERT INTO customers_demo (
    customer_name
)
VALUES (
    'Rahul'
)
RETURNING customer_id;

Possible output:

customer_id
-----------
501

Return multiple columns​

INSERT INTO customers_demo (
    customer_name
)
VALUES (
    'Amit'
)
RETURNING
    customer_id,
    customer_name;

Why prefer RETURNING?​

  • Gets the exact ID generated by that INSERT.
  • Avoids a separate query.
  • Works safely with concurrent sessions.
  • Avoids relying on lastval() or assumptions about sequence state.

21. Node.js and PostgreSQL Example​

Using the pg package:

const result = await pool.query(
  `INSERT INTO customers (
      customer_name,
      email
   )
   VALUES ($1, $2)
   RETURNING customer_id, customer_name`,
  ["Rahul", "rahul@example.com"],
);

const customer = result.rows[0];

console.log(customer.customer_id);

The application receives the generated customer ID directly.

Inside a transaction​

const client = await pool.connect();

try {
  await client.query("BEGIN");

  const result = await client.query(
    `INSERT INTO orders (
        customer_id,
        total_amount,
        status
     )
     VALUES ($1, $2, $3)
     RETURNING order_id`,
    [101, 2500, "pending"],
  );

  const orderId = result.rows[0].order_id;

  await client.query(
    `INSERT INTO order_items (
        order_id,
        product_id,
        quantity,
        unit_price
     )
     VALUES ($1, $2, $3, $4)`,
    [orderId, 101, 2, 1250],
  );

  await client.query("COMMIT");

  return orderId;
} catch (error) {
  await client.query("ROLLBACK");
  throw error;
} finally {
  client.release();
}

This ensures that the generated order ID is used for the related order item.

22. Common Mistakes​

MistakeCorrect understanding
Assuming SERIAL is a real data typeIt is shorthand for an integer column, sequence and default
Assuming sequence values are gap-freeGaps are normal
Assuming ROLLBACK restores sequence valuesSequence operations such as nextval() are not rolled back
Assuming sequence guarantees uniqueness in a tableUse PRIMARY KEY or UNIQUE constraints
Using lastval() across different connectionsSequence state is session-specific
Manually calculating the next ID using MAX(id) + 1Use identity columns or sequences
Forgetting to synchronize a sequence after importing explicit IDsUse the appropriate sequence reset procedure
Assuming IDENTITY always accepts explicit valuesGENERATED ALWAYS requires an explicit override
Assuming cached values are never lostSession termination can leave gaps
Using a separate SELECT to retrieve the inserted IDPrefer INSERT ... RETURNING

24. Interview Questions​

Q1. What is a sequence in PostgreSQL?

A database object that generates numeric values.

Q2. What is SERIAL?

A PostgreSQL shorthand that creates an integer column backed by a sequence.

Q3. What is an IDENTITY column?

A SQL-standard column feature that automatically generates values using an associated sequence.

Q4. What is the difference between SERIAL and IDENTITY?

SERIAL is PostgreSQL-specific shorthand. IDENTITY is the SQL-standard mechanism with explicit ALWAYS and BY DEFAULT behavior.

Q5. What is the difference between GENERATED ALWAYS and GENERATED BY DEFAULT?

ALWAYS normally prevents explicitly supplied values; BY DEFAULT allows them.

Q6. What does nextval() do?

Generates and returns the next sequence value.

Q7. What does currval() do?

Returns the last value obtained from a specified sequence in the current session.

Q8. What does lastval() do?

Returns the last value obtained from any sequence in the current session.

Q9. What does setval() do?

Changes the current state of a sequence.

Q10. Are sequence values rolled back when a transaction fails?

No. Sequence operations are not transactional in the same way as ordinary table modifications.

Q11. Why do auto-increment IDs have gaps?

Failed inserts, rollbacks, conflict handling, caching and manual sequence operations can consume values without creating corresponding rows.

Q12. Does a sequence guarantee uniqueness?

No. A sequence generates values, but uniqueness in a table must be enforced through a PRIMARY KEY or UNIQUE constraint.

Q13. What is the purpose of CACHE in a sequence?

It preallocates sequence values for performance, potentially creating gaps if cached values are lost.

Q14. Why is MAX(id) + 1 unsafe?

Concurrent transactions can calculate the same next value and attempt conflicting inserts.

Q15. Why is INSERT ... RETURNING useful?

It returns the exact generated identifier from the INSERT operation without another query.

Q16. How do you find a sequence associated with a column?

Use pg_get_serial_sequence().

Q17. What does TRUNCATE ... RESTART IDENTITY do?

It truncates the table and restarts sequences owned by columns of that table.

Q18. Can an identity sequence be manually reset?

Yes, through appropriate ALTER TABLE identity restart operations or sequence management, with suitable coordination.

Key Takeaways​

  • Sequences generate numeric values.
  • nextval() generates the next value.
  • currval() returns the last value from a specified sequence in the current session.
  • lastval() returns the last value generated by any sequence in the current session.
  • setval() changes sequence state.
  • SERIAL is PostgreSQL shorthand; IDENTITY is the modern SQL-standard approach.
  • GENERATED ALWAYS and GENERATED BY DEFAULT control explicit ID insertion.
  • Sequence values are not gap-free and are not rolled back like ordinary table changes.
  • Sequences do not automatically enforce table uniqueness.
  • Use PRIMARY KEY or UNIQUE constraints.
  • Use INSERT ... RETURNING to retrieve generated IDs in backend applications.
  • Never generate IDs using MAX(id) + 1 in concurrent applications.
