# Node.js CommonJS Module Resolution — Extensive Practical Notes

# 1. What Is Module Resolution?

When you write:

```js
const express = require("express");
```

Node has to answer:

> **"Which exact module should I load for the string `express`?"**

That process is called **module resolution**.

For example:

```js
require("./utils");
```

might become:

```text
/project/src/utils.js
```

Or:

```js
require("lodash");
```

might become:

```text
/project/node_modules/lodash/lodash.js
```

So:

```text
require("something")
       |
       v
   RESOLUTION
       |
       v
exact module target
       |
       v
    LOAD
       |
       v
module.exports
```

## The important distinction

**Resolution** answers:

> Where / what is the module?

**Loading** answers:

> Now that we know what it is, load and execute it.

This distinction becomes very useful when debugging Node.js applications.

---

# 2. The Big Picture

A simplified CommonJS `require()` flow is:

```text
require("something")
        |
        v
Classify the specifier
        |
        +------------------+
        |                  |
        v                  v
   built-in?           path-like?
        |                  |
       yes                 yes
        |                  |
        v                  v
   built-in            filesystem
                         probing
                            |
                            v
                    exact file / .js /
                    .json / .node /
                    directory
        |
        +------------------+
        |
        v
      package?
        |
        v
 search node_modules
        |
        v
 package metadata
(exports / main)
        |
        v
 exact target
        |
        v
 CommonJS cache
        |
        v
 load / execute
        |
        v
 module.exports
```

There are additional branches for `#` imports, package self-reference, symlinks, conditions, and other edge cases.

You do **not** need to memorize Node's source code.

You do need to understand the major branches.

---

# 3. First: What Is a Specifier?

The string passed to `require()` is called a **specifier**.

Examples:

```js
require("fs");
require("node:fs");
require("./utils");
require("../config");
require("/home/app/utils.js");
require("lodash");
require("@babel/core");
require("express/lib/router");
require("#db");
```

Node does **not** treat all these strings the same way.

The first important job is:

> **Classify the specifier.**

---

# 4. The Three Main Specifier Categories

For practical purposes, think of three major categories.

| Specifier              | Category          | What Node does                        |
| ---------------------- | ----------------- | ------------------------------------- |
| `"fs"`                 | Built-in          | Load Node's built-in module           |
| `"node:fs"`            | Explicit built-in | Load Node's built-in module           |
| `"./utils"`            | Relative path     | Resolve from caller's directory       |
| `"../utils"`           | Relative path     | Resolve from caller's directory       |
| `"/home/app/utils.js"` | Absolute path     | Resolve directly from filesystem      |
| `"lodash"`             | Bare package      | Search `node_modules`                 |
| `"@babel/core"`        | Scoped package    | Search `node_modules`                 |
| `"express/lib/router"` | Package subpath   | Find package, then subpath            |
| `"#db"`                | Package import    | Use nearest package's `"imports"` map |

The most important classification rule is:

```text
./      -> relative path
../     -> relative path
/       -> absolute path

everything else
        -> usually a package/bare specifier

#...    -> package "imports"
```

Built-ins are checked specially before ordinary package lookup.

---

# 5. Built-in Modules

Node itself provides modules such as:

```js
require("fs");
require("path");
require("http");
require("crypto");
```

These are **built-in modules**.

Node knows about them internally.

It does not need to search:

```text
node_modules
```

to find them.

For example:

```js
const fs = require("fs");
```

roughly means:

```text
Is "fs" a Node built-in?
       |
      YES
       |
       v
return built-in module
```

---

# 6. `node:` Prefix

You can explicitly request a built-in module:

```js
const fs = require("node:fs");
```

This is the explicit form.

You can use:

```js
const fs1 = require("fs");
const fs2 = require("node:fs");
```

Both refer to Node's built-in `fs` module.

For backend code, `node:` is a useful convention because it makes the intent obvious:

```js
const fs = require("node:fs");
const path = require("node:path");
const crypto = require("node:crypto");
```

---

# 7. Why `"fs"` and `"./fs"` Are Completely Different

Suppose your project contains:

```text
project/
├── app.js
└── fs.js
```

If you write:

```js
require("fs");
```

Node loads the **built-in `fs` module**.

If you write:

```js
require("./fs");
```

Node loads your local:

```text
./fs.js
```

The `./` changes the meaning.

Remember:

```text
"fs"
   -> Node built-in

"./fs"
   -> local filesystem path
```

This distinction applies to other built-ins too.

---

# 8. Inspecting Built-in Modules

You can inspect the built-in module list:

```js
const Module = require("node:module");

console.log(Module.builtinModules);
```

Or:

```js
const { builtinModules } = require("node:module");

console.log(builtinModules);
```

You generally do not need to inspect this list in application code.

It is mainly useful for understanding/debugging Node's module system.

---

# 9. Relative Paths

A relative request starts with:

```text
./
```

or:

```text
../
```

Example:

```js
require("./utils");
```

If the current file is:

```text
/home/app/src/controllers/user.js
```

then:

```js
require("./utils");
```

starts looking from:

```text
/home/app/src/controllers/utils
```

It does **not** start from:

```text
/home/app
```

and it does **not** depend on the terminal's current working directory in the normal CommonJS relative-resolution sense.

---

# 10. Caller Location Matters

This is extremely important.

Suppose:

```text
project/
├── app.js
├── utils.js
└── controllers/
    └── user.js
```

From:

```text
app.js
```

this:

```js
require("./utils");
```

means:

```text
project/utils.js
```

But from:

```text
controllers/user.js
```

the same:

```js
require("./utils");
```

means:

```text
project/controllers/utils.js
```

So:

> **Relative `require()` paths are relative to the file doing the requiring.**

---

# 11. Relative Path vs `process.cwd()`

A common mistake is thinking:

```js
require("./utils");
```

means:

```text
process.cwd() + "/utils"
```

That is not the correct mental model.

Instead:

```text
require("./utils")
       |
       v
directory of current CommonJS module
       |
       v
./utils
```

For example:

```js
console.log(process.cwd());
console.log(__dirname);
```

These can be different.

`process.cwd()` tells you where the process was started from.

`__dirname` tells you the directory of the current CommonJS file.

For relative CommonJS `require()`, the module's location is what matters.

---

# 12. Absolute Paths

An absolute filesystem path starts with `/` on Unix-like systems.

Example:

```js
require("/home/app/utils.js");
```

Node treats that as an absolute filesystem location.

There is no `node_modules` climbing involved.

The path itself tells Node where to look.

Absolute paths are usually less portable because they depend on the machine's filesystem layout.

---

# 13. File Extension Probing

Suppose you write:

```js
require("./config");
```

There might be:

```text
config
config.js
config.json
config.node
```

CommonJS can probe known extensions.

The normal extension order is:

```text
.js
.json
.node
```

So conceptually:

```text
require("./config")
        |
        v
./config
        |
        v
./config.js
        |
        v
./config.json
        |
        v
./config.node
```

The first successful match wins.

---

# 14. Why Extension Order Matters

Suppose you have:

```text
config.js
config.json
```

and:

```js
require("./config");
```

Node tries:

```text
config
config.js
config.json
config.node
```

Therefore:

```text
config.js
```

wins before:

```text
config.json
```

This is one reason you should avoid confusingly naming multiple files that can resolve from the same specifier.

---

# 15. Exact File Check Happens First

Node first tries the path exactly as written.

For:

```js
require("./utils");
```

it conceptually checks:

```text
./utils
```

before:

```text
./utils.js
./utils.json
./utils.node
```

Normally, you will almost always have conventional extensions such as `.js`.

But understanding this explains some unusual resolution behavior.

---

# 16. A Subtle Extension Edge Case

Consider:

```js
require("./utils.js");
```

Node starts with:

```text
utils.js
```

If that exact file exists:

```text
STOP
```

It does not need to continue probing.

If it does not exist, later extension probing can be based on the request itself, leading to candidates such as:

```text
utils.js.js
utils.js.json
utils.js.node
```

This is uncommon, but it explains why:

```js
require("./utils");
```

and:

```js
require("./utils.js");
```

are not identical resolution requests.

---

# 17. Should You Always Include `.js`?

Do not turn extension probing into a fake performance rule.

The difference between:

```js
require("./utils");
```

and:

```js
require("./utils.js");
```

is usually not an important application performance concern.

Startup performance is much more affected by:

- number of modules
- filesystem speed
- cold vs warm filesystem cache
- package structure
- Docker volume behavior
- network filesystems
- dependency tree size

Use whichever module-resolution style your project's conventions require.

---

# 18. Directory Resolution

CommonJS can also resolve a directory as a module.

Suppose:

```text
project/
└── mylib/
    ├── package.json
    └── index.js
```

Then:

```js
require("./mylib");
```

can load the directory's entry point.

The legacy directory flow is approximately:

```text
./mylib
   |
   v
directory?
   |
   v
package.json?
   |
   +--> "main"
   |
   +--> index.js
   |
   +--> index.json
   |
   +--> index.node
```

---

# 19. Directory `package.json` + `"main"`

Suppose:

```text
mylib/
├── package.json
└── lib/
    └── entry.js
```

and:

```json
{
  "main": "lib/entry.js"
}
```

Then:

```js
require("./mylib");
```

can resolve to:

```text
mylib/lib/entry.js
```

The `"main"` path is relative to the package/directory root.

---

# 20. `index.js` Fallback

If the directory does not provide a usable `"main"` entry, CommonJS has the legacy convention:

```text
index.js
index.json
index.node
```

For example:

```text
mylib/
└── index.js
```

Then:

```js
require("./mylib");
```

can resolve to:

```text
mylib/index.js
```

This convention is old but still important because you will encounter it in real Node.js codebases.

---

# 21. `"main"` Beats `index.js`

Suppose:

```text
mylib/
├── package.json
├── index.js
└── entry.js
```

and:

```json
{
  "main": "entry.js"
}
```

Then:

```js
require("./mylib");
```

uses:

```text
entry.js
```

rather than:

```text
index.js
```

So:

```text
valid "main"
      |
      v
use main
```

before the legacy index fallback.

---

# 22. Invalid `"main"` Fallback

The source describes a legacy compatibility behavior:

If `"main"` points to a missing target, Node can fall back to package-root `index.js`, `index.json`, or `index.node`, while reporting `DEP0128`.

Do not build new packages around this behavior.

For new code:

```text
package.json
      |
      v
valid entry point
```

is the correct approach.

---

# 23. Bare Specifiers

A **bare specifier** is usually a package name.

Examples:

```js
require("express");
require("lodash");
require("mongoose");
require("@babel/core");
```

Notice what is missing:

```text
./
../
/
#
```

Node therefore treats it as a package lookup request.

---

# 24. The `node_modules` Climbing Algorithm

This is one of the most important Node concepts to understand.

Suppose this file:

```text
/home/app/src/lib/foo.js
```

runs:

```js
require("lodash");
```

Node searches upward through `node_modules` directories.

Conceptually:

```text
/home/app/src/lib/node_modules/lodash
/home/app/src/node_modules/lodash
/home/app/node_modules/lodash
/home/node_modules/lodash
/node_modules/lodash
```

The first successful match wins.

---

# 25. Why Does Node Search Upward?

This lets different parts of an application have their own dependency versions.

Imagine:

```text
app
├── node_modules/
│   └── accepts@2
│
└── node_modules/
    └── express/
        └── node_modules/
            └── accepts@1
```

Code in the application can resolve:

```text
accepts@2
```

while Express can resolve:

```text
accepts@1
```

because the search begins from different directories.

The critical mental model:

> **The caller's location determines where package lookup begins.**

---

# 26. npm Hoisting

npm may flatten dependencies when versions are compatible.

For example, instead of:

```text
app/node_modules/packageA/node_modules/lodash
```

npm may place a compatible version at:

```text
app/node_modules/lodash
```

Node does not know that npm "hoisted" it.

Node simply sees the filesystem and applies its lookup rules.

So:

```text
package manager creates tree
            |
            v
Node resolves paths in that tree
```

---

# 27. pnpm and Symlinks

pnpm uses a different filesystem layout involving symlinks and a content-addressable store.

The important point is:

> Node still resolves what the filesystem presents to it.

Node does not have a special "pnpm resolution algorithm" that replaces CommonJS resolution.

Package managers construct dependency layouts; Node resolves modules from the resulting filesystem structure and package metadata.

---

# 28. Scoped Packages

Scoped packages look like:

```js
require("@babel/core");
```

The package path is:

```text
node_modules/@babel/core
```

The upward lookup remains the same.

For example:

```text
/home/app/src/node_modules/@babel/core
/home/app/node_modules/@babel/core
/home/node_modules/@babel/core
/node_modules/@babel/core
```

The scope:

```text
@babel
```

is simply the first directory level under `node_modules`.

---

# 29. Package Subpaths

You can require a path inside a package:

```js
require("express/lib/router");
```

Conceptually:

```text
find express package
       |
       v
inside express/
       |
       v
lib/router
       |
       v
router.js / directory rules
```

Historically, this made almost any internal package file reachable.

Modern packages can restrict this with `"exports"`.

---

# 30. Why Deep Imports Can Be Dangerous

Suppose a package has:

```text
my-pkg/
├── index.js
└── lib/
    ├── router.js
    └── internal.js
```

You write:

```js
require("my-pkg/lib/internal");
```

Now you depend on the package's internal file structure.

If the package author later changes:

```text
lib/internal.js
```

to:

```text
src/internal.js
```

your application breaks.

This is why package authors use:

```json
"exports"
```

to define a stable public interface.

---

# 31. `package.json` `"main"`

`"main"` is the older package entry-point mechanism.

Example:

```json
{
  "name": "my-pkg",
  "main": "./dist/index.cjs"
}
```

If Node finds:

```text
node_modules/my-pkg
```

then `"main"` tells it where the package's legacy entry point is.

Conceptually:

```text
require("my-pkg")
       |
       v
node_modules/my-pkg
       |
       v
package.json
       |
       v
"main": "./dist/index.cjs"
       |
       v
dist/index.cjs
```

---

# 32. What `"main"` Does Not Mean

Do not assume every package field is understood by Node.

For example:

```json
{
  "main": "./dist/cjs/index.js",
  "module": "./dist/esm/index.js"
}
```

Node uses:

```text
main
```

but does not use `"module"` as the standard Node package entry mechanism.

Bundlers may use `"module"`.

For modern Node package design, `"exports"` is the more important field.

---

# 33. `package.json` `"exports"`

`"exports"` is the modern way to define a package's public entry points.

Example:

```json
{
  "name": "my-pkg",
  "exports": {
    ".": "./lib/index.js",
    "./utils": "./lib/utils.js"
  }
}
```

Now consumers can use:

```js
require("my-pkg");
require("my-pkg/utils");
```

But they may not be able to use:

```js
require("my-pkg/lib/internal");
```

unless that path is explicitly exported.

---

# 34. Why `"exports"` Is Important

Before `"exports"`, package consumers could often reach directly into package internals:

```js
require("some-package/lib/internal");
```

That creates a maintenance problem.

With `"exports"`:

```text
package author
      |
      v
defines public API
      |
      v
"exports"
      |
      v
consumer can use only those public paths
```

Now the package author can freely reorganize internal files without necessarily breaking consumers.

---

# 35. `"exports"` Can Hide Files That Exist

This is important.

Suppose:

```text
node_modules/my-pkg/lib/internal.js
```

exists.

But:

```json
{
  "exports": {
    ".": "./lib/index.js"
  }
}
```

does not export:

```text
./lib/internal.js
```

Then:

```js
require("my-pkg/lib/internal");
```

can fail with:

```text
ERR_PACKAGE_PATH_NOT_EXPORTED
```

Even though the file physically exists.

This teaches an important rule:

> **A file existing on disk does not necessarily mean the package exposes it through package-name resolution.**

---

# 36. `"exports"` Is Not a Filesystem Security Sandbox

Do not misunderstand `"exports"`.

It controls package-name access such as:

```js
require("my-pkg");
require("my-pkg/utils");
```

It is not a security mechanism preventing every possible path-based access.

If code already knows an absolute filesystem path, it can potentially load that file directly:

```js
require("/some/path/node_modules/my-pkg/lib/internal.js");
```

Therefore:

```text
exports = public package interface
```

not:

```text
exports = security boundary
```

---

# 37. `"exports"` vs `"main"`

If both exist:

```json
{
  "main": "./index.cjs",
  "exports": {
    ".": "./index.cjs"
  }
}
```

modern Node package-name resolution uses:

```text
exports
```

rather than:

```text
main
```

A common modern package pattern is therefore to keep:

```text
main
+
exports
```

for compatibility with older consumers while making `"exports"` the authoritative modern public map.

---

# 38. Simple `"exports"` Example

Package:

```text
my-pkg/
├── package.json
└── lib/
    ├── index.js
    ├── utils.js
    └── internal.js
```

`package.json`:

```json
{
  "name": "my-pkg",
  "exports": {
    ".": "./lib/index.js",
    "./utils": "./lib/utils.js"
  }
}
```

Allowed:

```js
require("my-pkg");
require("my-pkg/utils");
```

Not necessarily allowed:

```js
require("my-pkg/internal");
require("my-pkg/lib/internal");
```

unless those paths are exported.

---

# 39. Conditional Exports

A package can provide different files depending on how it is consumed.

Example:

```json
{
  "exports": {
    ".": {
      "import": "./lib/index.mjs",
      "require": "./lib/index.cjs",
      "default": "./lib/index.js"
    }
  }
}
```

Now:

```js
require("my-pkg");
```

can select:

```text
require -> ./lib/index.cjs
```

while:

```js
import "my-pkg";
```

can select:

```text
import -> ./lib/index.mjs
```

This is important for packages supporting both CommonJS and ESM.

---

# 40. Think of Conditional Exports as an `if`

You can mentally simplify:

```json
{
  "exports": {
    ".": {
      "require": "./index.cjs",
      "import": "./index.mjs"
    }
  }
}
```

to something like:

```text
IF consumer is CommonJS
    -> index.cjs

IF consumer is ESM
    -> index.mjs
```

This is not literally JavaScript, but it is a good mental model.

---

# 41. The `"default"` Condition

You can provide:

```json
{
  "exports": {
    ".": {
      "require": "./index.cjs",
      "default": "./index.js"
    }
  }
}
```

Think:

```text
try require
   |
   +--> matching -> use it
   |
   +--> otherwise -> default
```

---

# 42. Condition Order Matters

This is critical.

Node evaluates condition objects in order and selects the first matching condition.

Good:

```json
{
  "exports": {
    ".": {
      "require": "./index.cjs",
      "default": "./index.js"
    }
  }
}
```

Potentially wrong:

```json
{
  "exports": {
    ".": {
      "default": "./index.js",
      "require": "./index.cjs"
    }
  }
}
```

Why?

Because `"default"` matches broadly.

If it is encountered first, Node can choose it before reaching `"require"`.

So:

> **Put more specific conditions before broader fallback conditions.**

---

# 43. Common Conditions

You may encounter conditions such as:

```text
import
require
node
default
browser
development
production
```

Custom conditions only matter when the consumer/runtime activates them.

For example:

```bash
node --conditions=development app.js
```

can activate a custom:

```json
"development"
```

condition.

Do not add custom conditions casually. They increase package-resolution complexity.

---

# 44. Node's CommonJS Conditions

The supplied source discusses modern Node versions where CommonJS `require()` can include conditions such as:

```text
node
require
module-sync
```

The exact condition set can change with Node versions and features.

For backend developers, the durable concept is:

> **The way a package is being loaded affects which `"exports"` condition can match.**

Do not memorize a particular Node version's internal condition list unless you are specifically debugging package-loader behavior.

---

# 45. Subpath Patterns

`"exports"` can expose groups of files using `*`.

Example:

```json
{
  "exports": {
    "./features/*": "./src/features/*.js"
  }
}
```

Then:

```js
require("my-pkg/features/auth");
```

can map to:

```text
src/features/auth.js
```

The wildcard is a replacement.

---

# 46. Wildcards Can Match Paths

A pattern such as:

```json
{
  "exports": {
    "./features/*": "./src/features/*.js"
  }
}
```

can also match:

```text
features/auth/handler
```

and map it to:

```text
src/features/auth/handler.js
```

The important idea is:

```text
package subpath
       |
       v
wildcard substitution
       |
       v
internal target
```

---

# 47. Export Targets Must Stay Inside the Package

`"exports"` targets are package-relative paths.

Example:

```json
{
  "exports": {
    ".": "./src/index.js"
  }
}
```

The target begins with:

```text
./
```

You cannot use the feature to deliberately escape the package directory with arbitrary traversal.

This prevents `"exports"` from becoming a generic filesystem aliasing system.

---

# 48. `package.json` `"imports"`

`"imports"` is different from `"exports"`.

A useful memory trick:

```text
exports
   -> what this package exposes OUTWARD

imports
   -> aliases used INSIDE this package
```

Example:

```json
{
  "imports": {
    "#utils": "./src/utils/index.js",
    "#db": "./src/database/client.js"
  }
}
```

Inside the package:

```js
require("#utils");
require("#db");
```

---

# 49. Why Use `"imports"`?

Without aliases:

```js
require("../../../../utils/helpers");
```

can become ugly and fragile.

If the file moves:

```text
src/a/b/c/file.js
```

the number of `../` segments may change.

With:

```json
{
  "imports": {
    "#utils": "./src/utils/index.js"
  }
}
```

you can write:

```js
require("#utils");
```

from anywhere inside the package.

The alias remains stable while internal folder structure changes.

---

# 50. `#` Is Required

Package import aliases use the `#` prefix:

```js
require("#db");
```

Not:

```js
require("db");
```

The `#` tells Node:

> This is a package `"imports"` mapping.

This prevents confusion with normal package names.

---

# 51. `"imports"` Is Private to the Package

Suppose:

```text
package-a/
  package.json
```

contains:

```json
{
  "imports": {
    "#db": "./src/db.js"
  }
}
```

Then code inside package A can use:

```js
require("#db");
```

Another unrelated package cannot automatically use package A's alias.

Package B would need its own:

```json
{
  "imports": {
    "#db": "..."
  }
}
```

This gives each package its own private alias namespace.

---

# 52. `"imports"` Does Not Use `node_modules` Climbing

This is an important distinction.

For:

```js
require("lodash");
```

Node searches:

```text
node_modules
node_modules
node_modules
...
```

For:

```js
require("#db");
```

Node looks at the nearest package scope and its:

```json
"imports"
```

map.

It does not keep climbing upward searching for another package's matching `#db`.

---

# 53. Conditional `"imports"`

`"imports"` can also use conditions.

Example:

```json
{
  "imports": {
    "#db": {
      "development": "./src/database/mock.js",
      "default": "./src/database/client.js"
    }
  }
}
```

Then:

```bash
node --conditions=development app.js
```

can make:

```js
require("#db");
```

resolve to the mock implementation.

Without the condition, it can resolve to:

```text
client.js
```

This is a useful pattern for development/test environments, but should be used deliberately.

---

# 54. Package Self-Reference

A package can sometimes require itself by its own package name.

Suppose:

```json
{
  "name": "my-pkg",
  "exports": {
    ".": "./lib/index.js",
    "./utils": "./lib/utils.js"
  }
}
```

Inside the package, code can use:

```js
require("my-pkg");
```

or:

```js
require("my-pkg/utils");
```

This is called **package self-reference**.

The package's `"exports"` map controls what is available.

---

# 55. Why Self-Reference Is Useful

Suppose internal code normally uses:

```js
require("../../utils");
```

while external consumers use:

```js
require("my-pkg/utils");
```

Now internal and external code can use the same public package interface:

```js
require("my-pkg/utils");
```

This can make package boundaries clearer.

---

# 56. `NODE_PATH`

`NODE_PATH` is an environment variable that adds additional CommonJS module search directories.

Example:

```bash
NODE_PATH=/home/shared/libs:/opt/custom/modules node app.js
```

Then:

```js
require("some-lib");
```

can eventually search those directories if normal package lookup does not find the module.

On Unix-like systems:

```text
:
```

separates entries.

On Windows:

```text
;
```

separates entries.

---

# 57. Why You Should Usually Avoid `NODE_PATH`

`NODE_PATH` is legacy.

It makes module resolution depend on the environment that launched the application.

That can create:

```text
works on my machine
```

problems.

For example:

```text
Developer machine
   -> NODE_PATH contains /home/shared/libs

Production server
   -> NODE_PATH does not contain it
```

The application behaves differently.

Prefer:

- local `node_modules`
- npm/yarn/pnpm workspaces
- proper package dependencies
- explicit package boundaries

Use `NODE_PATH` mainly when dealing with older systems or legacy environments.

---

# 58. Historical Global Folders

Node also has historical global search locations such as:

```text
$HOME/.node_modules
$HOME/.node_libraries
$PREFIX/lib/node
```

These are legacy behavior.

Modern applications generally should not depend on them.

You can inspect the runtime's configured global paths:

```js
const Module = require("node:module");

console.log(Module.globalPaths);
```

The important lesson is simply:

> **A module can sometimes resolve from locations beyond your project's local `node_modules`, so unexpected dependencies can come from the environment.**

In modern projects, avoid relying on this.

---

# 59. `require.resolve()`

`require.resolve()` performs module resolution without actually loading/evaluating the module.

Example:

```js
const path = require.resolve("./utils");

console.log(path);
```

Possible result:

```text
/home/app/src/utils.js
```

Think:

```text
require("./utils")
    |
    v
resolve
    |
    v
load
    |
    v
execute
    |
    v
exports
```

But:

```text
require.resolve("./utils")
    |
    v
resolve
    |
    v
filename
```

---

# 60. `require.resolve()` Does Not Execute the Module

Suppose:

```js
// expensive.js

console.log("I executed");

module.exports = 123;
```

Now:

```js
const path = require.resolve("./expensive");

console.log(path);
```

You do **not** get:

```text
I executed
```

because the module was resolved, not loaded.

This makes `require.resolve()` useful for debugging and optional dependencies.

---

# 61. `require.resolve()` for Debugging

If:

```js
require("some-package");
```

is loading something unexpected, use:

```js
console.log(require.resolve("some-package"));
```

You may discover:

```text
/home/app/node_modules/some-package/index.js
```

when you expected:

```text
/home/app/src/node_modules/some-package/index.js
```

That immediately tells you where Node found it.

---

# 62. `require.resolve()` and `MODULE_NOT_FOUND`

If Node cannot resolve the request:

```js
require.resolve("does-not-exist");
```

throws:

```text
MODULE_NOT_FOUND
```

So this:

```js
if (require.resolve("some-package")) {
  // ...
}
```

is not a safe existence check.

Use `try/catch`.

---

# 63. Optional Dependency Pattern

Suppose your application optionally supports YAML.

You can check:

```js
let yamlPath;

try {
  yamlPath = require.resolve("js-yaml");
} catch (err) {
  if (err.code !== "MODULE_NOT_FOUND") {
    throw err;
  }
}
```

Then:

```js
const yaml = yamlPath ? require(yamlPath) : null;
```

The important distinction is:

```text
package missing
    -> feature can be disabled

package found but broken during execution
    -> real error should still surface
```

Do not catch every error and silently pretend the dependency does not exist.

---

# 64. Finding a Package Root

You can sometimes locate a package's root by resolving a file inside it:

```js
const path = require("node:path");

const packageRoot = path.dirname(require.resolve("lodash/package.json"));

console.log(packageRoot);
```

This works only if the package exposes that path.

A package with `"exports"` may intentionally block:

```js
require.resolve("some-package/package.json");
```

even though Node internally reads its own `package.json` for package resolution.

---

# 65. `"exports"` Can Block `package.json`

Suppose:

```json
{
  "exports": {
    ".": "./index.js"
  }
}
```

Then:

```js
require.resolve("my-pkg/package.json");
```

may fail.

Why?

Because:

```text
package.json exists
```

does not imply:

```text
package.json is publicly exported
```

Again:

> **Physical file existence and package-name accessibility are different concepts.**

---

# 66. Symlinks

Symlinks can affect module identity.

Suppose:

```text
/home/app/node_modules/my-pkg
        |
        v
      symlink
        |
        v
/opt/packages/my-pkg
```

By default, Node can resolve the symlink to its real path.

So the effective module identity can become:

```text
/opt/packages/my-pkg/index.js
```

rather than the symlink path.

---

# 67. Why Symlink Behavior Matters

This matters because CommonJS caching is connected to resolved filenames.

If two paths ultimately resolve to:

```text
/opt/packages/my-pkg/index.js
```

they can share the same cached module instance under normal realpath behavior.

Conceptually:

```text
path A ----\
            \
             -> /opt/packages/my-pkg/index.js
            /
path B ----/
```

Both can collapse to one module identity.

---

# 68. `--preserve-symlinks`

Node provides:

```bash
node --preserve-symlinks app.js
```

This changes how symlink paths are treated.

Instead of immediately collapsing everything to the real path, Node can preserve the symlink path as module identity.

This can result in:

```text
symlink path A -> module instance A
symlink path B -> module instance B
```

even if both point to the same physical file.

---

# 69. Why Duplicate Module Instances Are Dangerous

Suppose a library exports a class:

```js
class User {}
module.exports = User;
```

If the same physical package is loaded as two different module instances:

```text
UserA !== UserB
```

Then:

```js
instanceof
```

can behave unexpectedly.

For example:

```js
const a = new UserA();

console.log(a instanceof UserB);
```

could be:

```text
false
```

even though both classes came from what appears to be the same package.

This is one reason symlink-related duplicate dependencies can be painful.

---

# 70. `--preserve-symlinks-main`

There is also:

```bash
node --preserve-symlinks-main app.js
```

This specifically affects how the main entry script's symlink is treated.

It can influence values such as:

```js
__dirname;
```

for the main module.

Most applications do not need this flag.

---

# 71. Case Sensitivity and Module Identity

Consider:

```js
require("./Utils");
require("./utils");
```

On a case-sensitive filesystem such as a typical Linux filesystem, one may fail if the actual file is:

```text
utils.js
```

On case-insensitive filesystems, both can potentially refer to the same physical file while producing different resolved filename identities.

That can lead to multiple module cache entries and separate module state.

---

# 72. Why This Causes Production Bugs

A developer may test on:

```text
macOS / Windows
```

where:

```text
Utils
utils
```

may behave permissively.

Then production runs on:

```text
Linux
```

where casing matters.

Result:

```text
development -> works
production -> MODULE_NOT_FOUND
```

Enforce import casing through linting and CI.

Do not rely on the local filesystem to catch these mistakes.

---

# 73. `Module._resolveFilename`

The internal CommonJS function responsible for the main resolution work is:

```js
Module._resolveFilename(request, parent, isMain, options);
```

You do not need to memorize its source code.

Think of it as:

```text
request
   +
caller
   +
resolution options
        |
        v
exact module identifier
```

It handles things such as:

- built-ins
- path-like requests
- package lookup
- `#` imports
- package self-reference
- package metadata
- final path resolution

---

# 74. The `parent` Module

The `parent` argument represents the module that requested the dependency.

For example:

```js
// controllers/user.js

require("../services/user");
```

The parent is conceptually:

```text
controllers/user.js
```

This matters because Node needs to know:

> From which location should I interpret this request?

For:

```js
require("../services/user");
```

the answer depends on the parent file's directory.

---

# 75. `isMain`

The internal resolver also receives information about whether the module is the main entry module.

For example:

```bash
node app.js
```

means:

```text
app.js = main module
```

This matters for some loader bookkeeping.

Normal application code rarely needs to interact with the internal `isMain` parameter directly.

---

# 76. `_findPath`

Another internal function involved in CommonJS resolution is:

```js
Module._findPath(request, paths, isMain);
```

Think of it as:

> **"Given this request and these possible lookup locations, find the actual target."**

This is where filesystem probing and package resolution become concrete.

You do not need to call this directly in normal code.

---

# 77. `Module._pathCache`

Node maintains an internal resolution cache.

The loaded module cache answers:

> Have I already loaded this module?

The path cache answers more like:

> Where does this request resolve given these lookup paths?

Conceptually:

```text
request + lookup paths
        |
        v
resolution cache
        |
        v
resolved filename
```

This is different from:

```js
require.cache;
```

---

# 78. Two Different Caches

Memorize this distinction.

## Module cache

```js
require.cache;
```

Contains loaded CommonJS modules.

```text
filename
   |
   v
Module object
```

## Resolution/path cache

Internal Node bookkeeping such as:

```text
Module._pathCache
```

helps avoid repeating resolution work.

```text
request + paths
       |
       v
resolved filename
```

Do not confuse:

```text
"where is it?"
```

with:

```text
"have I loaded it?"
```

---

# 79. `require.cache` vs Resolution Cache

Example:

```js
const path = require.resolve("./utils");
```

This resolves:

```text
./utils
   |
   v
/project/utils.js
```

but does not execute the module.

A later:

```js
require("./utils");
```

can load the module.

So resolution and loading are separate stages.

The path-resolution result can be cached independently of the evaluated module.

---

# 80. Synchronous Resolution

CommonJS resolution performs filesystem work synchronously.

That can include:

- checking whether candidate files exist
- checking whether a path is a directory
- reading package metadata
- resolving symlinks
- probing extensions

This means module loading can block JavaScript execution during startup.

---

# 81. Why Startup Can Be Slow

Large applications can load thousands of modules.

Each module can trigger resolution work.

A deep package tree can result in many filesystem probes.

For example:

```text
src/a/b/c/foo.js
       |
       v
require("lodash")
       |
       +--> src/a/b/c/node_modules?
       |
       +--> src/a/b/node_modules?
       |
       +--> src/a/node_modules?
       |
       +--> src/node_modules?
       |
       +--> node_modules?
```

Many failed checks may occur before the correct package is found.

---

# 82. Failed Filesystem Checks Still Cost Time

A failed lookup such as:

```text
ENOENT
```

means:

> "That path does not exist."

But the filesystem still had to answer the question.

Thousands of unnecessary failed probes can contribute to startup cost, especially on:

- slow disks
- Docker volumes
- network filesystems
- cold filesystem caches
- unusual package layouts

This is mainly a startup concern.

---

# 83. Why Bundlers Can Be Faster at Runtime

Bundlers such as:

```text
webpack
esbuild
Rollup
```

can resolve dependencies during a build.

Instead of the runtime repeatedly asking:

```text
Where is package X?
Where is file Y?
Where is package Z?
```

the build process can produce output where much of that relationship is already known.

Conceptually:

```text
source files
     |
     v
build-time resolution
     |
     v
bundled output
     |
     v
runtime
```

This is one reason bundling can reduce runtime module-resolution overhead.

---

# 84. Realpath and Symlinks

After finding a file, Node may canonicalize it using realpath behavior.

Conceptually:

```text
symlink path
     |
     v
realpath
     |
     v
actual filesystem path
```

This matters because the canonical path can become part of module identity and therefore caching.

Node also maintains internal realpath-related caching to avoid repeatedly doing expensive canonicalization work.

# 85. Debugging Module Resolution

When you have:

```text
Cannot find module ...
```

do not randomly change import paths.

Use Node's resolution tools.

---

# 86. Debugging Step 1 — `require.resolve()`

Run:

```js
console.log(require.resolve("some-pkg"));
```

If it succeeds:

```text
you know exactly which file Node selected
```

If it fails:

```text
Node cannot resolve the package from this location
```

This is usually the fastest first diagnostic.

---

# 87. Debugging Step 2 — Check Search Paths

Use:

```js
console.log(require.resolve.paths("some-pkg"));
```

This tells you the directories Node considers for a bare package request.

You may discover:

```text
[
  "/home/app/src/node_modules",
  "/home/app/node_modules",
  "/home/node_modules",
  "/node_modules"
]
```

If your expected dependency directory is not represented, you have a resolution-layout problem.

---

# 88. Debugging Step 3 — Check the Caller

Ask:

> Which file is executing the `require()`?

Because:

```js
require("./utils");
```

depends on the caller's location.

Print:

```js
console.log(__filename);
console.log(__dirname);
```

Then verify the path you expect.

---

# 89. Debugging Step 4 — Check `package.json`

If a package is involved, inspect:

```text
package.json
```

especially:

```json
{
  "exports": {},
  "imports": {},
  "main": "...",
  "type": "..."
}
```

For a package resolution issue, `"exports"` is often the first thing to check in modern Node packages.

---

# 90. Debugging Step 5 — Check `node_modules`

Verify the package is actually installed where you think it is:

```text
project/
└── node_modules/
    └── some-pkg/
```

Do not assume the package manager created the tree you expected.

Use:

```bash
npm ls some-pkg
```

or the equivalent command for your package manager when useful.

---

# 91. Debugging Step 6 — Check Symlinks

If using:

```text
npm link
pnpm
monorepos
workspace packages
local packages
```

inspect whether a dependency is symlinked.

Unexpected duplicate package instances can cause:

```text
instanceof failures
multiple singleton instances
separate caches
unexpected state
```

On a POSIX shell:

```bash
NODE_DEBUG=module node app.js
```

You may see output similar to:

This can reveal how Node is interpreting a request.

# 93. `NODE_DEBUG=module` vs `DEBUG`

Do not confuse:

```bash
NODE_DEBUG=module
```

with libraries that use:

```bash
DEBUG=*
```

`NODE_DEBUG=module` is specifically Node's module-loader debugging facility.

It can be extremely useful when diagnosing:

```text
wrong package
wrong path
unexpected resolution
```

# 94. Command-Line Resolution Test

For a quick test:

This is useful when you want to test resolution without modifying the application.

Conceptually:

```text
current environment
      |

Node resolution
      |

print resolved target
```

# 95. Inspecting Node's Lookup Paths

```js
const Module = require("node:module");
```

Use it for debugging, not as normal application architecture.

# 96. Internal Loader Hooks

The supplied source shows that you can patch internal loader functions such as:

```js
Module._findPath;
```

for diagnostics.

For example:

```js
const Module = require("node:module");

const original = Module._findPath;

Module._findPath = function (request, paths, ...rest) {
  console.log("findPath:", request, paths);
  return original.call(this, request, paths, ...rest);
};
```

This can help trace exactly what Node is checking.

But:

> **Do not build production application logic around private loader internals.**

Internal APIs can change between Node versions.

# 97. The `"type"` Field

The supplied source also mentions:

```json
{
  "type": "commonjs"
}
```

or:

```json
{
  "type": "module"
}
```

The `"type"` field affects how `.js` files are interpreted.

Conceptually:

```text
.js file
   |
   v
nearest package.json "type"
   |
   +--> commonjs -> CommonJS
   |
   +--> module   -> ESM
```

This is important when a project contains both CommonJS and ESM behavior.

---

# 98. CommonJS vs ESM Resolution

Do not assume:

```text
require()
```

and:

```text
import
```

use identical resolution rules.

They do not.

One of the most important differences is extension handling.

CommonJS can do:

```js
require("./foo");
```

and probe:

```text
foo
foo.js
foo.json
foo.node
```

ESM generally expects the actual filename for relative imports:

```js
import "./foo.js";
```

This difference causes many CommonJS → ESM migration bugs.

---

# 99. `"exports"` Works Across CJS and ESM

A package can use:

```json
{
  "exports": {
    ".": {
      "require": "./index.cjs",
      "import": "./index.mjs"
    }
  }
}
```

to support both systems.

Think:

```text
CommonJS require()
       |
       v
"require" condition
       |
       v
index.cjs


ESM import
       |
       v
"import" condition
       |
       v
index.mjs
```

This is the modern Node package model.

---

# 100. `require()` Loading ESM

Modern Node versions can support loading some ES modules through `require()`.

The important limitation from the supplied source is:

> A CommonJS `require()` cannot synchronously complete an ESM graph that depends on top-level `await`.

In that situation Node can throw:

```text
ERR_REQUIRE_ASYNC_MODULE
```

and the application needs asynchronous:

```js
import(...)
```

instead.

The exact support behavior depends on the Node version and relevant runtime flags/features.

For backend development, the durable rule is:

```text
CommonJS require()
    -> synchronous

ESM with asynchronous top-level dependency
    -> use dynamic import when necessary
```

---

# 101. Circular Dependencies Are Not a Resolution Problem

This distinction is important.

Resolution answers:

```text
What file does A mean?
What file does B mean?
```

Circular dependencies happen during:

```text
loading/evaluation
```

Example:

```text
A requires B
B requires A
```

Node can resolve both paths successfully.

The problem is:

```text
A is still executing when B asks for A
```

Therefore B may see partial exports.

---

# 102. Circular Dependency Example

### `a.js`

```js
exports.name = "A";

const b = require("./b");

exports.ready = true;
```

### `b.js`

```js
const a = require("./a");

console.log(a.name);
console.log(a.ready);
```

When B requires A, A has already done:

```js
exports.name = "A";
```

but has not yet reached:

```js
exports.ready = true;
```

So B can observe:

```text
A
undefined
```

---

# 103. Why Does This Happen?

The CommonJS loader puts the module into the cache before evaluation finishes.

Conceptually:

```text
A starts
 |
 v
A added to cache
 |
 v
A executes
 |
 v
A requires B
 |
 v
B executes
 |
 v
B requires A
 |
 v
A found in cache
 |
 v
B receives A's current exports
```

This prevents:

```text
A -> B -> A -> B -> A -> ...
```

from recursively loading forever.

---

# 104. Partial Exports

When a circular dependency occurs, you may receive:

```js
{
  alreadyInitialized: "yes";
}
```

rather than the final:

```js
{
  alreadyInitialized: "yes",
  initializedLater: "yes"
}
```

The module was found, but its evaluation had not completed.

This is why circular dependency bugs can look strange:

```text
undefined
missing function
empty object
partially populated object
```

---

# 105. Avoid Circular Dependencies

The best fix for a circular dependency is usually architectural.

Instead of:

```text
A <-> B
```

consider:

```text
       common
       /    \
      A      B
```

Move shared functionality into a third module.

Other options include:

- dependency injection
- separating initialization from usage
- lazy loading where appropriate

Do not use lazy `require()` as an excuse to keep a badly designed dependency graph forever.

---

# 106. `module.exports` Replacement Makes Cycles Worse

Suppose:

```js
// a.js

const b = require("./b");

module.exports = {
  ready: true,
};
```

If B requires A before A reaches the assignment, B can receive the original exports object:

```js
{
}
```

Then A later replaces:

```js
module.exports;
```

with:

```js
{
  ready: true;
}
```

B still holds the old object.

This is one reason mutation and replacement behave differently during cycles.

---

# 107. `"exports"` vs `"imports"` — Memorize This

A very useful memory rule:

```text
"exports"
    = what consumers can access FROM the package

"imports"
    = aliases code INSIDE the package can use
```

Example:

```json
{
  "exports": {
    ".": "./src/index.js",
    "./db": "./src/db.js"
  },
  "imports": {
    "#utils": "./src/utils.js"
  }
}
```

Outside:

```js
require("my-pkg");
require("my-pkg/db");
```

Inside:

```js
require("#utils");
```

---

# 108. `"main"` vs `"exports"` vs `"imports"`

| Field       | Main purpose                           |
| ----------- | -------------------------------------- |
| `"main"`    | Legacy package entry point             |
| `"exports"` | Modern public package API map          |
| `"imports"` | Private internal aliases               |

# 111. Practical `#imports` Example

Project:

```text
my-app/
├── package.json
└── src/
    ├── app.js
    ├── db.js
    └── utils.js
```

`package.json`:

```json
{
  "imports": {
    "#db": "./src/db.js",
    "#utils": "./src/utils.js"
  }
}
```

Now `src/app.js` can use:

```js
const db = require("#db");
const utils = require("#utils");
```

Instead of:

```js
const db = require("./db");
const utils = require("./utils");
```

For a deeply nested file, the alias becomes more valuable.

# 112. Practical `"exports"` Example

Package:

```text
my-package/
├── package.json
└── src/
    ├── index.js
    ├── db.js
    └── internal.js
```

`package.json`:

```json
{
  "name": "my-package",
  "exports": {
    ".": "./src/index.js",
    "./db": "./src/db.js"
  }
}
```

Consumers can use:

```js
const pkg = require("my-package");
const db = require("my-package/db");
```

But:

```js
require("my-package/internal");
```

is blocked because it is not part of the public map.

# 113. Practical Conditional Exports

```json
{
  "exports": {
    ".": {
      "require": "./dist/index.cjs",
      "import": "./dist/index.mjs"
    }
  }
}
```

CommonJS:

```js
const pkg = require("my-package");
```

gets:

```text
dist/index.cjs
```

ESM:

```js
import pkg from "my-package";
```

gets:

```text
dist/index.mjs
```

This is one of the most important package patterns to understand when working with modern Node.js libraries.

# 114. Practical Package Subpath Pattern

```json
{
  "exports": {
    "./services/*": "./src/services/*.js"
  }
}
```

Then:

```js
require("my-package/services/user");
```

maps to:

```text
src/services/user.js
```

This allows package authors to expose structured public APIs without exposing every internal file.

# 116. `MODULE_NOT_FOUND` vs `ERR_PACKAGE_PATH_NOT_EXPORTED`

These errors mean different things.

## `MODULE_NOT_FOUND`

Usually means:

```text
Node could not resolve the requested module.
```

Example:

```js
require("does-not-exist");
```

## `ERR_PACKAGE_PATH_NOT_EXPORTED`

Usually means:

```text
The package exists, but that package subpath is not publicly exported.
```

Example:

```js
require("my-pkg/lib/internal");
```

when `"exports"` does not expose it.

This distinction is extremely useful when debugging dependencies.

# 117. Another Important Error: `ERR_REQUIRE_ASYNC_MODULE`

When CommonJS `require()` tries to synchronously load an ESM dependency graph that requires asynchronous top-level evaluation, modern Node can throw:

```text
ERR_REQUIRE_ASYNC_MODULE
```

The solution is generally to use:

```js
await import("./module.js");
```

or another asynchronous ESM-compatible loading strategy.

Remember:

```text
require()
   -> synchronous contract
```

so an inherently asynchronous ESM graph cannot always fit inside it.

# 118. Module Resolution Does Not Mean Module Execution

This distinction is worth repeating.

```js
require.resolve("./foo");
```

does:

```text
resolve
```

but not:

```text
execute
```

While:

```js
require("./foo");
```

does:

```text
resolve
+
load
+
execute
```

This is one of the most common conceptual mistakes beginners make.

# 119. Resolution Happens Before Cache Lookup

A simplified flow is:

```text
require(request)
      |
      v
resolve request
      |
      v
resolved identifier
      |
      v
check module cache
      |
      +--> hit -> return cached exports
      |
      +--> miss -> load module
```

Therefore the cache needs a stable module identity.

For normal file-backed CommonJS modules, the resolved filename is central to that identity.

# 120. Why Same File Usually Means Same Module

Suppose:

```js
const a = require("./utils");
const b = require("./utils.js");
```

If both resolve to:

```text
/project/utils.js
```

they normally refer to the same cached CommonJS module.

Conceptually:

```text
"./utils"   ----\
                 \
                  -> /project/utils.js
                 /
"./utils.js" ----/
```

Then:

```text
same resolved filename
        |
        v
same module cache entry
```

The exact identity can be affected by symlink and filesystem behavior.

# 121. Symlinks Can Change That Identity

With symlink preservation or other unusual filesystem setups, two specifiers can lead to different identities:

```text
path A
   |
   v
symlink A
   |
   v
same physical file


path B
   |
   v
symlink B
   |
   v
same physical file
```

Depending on loader configuration, Node may preserve those apparent paths instead of collapsing them to one real path.

This can create duplicate module instances.

# 122. Resolution and Dependency Injection

A useful backend architecture lesson:

Avoid making your application depend on fragile relative paths across package boundaries.

Bad:


Better:

```js

```

or an internal:


when the package owns the alias.

This makes the dependency relationship explicit.

For example:


The package author later adds `"exports"` and blocks it.



# 125. Why Backend Developers Should Care About `"imports"`

As backend projects grow, paths become deeply nested:

# 160. Common Mistake: Thinking `require()` Searches Everywhere

Wrong:

> "Node searches my whole computer for the package."

Correct:

> **Node follows specific resolution rules based on the specifier and caller.**

For packages:

```text
node_modules hierarchy
+
environment/global legacy paths
+
package metadata
```

For relative paths:

```text
caller directory
+
filesystem probing
```

For built-ins:

```text
Node's built-in registry
```

For `#`:

```text
nearest package's imports map
```

---

# 161. Common Mistake: Thinking `node_modules` Is Always the Current Directory

Wrong:

```text
node_modules = process.cwd()/node_modules
```

Correct:

```text
node_modules lookup starts relative to the requiring module
and walks upward.
```

This is why nested packages can have separate dependencies.

---

# 162. Common Mistake: Thinking `"main"` Always Wins

Wrong:

> `"main"` is the package entry point no matter what.

Modern Node:

```text
exports
```

takes precedence for package-name resolution when present.

So inspect:

```json
"exports"
```

before assuming:

```json
"main"
```

is being used.

---

# 163. Common Mistake: Thinking `"exports"` Hides Files from the Filesystem

Wrong:

> `"exports"` means the file cannot be accessed.

Correct:

> `"exports"` controls package-name access and the package's public module interface.

It is not a complete filesystem sandbox.

---

# 164. Common Mistake: Thinking `"imports"` Is Like `NODE_PATH`

Wrong:

> `#db` searches globally.

Correct:

> `"imports"` is a package-scoped mapping.

Example:

```json
{
  "imports": {
    "#db": "./src/db.js"
  }
}
```

It works for code inside that package scope.

---

# 165. Common Mistake: Thinking `require.resolve()` Loads the Module

Wrong:

```js
require.resolve("./db");
```

means:

```text
db.js executed
```

Correct:

```text
resolve only
```

No module evaluation is required.

---

# 166. Common Mistake: Thinking Resolution Errors Are Always Missing Files

Wrong:

```text
Cannot load subpath
=
file does not exist
```

Not necessarily.

You may have:

```text
file exists
+
exports blocks access
```

Then the error can be:

```text
ERR_PACKAGE_PATH_NOT_EXPORTED
```

Always identify which resolution branch failed.

---

# 167. Common Mistake: Using Deep Package Internals

Fragile:

```js
require("package/lib/internal");
```

Better:

```js
require("package");
```

or a documented public subpath:

```js
require("package/router");
```

if exposed.

If a package does not expose the internal module, do not fight the package's public API boundary.

---

# 168. Common Mistake: Using `NODE_PATH` to "Fix" Imports

Suppose:

```js
require("shared-utils");
```

fails.

Do not immediately add:

```bash
NODE_PATH=/some/random/path
```

That hides the underlying dependency/layout problem.

Prefer:

```text
proper package dependency
workspace
node_modules
package alias
```

depending on the architecture.

---

# 169. Common Mistake: Ignoring Node Version

Package resolution behavior evolves.

Modern Node versions have features such as:

```text
exports
imports
package self-reference
CJS/ESM interop
new condition handling
```

When debugging a package issue, record:

```bash
node --version
```

A resolution rule documented for one Node release should not automatically be assumed to describe every older release.

---

# 170. Common Mistake: Treating Private Internals as Stable

Avoid production dependencies on:

```js
Module._findPath;
Module._resolveFilename;
Module._pathCache;
Module._extensions;
```

These are useful for:

```text
debugging
learning
runtime investigation
```

They are not good foundations for application architecture.

Use public APIs wherever possible.

# 171. A Strong Backend Mental Model

When you see:

```js
const something = require("X");
```

ask four questions:

### Question 1 — What kind of specifier is X?

```text
built-in?
path?
package?
# alias?
```

### Question 2 — Where does Node start looking?

```text
caller directory?
package scope?
node_modules chain?
```

### Question 3 — What metadata affects the result?

```text
exports?
imports?
main?
type?
```

### Question 4 — What exact file did Node select?

Use:

```js

```

These four questions solve a large percentage of real-world module-resolution problems.


# 174. Final Rules to Remember

If you are preparing for serious Node.js backend development, these are the rules worth remembering.

## Rule 1

```text
require() starts with a specifier.
```

## Rule 2

```text
Node first determines what kind of specifier it is.
```

## Rule 3

```text
Relative paths are relative to the requiring module.
```

## Rule 4

```text
Bare package names use node_modules lookup.
```

## Rule 5

```text
node_modules lookup walks upward from the caller.
```

## Rule 6

```text
Built-ins are handled separately.
```

## Rule 7

```text
./foo can probe foo.js, foo.json, and foo.node.
```

## Rule 8

```text
Directories can use package.json "main" and legacy index files.
```

## Rule 9

```text
"exports" defines a package's modern public entry points.
```

## Rule 10

```text
"exports" can block files that physically exist.
```

## Rule 11

```text
"imports" creates private # aliases inside a package.
```

## Rule 12

```text
"main" is legacy compared with "exports".
```

## Rule 13

```text
require.resolve() resolves without loading.
```

## Rule 14

```text
require.resolve.paths() shows package lookup directories.
```

## Rule 15

```text
Symlinks and filename casing can affect module identity.
```

## Rule 16

```text
Resolution is synchronous in CommonJS.
```

## Rule 17

```text
Circular dependencies are a loading/evaluation problem, not simply a resolution problem.
```

## Rule 18

```text
Do not depend on private Node loader internals in production.
```
