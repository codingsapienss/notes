# Node.js `import.meta`, URLs, Caching & Module State --- Extensive Study Notes

## 1. The Big Picture

This chapter connects four ideas:

```text
import.meta
    ↓
module location / resolution
    ↓
resolved URL
    ↓
ESM module identity
    ↓
loader cache
    ↓
shared module state
    ↓
circular dependency behavior
```

The most important mental model is:

> **For ESM, module identity is based on the resolved URL.**

For CommonJS, the corresponding mental model is:

> **For CJS, module identity is primarily based on the resolved
> filename.**

That difference explains many behaviors involving:

- `import.meta.url`
- `import.meta.filename`
- `import.meta.dirname`
- `import.meta.main`
- `import.meta.resolve()`
- module caching
- singleton state
- symlinks
- duplicate dependencies
- hot reload
- circular dependencies
- ESM's Temporal Dead Zone behavior

---

# 2. `import.meta`

## What is `import.meta`?

Inside an ES module, `import.meta` is an object containing metadata
about the current module.

CommonJS historically gave you:

```js
__filename;
__dirname;
require.resolve();
```

because Node wrapped CommonJS files in a function and injected those
values.

ES modules do **not** use that CommonJS wrapper.

Instead:

```js
import.meta;
```

provides module-specific metadata.

In modern Node versions, the fields you commonly care about are:

```text
import.meta.url
import.meta.filename
import.meta.dirname
import.meta.main
import.meta.resolve()
```

### Important distinction

Each module gets its **own** `import.meta`.

It is not one global object shared by the entire dependency graph.

---

# 3. `import.meta.url`

Every file-backed ES module has:

```js
console.log(import.meta.url);
```

Example:

```text
file:///home/app/src/index.mjs
```

This is a **URL string**, not a normal filesystem path.

## Why does Node use a URL?

ESM is designed around URL-based module identity.

So instead of thinking:

```text
/home/app/src/index.mjs
```

think:

```text
file:///home/app/src/index.mjs
```

The second form is a URL.

---

## 3.1 URL formatting

On Linux/macOS:

```text
file:///home/app/src/index.mjs
```

On Windows:

```text
file:///C:/Users/app/src/index.mjs
```

URLs use `/` as separators.

Special characters are URL-encoded.

For example:

```text
/home/my app/data.json
```

can appear as:

```text
/home/my%20app/data.json
```

And:

```text
#
```

is represented as:

```text
%23
```

---

# 4. Using `import.meta.url` as a Base URL

One of the most useful patterns is resolving a file relative to the
current module.

```js
const dataUrl = new URL("./data.json", import.meta.url);

console.log(dataUrl);
```

Conceptually:

```text
Current module:
file:///home/app/src/index.mjs

./data.json
       ↓
file:///home/app/src/data.json
```

The `URL` constructor applies normal URL resolution rules.

---

# 5. URL vs Filesystem Path

This distinction is extremely important.

### URL

```text
file:///home/my%20app/data.json
```

### Filesystem path

```text
/home/my app/data.json
```

They are not the same thing.

Do not blindly treat:

```js
import.meta.url;
```

as though it were:

```text
__filename
```

---

## 5.1 The `.pathname` trap

You might write:

```js
const dataUrl = new URL("./data.json", import.meta.url);

console.log(dataUrl.pathname);
```

You may get:

```text
/home/my%20app/data.json
```

Notice:

```text
%20
```

The path is still URL-encoded.

---

# 6. `fileURLToPath()`

When you need a real operating-system filesystem path, use:

```js
import { fileURLToPath } from "node:url";
```

Example:

```js
const filename = fileURLToPath(import.meta.url);
```

Now you get a real filesystem path.

For example:

```text
/home/app/src/index.mjs
```

instead of:

```text
file:///home/app/src/index.mjs
```

This also handles platform-specific path formatting.

---

# 7. The Older ESM Replacement for `__filename` and `__dirname`

Before Node provided `import.meta.filename` and `import.meta.dirname`,
the common pattern was:

```js
import { fileURLToPath } from "node:url";
import { dirname } from "node:path";

const __filename = fileURLToPath(import.meta.url);
const __dirname = dirname(__filename);
```

Mental model:

```text
import.meta.url
      ↓
fileURLToPath()
      ↓
filesystem filename
      ↓
dirname()
      ↓
filesystem directory
```

---

# 8. `import.meta.filename`

Modern Node provides:

```js
console.log(import.meta.filename);
```

Example:

```text
/home/app/src/index.mjs
```

This is a regular filesystem path.

Conceptually it is equivalent to:

```js
fileURLToPath(import.meta.url);
```

for file-backed modules.

So:

```js
import.meta.filename;
```

is the convenient modern ESM equivalent of:

```js
__filename;
```

---

# 9. `import.meta.dirname`

Similarly:

```js
console.log(import.meta.dirname);
```

might produce:

```text
/home/app/src
```

Conceptually:

```js
dirname(import.meta.filename);
```

So the mapping is:

CommonJS Modern ESM

---

`__filename` `import.meta.filename`
`__dirname` `import.meta.dirname`
`require.resolve()` `import.meta.resolve()`

---

# 10. Important: `filename` and `dirname` Are Not Universal

The filesystem helpers make sense for file-backed modules.

Consider a `data:` module.

It can have:

```js
import.meta.url;
```

but there is no normal filesystem filename.

Therefore:

```js
import.meta.filename;
import.meta.dirname;
```

can be:

```js
undefined;
```

Mental model:

```text
file: module
    → URL
    → filesystem location exists
    → filename / dirname available

non-file module
    → URL may exist
    → filesystem location may not exist
    → filename / dirname may be unavailable
```

---

# 11. Symlink Behavior

There is another important filesystem detail.

By default:

```js
import.meta.filename;
```

resolves symlinks.

Suppose:

```text
/home/app/lib/index.mjs
```

is a symlink to:

```text
/home/shared/lib/index.mjs
```

The default filename can resolve to:

```text
/home/shared/lib/index.mjs
```

Node has flags that preserve symlink spelling:

```text
--preserve-symlinks
--preserve-symlinks-main
```

If you specifically need the URL used by the loader, `import.meta.url`
is the better mental reference.

---

# 12. `import.meta.main`

`import.meta.main` answers:

> **Is this module the process entry point?**

Example:

```js
function main() {
  console.log("Starting application...");
}

if (import.meta.main) {
  main();
}
```

If you run:

```bash
node app.mjs
```

then:

```js
import.meta.main;
```

is:

```js
true;
```

If another module imports `app.mjs`:

```js
import "./app.mjs";
```

then inside `app.mjs`:

```js
import.meta.main;
```

is:

```js
false;
```

---

## 12.1 CommonJS equivalent

CommonJS traditionally used:

```js
if (require.main === module) {
  main();
}
```

ESM provides:

```js
if (import.meta.main) {
  main();
}
```

This is useful for modules that can function both as:

- reusable modules
- command-line programs

---

# 13. `import.meta.resolve()`

This API answers:

> **"Where would this module specifier resolve from the current
> module?"**

Example:

```js
const resolved = import.meta.resolve("node:fs");

console.log(resolved);
```

Result:

```text
node:fs
```

It returns a **URL string**.

---

# 14. How Different Specifiers Resolve

## Built-in module

```js
import.meta.resolve("fs");
```

returns conceptually:

```text
node:fs
```

---

## Relative module

```js
import.meta.resolve("./utils.js");
```

can return:

```text
file:///home/app/src/utils.js
```

The important part is:

> Relative resolution happens relative to the module calling
> `import.meta.resolve()`.

---

## Package

```js
import.meta.resolve("some-package");
```

uses Node's package resolution rules.

That can involve:

```text
node_modules
package.json
exports
conditions
subpaths
```

---

# 15. `import.meta.resolve()` Does NOT Import the Module

This distinction is critical.

```js
const url = import.meta.resolve("./utils.js");
```

does **not**:

- execute `utils.js`
- evaluate `utils.js`
- return its exports
- load its module state

It only answers:

```text
"Where does this specifier point?"
```

Think:

```text
resolve()
    ↓
find location

import()
    ↓
load + evaluate module
```

---

# 16. `import.meta.resolve()` vs `require.resolve()`

Conceptually:

```text
CJS:
require.resolve()

ESM:
import.meta.resolve()
```

Both answer a similar question:

> Where would this module specifier resolve?

But their underlying resolution systems differ because ESM uses
URL-based resolution and CJS uses filename-oriented resolution.

---

# 17. Resolving Package Files

Suppose a package exposes:

```text
my-lib/schema.json
```

You can resolve it:

```js
const schemaUrl = import.meta.resolve("my-lib/schema.json");
```

Then convert it into a filesystem path:

```js
import { fileURLToPath } from "node:url";
import { readFileSync } from "node:fs";

const schemaUrl = import.meta.resolve("my-lib/schema.json");

const schemaPath = fileURLToPath(schemaUrl);

const schema = readFileSync(schemaPath, "utf8");
```

Flow:

```text
package specifier
      ↓
import.meta.resolve()
      ↓
URL
      ↓
fileURLToPath()
      ↓
filesystem path
      ↓
fs.readFileSync()
```

Notice that the package itself was **not imported**.

---

# 18. Package Encapsulation Still Applies

Suppose:

```json
{
  "exports": {
    ".": "./index.js"
  }
}
```

and the package physically contains:

```text
schema.json
```

But `schema.json` is not exposed through `"exports"`.

Then:

```js
import.meta.resolve("my-lib/schema.json");
```

can fail with an exports-related error.

The fact that the file exists physically does not mean consumers are
allowed to access it through the package specifier.

Important rule:

> **`exports` controls the public package surface.**

This also applies to:

```js
require.resolve("my-lib/schema.json");
```

in CommonJS.

---

# 19. How `import.meta` Is Populated --- Conceptual Internals

You do not need to memorize Node's internal source files, but the
architecture explains the behavior.

V8 knows about JavaScript modules.

V8 does not inherently know:

- Node filesystem paths
- Node package resolution
- `node_modules`
- package `"exports"`

So Node acts as the host environment.

Conceptually:

```text
Your ESM code
     ↓
V8 module system
     ↓
Node host integration
     ↓
Node knows module URL
     ↓
Node populates import.meta
```

Node's internal `ModuleWrap` connects Node's loader machinery to V8's
native module representation.

---

# 20. `import.meta` Is Initialized Lazily

Node initializes the metadata when module code actually accesses:

```js
import.meta;
```

If a module never accesses it, that initialization work is not needed
for that module.

This is a small optimization, but the concept is useful:

> Metadata is attached to the module by the host environment rather than
> being a CommonJS wrapper variable.

---

# 21. Module Caching

Both module systems cache modules.

Why?

Imagine:

```text
A → utility
B → utility
C → utility
D → utility
```

Without caching, Node might repeatedly:

```text
read file
parse
compile
evaluate
```

Instead:

```text
First request
    ↓
load + evaluate
    ↓
cache

Later requests
    ↓
reuse cached module
```

This gives module-level state its familiar singleton-like behavior.

---

# 22. CJS and ESM Cache Differ

This is one of the most important distinctions in the chapter.

                       CommonJS                   ESM

---

Main identity resolved filename resolved URL
Cache visibility `require.cache` not publicly exposed
Cache manipulation possible no public delete API
Typical loading `require()` `import` / `import()`
Cycle behavior partial exports possible live bindings + TDZ

---

# 23. CommonJS Cache: `Module._cache`

Suppose:

```js
const foo = require("./foo");
```

Node resolves:

```text
./foo
    ↓
/home/app/foo.js
```

Then it checks:

```js
Module._cache["/home/app/foo.js"];
```

If present, Node can return the cached exports.

It does not need to:

- read the file again
- compile it again
- evaluate it again

---

# 24. `require.cache`

CommonJS exposes the same cache through:

```js
require.cache;
```

For example:

```js
const Module = require("node:module");

console.log(require.cache === Module._cache);
// true
```

Because this is a normal JavaScript object, code can inspect it.

---

# 25. Clearing a CommonJS Cache Entry

You can do:

```js
delete require.cache[require.resolve("./myModule")];
```

The next:

```js
require("./myModule");
```

can then load a fresh module instance.

Conceptually:

```text
existing cache entry
       ↓
delete
       ↓
cache miss
       ↓
read
compile
evaluate
       ↓
new cache entry
```

---

# 26. Important: Cache Deletion Does Not Replace Existing References

Suppose:

```js
const foo = require("./foo");
```

Now:

```js
delete require.cache[require.resolve("./foo")];
```

Does `foo` automatically become the new module?

**No.**

The variable:

```js
foo;
```

still points to the old exports object.

Think:

```text
foo variable
   ↓
old exports object
```

Deleting:

```text
require.cache[key]
```

only changes what a **future `require()`** can retrieve.

It does not rewrite:

- existing variables
- existing closures
- references held by other modules
- already-created objects

This is why CommonJS hot reload can become complicated.

---

# 27. Why Restarting the Process Is Often Cleaner

Tools such as development process watchers commonly restart the process
instead of trying to surgically reload modules.

Why?

Because process restart gives you:

```text
new process
    ↓
empty module caches
    ↓
fresh module graph
    ↓
fresh state
```

Whereas manual cache deletion can leave:

```text
old references
old closures
old objects
old dependency state
```

still alive.

---

# 28. `module.children` Detail

When CommonJS module A requires module B, Node records B in A's:

```js
module.children;
```

Deleting B from:

```js
require.cache;
```

does not automatically remove B from:

```js
module.children;
```

This matters for sophisticated:

- test isolation
- module reset
- hot reload
- dependency graph tooling

You generally do not need to manipulate this yourself in normal backend
code.

---

# 29. CJS Cache + Symlinks

CommonJS commonly uses the resolved real filename as its cache identity.

Suppose:

```text
/home/app/node_modules/foo
```

is a symlink to:

```text
/home/shared/foo
```

The cache key can become:

```text
/home/shared/foo/index.js
```

Therefore two different symlink paths may still resolve to the same
physical file and reuse the same cache entry.

---

# 30. `--preserve-symlinks`

With:

```bash
--preserve-symlinks
```

Node can preserve symlink paths for module identity.

This can be useful in:

- monorepos
- workspace setups
- linked packages

But it can also create duplicate module instances.

Example:

```text
same physical file
       ↓
symlink path A → module instance A

symlink path B → module instance B
```

That means:

```text
two cache identities
→ two evaluations
→ two sets of module state
```

This is one reason symlink configuration can produce strange singleton
bugs.

---

# 31. ESM Loader Cache

ESM is different.

There is no public:

```js
import.cache
```

and there is no normal public API to delete ESM cache entries.

The ESM loader maintains its own internal cache structures.

The key idea you should remember is:

> **ESM caching is loader-managed and URL-based.**

Do not memorize internal filenames unless you are studying Node
internals.

---

# 32. ESM Cache Identity = Resolved URL

Suppose:

```js
import "./foo.mjs";
```

resolves to:

```text
file:///home/app/foo.mjs
```

The loader caches that URL's module record.

Later:

```js
import "./foo.mjs";
```

resolves to the same URL.

Therefore:

```text
same URL
   ↓
same module identity
   ↓
same evaluation
   ↓
same module state
```

---

# 33. Query Strings Change ESM Module Identity

This is one of the most important ESM-specific behaviors.

Consider:

```js
import "./foo.mjs";
import "./foo.mjs?v=1";
import "./foo.mjs?v=2";
```

They can resolve to:

```text
file:///home/app/foo.mjs
file:///home/app/foo.mjs?v=1
file:///home/app/foo.mjs?v=2
```

Those are three different URLs.

Therefore Node can treat them as:

```text
Module A
Module B
Module C
```

even though they point to the same underlying file.

---

# 34. Fragments Also Affect Identity

The same principle applies to URL fragments.

Conceptually:

```text
file:///home/app/foo.mjs#one
file:///home/app/foo.mjs#two
```

are different URLs.

Therefore they can represent different ESM module identities.

---

# 35. ESM Query Strings as Cache Busting

This means dynamic imports can sometimes be used like:

```js
await import(`./plugin.mjs?v=${version}`);
```

A new query string produces a new module identity.

This can be useful during development.

But there is a serious downside.

---

# 36. The Memory Problem with Unique ESM URLs

Suppose you continuously generate:

```text
foo.mjs?v=1
foo.mjs?v=2
foo.mjs?v=3
...
foo.mjs?v=100000
```

Each URL can represent another module instance.

So:

```text
unique URLs
    ↓
unique module records
    ↓
more module instances
    ↓
more memory
```

They remain associated with the process lifetime.

Therefore:

> **Do not use endlessly changing ESM query strings as a production
> hot-reload strategy.**

---

# 37. Why ESM Has No Simple Cache Delete API

CommonJS makes this easy to understand:

```js
delete require.cache[key];
```

But ESM has a graph of linked module records.

Conceptually:

```text
A
↓
B
↓
C
```

and imports are connected to bindings.

After evaluation:

```text
A namespace/bindings
      ↓
B bindings
      ↓
C bindings
```

Other module records may already depend on those records.

Simply deleting one lookup entry would not safely undo all those
relationships.

So ESM does not expose a simple equivalent to:

```js
delete require.cache[key];
```

---

# 38. Singleton State Through Module Caching

A very useful backend concept:

> **A module can naturally act like a singleton because the module
> system evaluates it once per module identity.**

Example:

```js
// counter.mjs

let count = 0;

export function increment() {
  count++;
}

export function getCount() {
  return count;
}
```

Suppose:

```text
server.js → counter.mjs
worker.js → counter.mjs
routes.js → counter.mjs
```

If all resolve to the same URL:

```text
same module identity
       ↓
one evaluation
       ↓
one `count`
```

Every importer interacts with the same module-level state.

---

# 39. You Do Not Need a Singleton Class

You do not necessarily need:

```js
class CounterSingleton {}
```

The module system already gives you shared state.

For example:

```js
let connection;

export function getConnection() {
  if (!connection) {
    connection = createConnection();
  }

  return connection;
}
```

The module itself can own the state.

This pattern is common for things such as:

- configuration
- connection pools
- clients
- registries
- shared caches

But there is a major condition:

> All consumers must resolve to the same module identity.

---

# 40. Duplicate Package Installs Can Break Singleton Assumptions

Suppose your dependency graph contains:

```text
app
├── package-A
│   └── node_modules/shared-lib
│
└── node_modules/shared-lib
```

Now there may be two copies:

```text
shared-lib copy A
shared-lib copy B
```

Each copy can be evaluated separately.

Therefore:

```text
two module identities
→ two module states
→ two "singletons"
```

This can cause:

- duplicate logger instances
- duplicate database pools
- different configuration state
- separate registries
- unexpected `instanceof` behavior

A useful debugging command is:

```bash
npm ls <package>
```

---

# 41. Workers Have Separate Module Caches

A `worker_threads` worker has its own module graph.

So:

```text
Main thread
    ↓
counter.mjs
    ↓
count = 0
```

and:

```text
Worker
    ↓
counter.mjs
    ↓
count = 0
```

are separate module states.

Even though both run inside the same operating-system process, their
module caches are separate.

Therefore:

> **Same process does not necessarily mean same module singleton.**

---

# 42. V8 Module States

To understand ESM cycles and cache behavior, it helps to know the broad
V8 module lifecycle.

A synchronous ESM module goes through:

```text
Uninstantiated
      ↓
Instantiating
      ↓
Instantiated
      ↓
Evaluating
      ↓
Evaluated
```

There is also:

```text
Errored
```

---

# 43. State 1 --- Uninstantiated

V8 has parsed the source and created the module record.

It knows:

- static imports
- static exports
- module structure

But runtime binding storage has not been fully initialized.

Important:

> **The code has not executed yet.**

---

# 44. State 2 --- Instantiating

V8 allocates binding slots and connects imports to exports.

Example:

```js
// a.mjs
export const x = 10;
```

and:

```js
// b.mjs
import { x } from "./a.mjs";
```

The import in B becomes connected to the export binding in A.

It is not:

```text
copy x's value
```

It is:

```text
B.x import
   ↓
A.x export binding
```

That is the basis of **live bindings**.

---

# 45. Cycles Are Detected During Instantiation

If:

```text
A → B
B → A
```

V8 discovers the cycle while linking the module graph.

But:

> **A cycle does not automatically mean failure.**

The graph can still be instantiated.

The danger comes when code reads a binding before it has been
initialized.

---

# 46. State 3 --- Instantiated

All module bindings have been connected.

But top-level code still has not run.

This is a subtle but important distinction:

```text
bindings connected
≠
values initialized
≠
top-level code evaluated
```

For example, lexical declarations such as:

```js
let
const
class
```

can still be uninitialized.

---

# 47. State 4 --- Evaluating

Now top-level module code runs.

For example:

```js
export const x = 10;

console.log("running");
```

During evaluation:

```text
x receives its initialized value
```

and:

```text
console.log()
```

executes.

---

# 48. State 5 --- Evaluated

The module completed top-level execution successfully.

Its state remains associated with the module record.

Mutable exported bindings can still change:

```js
export let count = 0;

export function increment() {
  count++;
}
```

Importers continue to observe the live binding.

---

# 49. Evaluated Is Not Resettable

V8 does not provide a simple operation that means:

```text
take this evaluated module
↓
make it a brand-new uninstantiated module
```

That is another reason ESM cache invalidation is not equivalent to
deleting a property from:

```js
require.cache;
```

---

# 50. State 6 --- Errored

If module evaluation throws:

```js
throw new Error("startup failed");
```

the module record becomes errored.

Future use of that same module record rethrows the stored error.

For the same URL, you should not expect:

```text
edit source
↓
try same module again
↓
fresh evaluation
```

within the same module record.

Restarting the process is the clean reset.

A different URL, such as one with a different query string, can
represent a different module identity.

---

# 51. Important: Resolution/Load Errors vs Evaluation Errors

These are different categories.

### Resolution error

Node cannot resolve the requested module.

Example:

```text
ERR_MODULE_NOT_FOUND
```

### Package exports error

The package exists, but the requested subpath is not exposed.

Example:

```text
ERR_PACKAGE_PATH_NOT_EXPORTED
```

### Evaluation error

The module was found and evaluated, but its code threw.

These failures happen at different stages.

Mental model:

```text
resolve
  ↓
load
  ↓
parse
  ↓
link
  ↓
evaluate
```

The earlier the failure, the different the debugging approach.

---

# 52. CommonJS Cycle Timing

CommonJS has a very different cycle mechanism.

When a fresh CJS module starts loading, Node conceptually does:

```text
1. create Module object
2. module.exports = {}
3. put Module into cache
4. compile/wrap source
5. execute source
```

The critical part is:

> **The module enters the cache before its code finishes executing.**

That enables partial exports during cycles.

---

# 53. Classic CommonJS Circular Dependency

### `a.js`

```js
module.exports.x = 1;

const b = require("./b");

module.exports.y = 2;

console.log("a sees b:", { ...b });
```

### `b.js`

```js
const a = require("./a");

module.exports.value = 42;

console.log("b sees a:", { ...a });
```

Run:

```bash
node a.js
```

Conceptual output:

```text
b sees a: { x: 1 }
a sees b: { value: 42 }
```

---

# 54. Why Does B See Only `{ x: 1 }`?

Sequence:

```text
A starts
↓
A exports x = 1
↓
A requires B
↓
B starts
↓
B requires A
↓
A already exists in CJS cache
↓
B receives A's current exports object
↓
A has not reached y = 2 yet
```

So B sees:

```js
{
  x: 1;
}
```

not:

```js
{
  x: 1,
  y: 2
}
```

because `y` has not been added yet.

---

# 55. CJS Cycles Expose Partial Objects

This is the key CJS mental model:

```text
module.exports
     ↓
cached early
     ↓
currently contains whatever has been assigned so far
```

Therefore circular dependencies can expose:

```text
partial exports
```

This can lead to bugs such as:

```js
someFunction === undefined;
```

even though the function exists later in the module.

---

# 56. Mutating `module.exports` vs Replacing It

This distinction is especially important in circular dependencies.

### Safer during cycles

```js
module.exports.x = 1;
module.exports.y = 2;
```

This keeps mutating the same object.

### Dangerous pattern

```js
module.exports = {
  x: 1,
  y: 2,
};
```

Why?

Because another module may already have a reference to the old object.

---

# 57. CJS `module.exports` Replacement Problem

Imagine:

```text
A's initial exports object
        ↑
        |
B holds reference
```

Later A does:

```js
module.exports = {
  x: 1,
  y: 2,
};
```

Now:

```text
A's cache → NEW object
B         → OLD object
```

B does not magically switch to the new object.

This is the same reference/aliasing principle behind many CommonJS
export bugs.

---

# 58. ESM Circular Dependencies

ESM does not work by handing another module a half-built exports object.

Instead:

```text
import binding
      ↓
export binding
```

The binding is connected during linking.

This is called a **live binding**.

---

# 59. Live Binding Does Not Mean "Always Initialized"

This distinction is critical.

An imported binding can exist:

```text
binding exists
```

while its exported lexical variable is still:

```text
uninitialized
```

If another module reads it too early, JavaScript's Temporal Dead Zone
rules apply.

The result can be:

```text
ReferenceError
```

---

# 60. ESM Circular Dependency Example

### `a.mjs`

```js
import { value } from "./b.mjs";

export const x = 1;

console.log("a sees value:", value);
```

### `b.mjs`

```js
import { x } from "./a.mjs";

export const value = 42;

console.log("b sees x:", x);
```

During linking, the bindings are connected.

But during evaluation, one module can run before the other's lexical
export has been initialized.

If:

```js
x;
```

is read too early, you can get:

```text
ReferenceError: Cannot access 'x' before initialization
```

---

# 61. CJS vs ESM Cycle: The Core Difference

---

CommonJS ESM

---

Module object is cached early Module records/bindings are linked

Other module can receive partial Other module receives binding
exports object connection

Partial object can be observed Uninitialized lexical binding can
throw

`module.exports` reference matters Live binding matters

`ReferenceError`

---

A useful simplified comparison:

```text
CJS:

A exports object
     ↓
cached early
     ↓
B receives current object
     ↓
possibly partial


ESM:

A export binding
     ↓
linked before evaluation
     ↓
B receives live connection
     ↓
```

# 62. ESM Live Bindings

Consider:

```js
// c.mjs
export let count = 0;

import { logCount } from "./d.mjs";

count = 10;
logCount();
```

and:

```js
// d.mjs
import { count } from "./c.mjs";

export function logCount() {
  console.log("count is:", count);
}
```

When:

```js
count = 10;
```

happens, the imported binding remains connected.

Then:

```js
logCount();
```

reads the current value:

```text
count is: 10
```

It is not a stale snapshot.

---

# 63. Why Functions Often Make Cycles Safer

Compare:

```js
export const snapshot = count;
```

with:

```js
export function getCount() {
  return count;
}
```

The first reads `count` immediately during startup.

The second reads it later when the function executes.

Therefore:

```text
top-level read
    ↓
more cycle-sensitive

function read
    ↓
delayed until call
    ↓
usually easier to reason about
```

This is a very useful design technique.

---

# 64. Cycles Are Usually a Design Smell

A circular dependency is not automatically invalid.

But if:

```text
A → B
B → A
```

you should ask:

> Why do these modules know so much about each other?

Often there is a missing abstraction.

For example:

```text
A ↔ B
```

might become:

```text
A → shared
B → shared
```

where:

```text
shared → neither A nor B
```

This produces a cleaner dependency graph.

---

# 65. Breaking Cycles with a Shared Module

Instead of:

```text
A ↔ B
```

create:

```text
A → shared
B → shared
```

Example:

```js
// shared.js
export function formatUser(user) {
  // shared logic
}
```

Then:

```js
// a.js
import { formatUser } from "./shared.js";
```

and:

```js
// b.js
import { formatUser } from "./shared.js";
```

Now the shared abstraction has no reason to import either A or B.

---

# 66. Dependency Inversion

Another option is to invert the dependency.

Instead of:

```text
A directly imports B
```

A can accept something B provides later:

```js
export function createService(callback) {
  return {
    run() {
      return callback();
    },
  };
}
```

The runtime relationship still exists, but the static module graph does
not necessarily contain a cycle.

This is often cleaner for larger systems.

---

# 67. Lazy CommonJS Dependencies

In CommonJS, you can delay a dependency:

```js
module.exports.x = 1;

module.exports.getB = () => require("./b");
```

Now:

```text
initial loading
    ↓
B is not required yet

later getB()
    ↓
require('./b')
```

This moves the dependency away from startup.

It can avoid a circular initialization window.

However, lazy loading should be used intentionally, not merely to hide
poor architecture.

---

# 68. Lazy ESM Dependencies: `import()`

In ESM:

```js
export const x = 1;

export async function getB() {
  const b = await import("./b.mjs");
  return b.value;
}
```

Here:

```text
static graph
    ↓
A does not immediately depend on B

later:
getB()
    ↓
dynamic import()
    ↓
B loads
```

This can prevent startup-time TDZ problems.

---

# 69. Static vs Dynamic Dependency

### Static import

```js
import { x } from "./x.mjs";
```

The dependency is part of the static module graph.

### Dynamic import

```js
const module = await import("./x.mjs");
```

The dependency is requested later at runtime.

This distinction matters for:

- circular dependencies
- lazy loading
- startup cost
- code splitting
- optional functionality

# 70. How to Debug a Module Identity Problem

When you suspect duplicate module instances, ask:

### Step 1 --- What module system?

```text
CJS or ESM?
```

### Step 2 --- What is the resolved identity?

For CJS:

```js
require.resolve("some-package");
```

For ESM:

```js
console.log(import.meta.resolve("some-package"));
```

### Step 3 --- Are there duplicate package installations?

```bash
npm ls some-package
```

### Step 4 --- Are symlinks involved?

Check workspace/monorepo setup and Node symlink flags.

### Step 5 --- Are multiple workers involved?

Each worker has its own module graph/cache.

---

# 71. How to Debug Circular Dependencies

Start with the graph:

```text
A → B → C → A
```

Then identify:

1.  Which module is evaluated first?
2.  Which export is read during top-level execution?
3.  Has that export been initialized yet?
4.  Is CJS exposing a partial object?
5.  Is ESM reading a lexical binding inside its TDZ?
6.  Can the dependency be delayed?
7.  Can shared logic be extracted?

Suppose:

```js
// db.mjs
let client;

export function getDb() {
  if (!client) {
    client = createDatabaseClient();

  return client;
```

If all application code imports the same `db.mjs` URL:

```text
routes
services
jobs
controllers
    ↓
same db.mjs
    ↓
same module state
    ↓
same client
```

This is a valid and common pattern.

But if duplicate package/module identities appear, the assumption can

# 74. Practical Backend Example: Configuration

A module can own application configuration:

```js
// config.mjs
export const config = {
  port: process.env.PORT || 3000,
  env: process.env.NODE_ENV || "development",
};
```

All importers resolving the same module identity receive the same
exported module state.

The important point is not the `config` object itself.

The important point is:

```text
same module identity
→ same module evaluation
→ shared module state
```

# 75. Practical Backend Example: Why Workers Are Different

Suppose your API process has:

```text
main thread
    ↓
cache.mjs
```

and a worker has:

```text
worker thread
    ↓
cache.mjs
```

Do not assume they share:

```js
let cache = new Map();
```

They do not simply share the same module instance.

For cross-thread shared state, you need an explicit
communication/shared-memory mechanism rather than relying on module
caching.

This entire chapter becomes easier if you focus on one question:

> **What exact identity does Node use for this module?**

For CJS:

```text
resolved filename
```

For ESM:

```text
resolved URL
```

Then:

```text
identity
   ↓
cache entry
   ↓
module instance
   ↓
module-level state
```

# 77. Why "Same File" Does Not Always Mean "Same Module"

This is a common misconception.

You might think:

```text
same physical file
    =
same module
```

Not necessarily.

For ESM:

```text
foo.mjs
foo.mjs?v=1
foo.mjs?v=2
```

can represent different identities.

For packages:

```text
copy A of package
copy B of package
```

can represent different module instances.

For symlinked packages:

```text
different paths
```

can affect identity depending on Node's resolution/symlink behavior.

# 78. `import.meta.url` vs `import.meta.filename`

Use:

### `import.meta.url`

when you need:

- the module's URL
- URL-relative resolution
- a URL for another API
- the loader's URL identity

Example:

```js
const url = new URL("./data.json", import.meta.url);
```

### `import.meta.filename`

when you need:

- a filesystem path
- path-oriented APIs
- the current module's filename

Example:

```js
console.log(import.meta.filename);
```

---

# 79. `URL` Objects vs URL Strings

This distinction is also important.

`import.meta.url` is:

```js
string;
```

while:

```js
new URL("./data.json", import.meta.url);
```

creates a:

```js
URL object
```

Some Node APIs accept `URL` objects directly.

For example, filesystem APIs can accept a `URL` object.

Therefore this can be useful:

```js
import { readFileSync } from "node:fs";

const dataUrl = new URL("./data.json", import.meta.url);

const data = readFileSync(dataUrl, "utf8");
```

You do not always need to convert to a path first.

---

# 80. Common Mistake: Passing a URL String as a Path

This is wrong conceptually:

```js
const url = import.meta.url;

readFileSync(url, "utf8");
```

because:

```js
import.meta.url;
```

is a URL **string**.

Do not confuse:

```text
URL string
```

with:

```text
URL object
```

or:

```text
filesystem path string
```

When necessary, use:

```js
fileURLToPath(import.meta.url);
```

or create a proper URL object:

```js
new URL("./data.json", import.meta.url);
```

---

# 81. Common Mistake: Assuming ESM Has `__dirname`

This does not work in normal ESM:

```js
console.log(__dirname);
```

Instead use:

```js
import.meta.dirname;
```

when available in your supported Node version.

Or the compatibility pattern:

```js
import { fileURLToPath } from "node:url";
import { dirname } from "node:path";

const filename = fileURLToPath(import.meta.url);
const directory = dirname(filename);
```

---

# 82. Common Mistake: Treating `import.meta.resolve()` as `import()`

These are fundamentally different:

```js
import.meta.resolve("./foo.mjs");
```

means:

```text
Where is foo.mjs?
```

while:

```js
await import("./foo.mjs");
```

means:

```text
Load/evaluate foo.mjs and give me its module namespace.
```

---

# 83. Common Mistake: Assuming `require.cache` Controls ESM

It does not.

```js
require.cache;
```

is the CommonJS cache.

ESM has a separate loader-managed cache.

Therefore:

```text
delete require.cache[...]
```

does not provide general ESM cache invalidation.

---

# 84. Common Mistake: Assuming Cache Deletion Resets State Everywhere

Even in CommonJS:

```js
delete require.cache[key];
```

does not destroy every old reference.

If some code still has:

```js
const oldModule = require("./module");
```

then:

```text
oldModule
```

still exists.

Therefore cache deletion is not equivalent to:

```text
"destroy every object created by this module"
```

---

# 85. Common Mistake: Assuming a Singleton Is Always Singleton

A module-level singleton depends on module identity.

It can be duplicated through:

- duplicate dependency installations
- symlink differences
- worker threads
- different ESM URLs
- separate copies of a package

So the better statement is:

> **A module is singleton-like within one module graph/cache identity,
> not globally across every execution context.**

---

# 86. Common Mistake: Ignoring Circular Dependencies

CJS cycles can silently expose partial exports.

ESM cycles can throw:

```text
ReferenceError: Cannot access 'x' before initialization
```

If startup suddenly produces:

```text
undefined
```

or:

```text
Cannot access ... before initialization
```

inspect the module graph.

# 87. Backend Best Practices

## 1. Prefer simple dependency graphs

Aim for:

```text
controllers
    ↓
services
    ↓
repositories
    ↓
database
```

rather than:

```text
A ↔ B ↔ C ↔ A
```

---

## 2. Keep initialization predictable

Avoid doing complex work at module top level when other modules depend
on it.

Prefer:

```js
export function createService() {
  // initialization
}
```

or:

```js
export async function initialize() {
  // startup work
}
```

when appropriate.

---

## 3. Treat module-level state deliberately

Ask:

```text
Should this state be shared?
```

If yes:

```text
module-level state can be useful
```

If no:

```text
create state per request/object/function
```

---

## 4. Do not depend on cache hacks for production architecture

Manual cache deletion is a development/testing technique, not a
substitute for clean application lifecycle design.

---

## 5. Be careful with duplicate dependencies

For singleton-sensitive libraries:

```bash
npm ls <package>
```

can help detect multiple installed versions/copies.

---

## 6. Be deliberate with symlinks

Especially in:

- monorepos
- workspaces
- local package linking

understand how Node's symlink behavior affects module identity.

# 88. A Complete ESM Startup Mental Model

Suppose:

```text
app.mjs
  ↓
service.mjs
  ↓
db.mjs
```

Conceptually:

```text
1. Resolve specifiers
        ↓
2. Obtain URLs
        ↓
3. Load source
        ↓
4. Parse modules
        ↓
5. Link import/export bindings
        ↓
6. Evaluate modules
        ↓
7. Cache module records
        ↓
8. Reuse same records for same URLs
```

If:

```text
same URL
```

is encountered again:

```text
reuse existing module identity
```

If:

```text
different URL
```

is encountered:

```text
potentially different module identity
```

# 89. Complete CJS Startup Mental Model

For CommonJS:

```text
require(specifier)
       ↓
resolve filename
       ↓
check require.cache
       ↓
cache hit?
   ↙        ↘
 yes        no
 ↓           ↓
exports    create Module
            ↓
          cache early
            ↓
          compile
            ↓
          execute
            ↓
          module.exports
            ↓
          return exports
```

The "cache early" step is the reason CJS circular dependencies can
expose partial exports.

# 90. Complete ESM Cycle Mental Model

For ESM:

```text
parse graph
    ↓
resolve dependencies
    ↓
link bindings
    ↓
detect cycle structure
    ↓
evaluate
    ↓
top-level read
    ↓
binding initialized?
   ↙          ↘
 yes          no
 ↓             ↓
value          ReferenceError
```

The binding can exist before its value is initialized.

# 91. Interview Questions

## Q1. What is `import.meta`?

It is module metadata provided by the host environment to an ES module.

In Node, it provides useful information such as the module URL,
filesystem location, entry-point status, and module resolution.

---

## Q2. What is `import.meta.url`?

It is the URL of the current ES module.

For a local file, it is typically a:

```text
file://
```

URL.

---

## Q3. Is `import.meta.url` a filesystem path?

No.

It is a URL string.

Use:

```js
fileURLToPath(import.meta.url);
```

when you need a filesystem path.

---

## Q4. How do you get `__dirname`-like behavior in ESM?

Modern Node:

```js
import.meta.dirname;
```

Compatibility pattern:

```js
import { fileURLToPath } from "node:url";
import { dirname } from "node:path";

const filename = fileURLToPath(import.meta.url);
const directory = dirname(filename);
```

---

## Q5. What does `import.meta.resolve()` do?

It resolves a module specifier relative to the current module and
returns the resulting URL string.

It does **not** import or execute the module.

---

## Q6. How is ESM caching different from CommonJS caching?

CommonJS exposes a filename-keyed cache through:

```js
require.cache;
```

ESM uses a loader-managed URL-keyed cache that does not have an
equivalent public cache deletion API.

---

## Q7. Why can ESM query strings create duplicate module instances?

Because URL identity includes the query string.

Therefore:

```text
foo.mjs
foo.mjs?v=1
```

are different URLs and can represent different module records.

---

## Q8. Why is cache deletion harder in ESM?

Because ESM modules are linked into a graph of module records and live
bindings.

Deleting one lookup entry would not undo all existing relationships.

---

## Q9. How do module caches create singleton state?

A module is evaluated once for a particular module identity. Later
imports/requires reuse that identity, so module-level variables are
shared.

---

## Q10. Can a singleton be duplicated?

Yes.

Possible causes include:

- duplicate package copies
- different symlink identities
- different ESM URLs
- separate worker module graphs

---

## Q11. Why are CommonJS circular dependencies able to expose partial objects?

Because CommonJS puts the module into its cache before the module
finishes evaluating.

Another module can therefore receive the current, partially populated
`module.exports` object.

---

## Q12. Why can ESM circular dependencies throw `ReferenceError`?

ESM imports are live bindings. A binding can exist but remain
uninitialized until evaluation reaches its declaration.

Reading it too early triggers the Temporal Dead Zone.

---

## Q13. What is the key difference between CJS and ESM cycles?

Simplified:

```text
CJS → partial exports object

ESM → live binding + possible TDZ error
```

---

## Q14. How can you reduce circular dependency problems?

Prefer:

- shared modules
- dependency inversion
- delayed reads
- lazy `require()`
- dynamic `import()`
- simpler dependency graphs

---

# 95. Final Mental Model

If you remember only one chain, remember this:

```text
Specifier
   ↓
Resolution
   ↓
Module identity
   ↓
Cache
   ↓
Module instance
   ↓
Module-level state
```

For ESM:

```text
specifier
   ↓
resolved URL
   ↓
ESM loader cache
   ↓
V8 module record
   ↓
live bindings
   ↓
shared state
```

For CommonJS:

```text
specifier
   ↓
resolved filename
   ↓
require.cache
   ↓
Module object
   ↓
module.exports
   ↓
shared state
```

And for cycles:

```text
CJS:
cache early
   ↓
partial exports may be observed

ESM:
link first
   ↓
live bindings
   ↓
read before initialization
   ↓
ReferenceError
```

The deepest practical lesson is:

> **Caching is not merely an optimization. It defines module identity
> and therefore determines how module-level state is shared.**

And the second:

> **Circular dependencies are mainly an initialization-order problem,
> not simply an import-syntax problem.**

For backend development, this matters when designing:

- database clients
- configuration modules
- service registries
- caches
- dependency injection
- package boundaries
- monorepos
- worker-thread architecture
- development reload systems
- ESM/CJS migrations

Keep the dependency graph simple, understand the exact module identity
being used, and treat module-level state as an intentional architectural
decision rather than an accidental side effect of the module system.
