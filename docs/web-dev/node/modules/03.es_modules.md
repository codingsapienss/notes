# Node.js ES Modules (ESM): `import` / `export` & Linking

## 1. What Are ES Modules?

Node.js supports two major JavaScript module systems:

- **CommonJS (CJS)** → `require()` / `module.exports`
- **ES Modules (ESM)** → `import` / `export`

Example:

```js
// CommonJS
const express = require("express");
module.exports = app;
```

```js
// ESM
import express from "express";
export default app;
```

The important difference is **how Node loads them**.

### CommonJS

CommonJS can discover dependencies while code is executing:

```js
if (useRedis) {
  const redis = require("./redis.js");
}
```

`require()` is a synchronous function call.

### ESM

Static imports are known before normal module code executes:

```js
import redis from "./redis.js";
```

Node can therefore:

1.  Parse the module.
2.  Discover its imports and exports.
3.  Resolve its dependencies.
4.  Build the module graph.
5.  Create the import/export bindings.
6.  Evaluate the modules.

That up-front structure is one of the biggest reasons ESM behaves
differently from CommonJS.

---

# 2. The Most Important Mental Model: Parse → Instantiate → Evaluate

For ESM, remember:

```text
Source code
    ↓
Parse
    ↓
Discover imports/exports
    ↓
Resolve dependencies
    ↓
Instantiate / link bindings
    ↓
Evaluate module code
```

These phases explain most ESM behavior.

## Phase 1: Parsing

Node reads the source using the ES module grammar.

It discovers things such as:

```js
import { db } from "./db.js";
export const PORT = 3000;
```

At this point:

- module code has **not** run
- functions have not been called
- variables have not been initialized by evaluation
- imports/exports are being identified

If:

```text
a.js → b.js → c.js
```

Node can discover the graph before evaluating the module bodies.

---

## Phase 2: Instantiation / Linking

Now Node/V8 creates the module's bindings.

Suppose:

```js
// counter.js
export let count = 0;
```

```js
// app.js
import { count } from "./counter.js";
```

The importer does not receive an independent copy of `count`.

Conceptually:

```text
counter.js
   │
   │ owns binding
   ▼
 count = 0
   ▲
   │
app.js imported binding
```

The connection is established during linking.

This is called a **live binding**.

The value is initialized during evaluation.

---

## Phase 3: Evaluation

Now top-level code actually executes.

For example:

```js
// config.js
export const port = Number(process.env.PORT) || 3000;
console.log("config evaluated");
```

Only during evaluation does `process.env.PORT` get read and the
`console.log()` execute.

Generally, dependencies must be evaluated before modules that depend on
them.

---

# 3. Why ESM Is Called "Static"

Static does **not** mean "the module never changes."

It means the **static import declarations have a structure Node can
determine before executing the module body**.

This works:

```js
import { connect } from "./db.js";
```

This does not work as a static import:

```js
import something from condition ? "./a.js" : "./b.js";
```

For runtime-dependent loading, use dynamic import:

```js
const path = condition ? "./a.js" : "./b.js";

const module = await import(path);
```

---

# 4. Why Static Imports Matter

Because Node can know the dependency graph early, several things become
possible:

- dependency linking before execution
- earlier missing-export errors
- cycle detection
- live binding setup
- better tooling
- bundler/tree-shaking analysis
- static analysis by linters/type checkers

This is a major architectural difference from CommonJS.

# 6. How Node Decides CJS vs ESM

Before Node can load a file, it must determine its module format.

The most important rules are:

## `.mjs`

Always ESM:

```text
app.mjs → ESM
```

## `.cjs`

Always CommonJS:

```text
app.cjs → CommonJS
```

## `.js`

Depends on the nearest controlling `package.json`.

With:

```json
{
  "type": "module"
}
```

`.js` files in that package scope are ESM.

With:

```json
{
  "type": "commonjs"
}
```

or with no `"type"` field, `.js` is treated as CommonJS under the
normal/default behavior.

---

# 7. Package Scope and `"type"`

Consider:

```text
project/
├── package.json
├── app.js
└── src/
    └── server.js
```

If `package.json` contains:

```json
{
  "type": "module"
}
```

then:

```text
app.js        → ESM
src/server.js → ESM
```

A nested package can change the rule:

```text
project/
├── package.json          type: module
└── legacy/
    ├── package.json      type: commonjs
    └── old.js
```

Then:

```text
app.js       → ESM
legacy/old.js → CommonJS
```

**Use `"type"` explicitly in real projects.** Do not rely on Node
guessing.

---

# 8. `--input-type=module`

For code supplied through `--eval`, `-e`, or standard input, Node can be
explicitly told to use ESM:

```bash
node --input-type=module -e "import path from 'node:path'; console.log(path.basename('/a/b.txt'))"
```

This is mainly useful for scripts, experiments, and tooling.

---

# 9. Syntax Detection

Modern Node versions can detect some ESM-only syntax in otherwise
ambiguous JavaScript input.

Examples include:

- static `import`
- static `export`
- `import.meta`
- top-level `await`

However, **do not build production package structure around syntax
detection**.

Prefer:

```json
{
  "type": "module"
}
```

or explicit `.mjs` / `.cjs` extensions.

The goal is to make the module format obvious to:

- Node
- developers
- editors
- linters
- test runners
- build tools

---

# 10. ESM Import Syntax

There are several important forms.

---

## 10.1 Named Imports

```js
import { readFile, writeFile } from "node:fs/promises";
```

The imported names must exist as exports of the target module.

You can rename an import:

```js
import { readFile as read } from "node:fs/promises";
```

Now your local code uses:

```js
await read("data.txt");
```

The exported binding is still called `readFile`.

---

# 11. Default Imports

If a module has:

```js
export default function createApp() {
  // ...
}
```

another module can write:

```js
import createApp from "./app.js";
```

The importer chooses the local name.

These are both valid:

```js
import createApp from "./app.js";
```

```js
import makeApplication from "./app.js";
```

The export is still the `default` export.

---

# 12. Namespace Imports

You can import the entire module namespace:

```js
import * as fs from "node:fs/promises";
```

Then:

```js
await fs.readFile("data.txt");
await fs.writeFile("out.txt", "hello");
```

Conceptually:

```text
fs
 ↓
Module Namespace Object
 ├── readFile
 ├── writeFile
 ├── ...
 └── default (if present)
```

The namespace object is a special object representing the module's
exports.

You cannot treat it like an ordinary mutable object:

```js
fs.someNewProperty = 123; // rejected
```

---

# 13. Side-Effect Imports

Sometimes you want to execute a module but do not need its exports:

```js
import "./setup.js";
```

Useful for:

- application initialization
- instrumentation
- registering handlers
- polyfills
- setup code

The target module still goes through normal ESM
loading/linking/evaluation.

---

# 14. Combining Default + Named Imports

This is valid:

```js
import express, { Router } from "some-package";
```

The exact availability of a default export and named exports depends on
the target package.

Do not assume that every package supports both forms.

---

# 15. ESM Export Syntax

## Named Export

```js
export const PORT = 3000;

export function startServer() {
  // ...
}

export class Router {
  // ...
}
```

These create named exports:

```text
PORT
startServer
Router
```

---

## Export Later

You can declare first:

```js
const PORT = 3000;

function startServer() {
  // ...
}

export { PORT, startServer };
```

Same public exports.

---

# 16. Renaming Exports

You can expose a local name under another public name:

```js
function startServer() {
  // ...
}

export { startServer as start };
```

Consumers use:

```js
import { start } from "./server.js";
```

The local binding is still:

```text
startServer
```

The public export is:

```text
start
```

---

# 17. Default Export

A module can have one default export:

```js
export default function createApp() {
  return {};
}
```

Consumer:

```js
import createApp from "./app.js";
```

Or:

```js
import whateverNameYouWant from "./app.js";
```

The local name is chosen by the importer.

---

# 18. Named vs Default Export

A useful practical distinction:

```js
export function createUser() {}
export function deleteUser() {}
```

These expose specific named API members.

Versus:

```js
export default function createUser() {}
```

This exposes one default API value.

Neither is universally "better."

For larger backend modules, named exports often make the public API
explicit:

```js
export { createUser, findUser, deleteUser };
```

---

# 19. Important Default-Export Live-Binding Detail

This is subtle and worth understanding.

Consider:

```js
let count = 0;

export default count;

count++;
```

The default expression exports the value produced when that expression
is evaluated.

It is **not equivalent** to exporting the `count` binding itself.

If you want the binding:

```js
let count = 0;

export { count };

count++;
```

Now consumers observe the live binding.

### Rule

```js
export { count };
```

means:

> export this binding.

Whereas:

```js
export default count;
```

means:

> evaluate this default expression and use its resulting value as the
> default export.

---

# 20. Re-Exports

A module can forward exports from another module.

```js
export { readFile, writeFile } from "node:fs/promises";
```

This module does not need to create local variables first.

---

## Re-Export a Default Export as a Named Export

```js
export { default as EventEmitter } from "node:events";
```

Now consumers can do:

```js
import { EventEmitter } from "./api.js";
```

---

# 21. `export *`

You can forward named exports:

```js
export * from "./utils.js";
```

Important:

> `export *` does **not** re-export the default export.

If you also want the default:

```js
export { default } from "./utils.js";
```

or:

```js
export { default as utils } from "./utils.js";
```

---

# 22. Barrel Files

A common backend/project pattern is a barrel file:

```text
services/
├── user.service.js
├── auth.service.js
├── payment.service.js
└── index.js
```

`index.js`:

```js
export { createUser } from "./user.service.js";
export { login } from "./auth.service.js";
export { charge } from "./payment.service.js";
```

Consumers:

```js
import { createUser, login } from "./services/index.js";
```

Benefits:

- cleaner public API
- hides internal file structure
- centralizes exports

But avoid creating enormous barrel files without a reason; they can make
dependency relationships harder to understand.

---

# 23. Live Bindings --- One of the Most Important ESM Concepts

ESM imports are **live bindings**.

Example:

```js
// counter.js
export let count = 0;

export function increment() {
  count++;
}
```

```js
// main.js
import { count, increment } from "./counter.js";

console.log(count); // 0

increment();

console.log(count); // 1
```

Why?

Because `main.js` is connected to the exported `count` binding owned by
`counter.js`.

It is not simply:

```js
const count = 0;
```

copied into `main.js`.

---

# 24. Importers Cannot Reassign Imported Bindings

This is invalid:

```js
import { count } from "./counter.js";

count = 10;
```

The importer does not own that binding.

The exporter owns it:

```js
// counter.js
export let count = 0;

export function setCount(value) {
  count = value;
}
```

Then:

```js
import { count, setCount } from "./counter.js";

setCount(10);

console.log(count); // 10
```

---

# 25. ESM Live Binding vs CommonJS Destructuring

CommonJS:

```js
const counter = require("./counter.js");

console.log(counter.count);
counter.increment();
console.log(counter.count);
```

This can observe property changes because the object is retained.

But:

```js
const { count, increment } = require("./counter.js");

increment();

console.log(count);
```

`count` is now a local variable holding the value obtained during
destructuring.

For primitive values, later changes do not update that local variable.

### Important distinction

```text
ESM import
    ↓
live binding

CJS object property
    ↓
property lookup each time

CJS destructuring
    ↓
local value obtained from property
```

This distinction matters when migrating code from CommonJS to ESM.

---

# 26. Circular Imports in ESM

Suppose:

```text
a.js → b.js
↑      ↓
└──────┘
```

ESM can represent this cycle because bindings are created during
instantiation before evaluation.

That does **not** mean every circular dependency is safe.

The danger is reading an export before it has initialized.

Example:

```js
// a.js
import { valueB } from "./b.js";

export const valueA = valueB + 1;
```

```js
// b.js
import { valueA } from "./a.js";

export const valueB = valueA + 1;
```

One side may attempt to read a lexical binding while it is still
uninitialized.

That can produce:

```text
ReferenceError
```

---

# 27. Temporal Dead Zone in Circular Imports

For:

```js
export let value = 10;
```

or:

```js
export const value = 10;
```

the binding exists during linking, but it is not readable before
initialization during evaluation.

So:

```text
binding exists
      ↓
not initialized yet
      ↓
read too early
      ↓
ReferenceError
```

`var` has different initialization behavior and can produce `undefined`
in situations where lexical bindings throw.

---

# 28. Practical Rule for Circular Dependencies

Circular imports are safest when the top-level code does not immediately
read another module's not-yet-initialized values.

Prefer:

```js
export function getValue() {
  return otherValue;
}
```

over eagerly reading the value during initialization when the dependency
graph is cyclic.

If a cycle becomes complicated, consider:

```text
A ↔ B
```

becoming:

```text
A → shared.js
B → shared.js
```

or redesigning the dependency direction.

---

# 29. Dynamic `import()`

Static import:

```js
import { createClient } from "./client.js";
```

Dynamic import:

```js
const module = await import("./client.js");
```

Dynamic import returns a Promise.

```js
const mod = await import("./heavy-module.js");

mod.doSomething();
```

---

# 30. Why `import()` Is Different

The argument to `import()` is evaluated at runtime.

Therefore:

```js
const language = getUserLanguage();

const i18n = await import(`./locales/${language}.js`);
```

is possible.

This is not possible with a static import declaration.

---

# 31. `import()` Works in CommonJS Too

This is particularly important for migration.

A CommonJS file can do:

```js
async function main() {
  const mod = await import("./modern-esm-module.mjs");

  mod.start();
}

main();
```

This is one of the main bridges from CJS to ESM.

---

# 32. `import()` Returns the Module Namespace

If:

```js
// math.js
export const add = (a, b) => a + b;

export default function multiply(a, b) {
  return a * b;
}
```

Then:

```js
const math = await import("./math.js");

math.add(2, 3);
math.default(2, 3);
```

The namespace contains:

```text
math
├── add
└── default
```

---

# 33. `import()` Is Asynchronous

CommonJS:

```js
const db = require("./db.js");

startServer();
```

The dependency is loaded before `require()` returns.

Dynamic ESM:

```js
const db = await import("./db.js");

startServer();
```

The code must account for the Promise.

This makes dynamic import useful for:

- lazy loading
- optional functionality
- plugin systems
- expensive modules
- runtime-selected modules
- CJS → ESM migration

---

# 34. ESM Uses URLs Internally

A major difference from CommonJS is that ESM module identity is
URL-based.

A file such as:

```js
import "./utils.js";
```

is internally resolved to something like:

```text
file:///Users/dev/project/utils.js
```

The exact filesystem path depends on the machine.

---

# 35. URL-Based Cache Identity

ESM caching is based on the resolved URL.

These can therefore represent different module identities:

```js
import "./foo.js";
import "./foo.js?version=2";
```

Even though they refer to the same underlying source file, the URLs
differ.

Conceptually:

```text
file:///project/foo.js
              ≠
file:///project/foo.js?version=2
```

Therefore they can produce separate module instances.

### Why this matters

If a module contains mutable state:

```js
export const state = {
  requests: 0,
};
```

loading it twice under different URLs can create two separate states.

This is an advanced edge case, but important for tooling, loaders,
tests, and debugging.

---

# 36. Built-in Modules and `node:`

Node built-ins can be imported using:

```js
import fs from "node:fs";
```

```js
import { readFile } from "node:fs/promises";
```

The `node:` scheme clearly indicates a Node built-in.

This is preferable in modern Node code because it removes ambiguity with
package names.

---

# 37. `data:` Modules

Node also supports inline modules through `data:` URLs:

```js
import { name } from 'data:text/javascript,export const name="inline"';
```

This is mainly useful for:

- experiments
- tests
- specialized tooling

It is not a normal application architecture.

---

# 38. Mandatory File Extensions in ESM

This is one of the most important migration differences.

CommonJS can often do:

```js
const utils = require("./utils");
```

and Node probes:

```text
./utils
./utils.js
./utils.json
./utils.node
```

ESM does not perform the same extension probing for relative imports.

Write:

```js
import utils from "./utils.js";
```

not:

```js
import utils from "./utils";
```

---

# 39. Directory Imports

CommonJS commonly supports directory resolution such as:

```js
require("./utils");
```

leading to an `index.js` fallback in appropriate situations.

Do not expect ESM to turn:

```js
import "./utils/";
```

into:

```js
import "./utils/index.js";
```

Instead write the actual file:

```js
import "./utils/index.js";
```

or, preferably, expose a clear package entry point where appropriate.

Directory imports can produce:

```text
ERR_UNSUPPORTED_DIR_IMPORT
```

---

# 40. ESM and `package.json` `"exports"`

For package imports:

```js
import express from "some-package";
```

or:

```js
import x from "some-package/utils";
```

package metadata can control what consumers are allowed to access.

The `"exports"` field is particularly important for modern Node
packages.

Example:

```json
{
  "exports": {
    ".": "./src/index.js",
    "./utils": "./src/utils.js"
  }
}
```

Consumers can use:

```js
import pkg from "some-package";
```

and:

```js
import { helper } from "some-package/utils";
```

but arbitrary internal paths may be blocked.

This creates a public package API boundary.

---

# 41. `main` vs `exports`

Historically:

```json
{
  "main": "./index.js"
}
```

defined the main package entry point.

Modern packages often use:

```json
{
  "exports": {
    ".": "./index.js"
  }
}
```

`exports` is more powerful because it can define:

- multiple entry points
- public subpaths
- conditional exports
- ESM/CJS variants
- package API boundaries

For modern Node package development, understand `exports` well.

---

# 42. Conditional Exports

A package can provide different files depending on the
environment/loader conditions.

Conceptually:

```json
{
  "exports": {
    ".": {
      "import": "./dist/index.js",
      "require": "./dist/index.cjs"
    }
  }
}
```

Then:

```text
ESM consumer
    ↓
import condition
    ↓
dist/index.js
```

while:

```text
CJS consumer
    ↓
require condition
    ↓
dist/index.cjs
```

This is important when publishing libraries supporting both module
systems.

---

# 43. `import` vs `require` Conditions

When designing dual-format packages, you may encounter:

```json
{
  "exports": {
    ".": {
      "import": "./dist/index.js",
      "require": "./dist/index.cjs"
    }
  }
}
```

The package can therefore expose different implementations depending on
how it is consumed.

Do not assume:

```text
ESM → always .mjs
CJS → always .cjs
```

Package `"exports"` can map these conditions to whatever files the
package author chooses.

---

# 44. `import.meta`

Every ESM module gets:

```js
import.meta;
```

It provides metadata about the current module.

The most important property is:

```js
console.log(import.meta.url);
```

For a local file:

```text
file:///project/src/server.js
```

---

# 45. `import.meta.url` Replaces a Major Use of `__filename`

CommonJS:

```js
console.log(__filename);
console.log(__dirname);
```

ESM:

```js
console.log(import.meta.url);
```

Modern Node also provides:

```js
console.log(import.meta.filename);
console.log(import.meta.dirname);
```

for local `file:` modules.

---

# 46. Converting `import.meta.url` to a Filesystem Path

The portable/manual pattern is:

```js
import { fileURLToPath } from "node:url";
import { dirname } from "node:path";

const filename = fileURLToPath(import.meta.url);
const directory = dirname(filename);
```

This is useful when an API requires a normal filesystem path.

---

# 47. `import.meta.filename` and `import.meta.dirname`

Modern Node provides:

```js
console.log(import.meta.filename);
console.log(import.meta.dirname);
```

Conceptually:

```text
CommonJS                  ESM

__filename       ↔       import.meta.filename
__dirname        ↔       import.meta.dirname
```

These are available for local `file:` modules.

A `data:` module does not have a normal filesystem filename/dirname.

---

# 48. `import.meta.resolve()`

You can resolve a module specifier without loading it:

```js
const resolved = import.meta.resolve("./config.json");

console.log(resolved);
```

Possible result:

```text
file:///project/src/config.json
```

Important:

```text
resolve
  ↓
returns URL

does NOT:
  ↓
load
  ↓
parse
  ↓
evaluate
```

This makes it useful for diagnostics and resolution logic.

---

# 49. `require.resolve()` vs `import.meta.resolve()`

CommonJS:

```js
require.resolve("./config.js");
```

ESM:

```js
import.meta.resolve("./config.js");
```

Both answer the general question:

> "Where would this module resolve to?"

But the underlying systems differ:

```text
CJS → filesystem path-oriented resolution
ESM → URL-oriented resolution
```

---

# 50. ESM Is Always Strict Mode

ESM automatically runs in strict mode.

You do not need:

```js
"use strict";
```

This means:

```js
undeclaredVariable = 10;
```

throws instead of silently creating a global.

---

# 51. Top-Level `this`

This is a common migration trap.

In CommonJS, top-level `this` is affected by the CommonJS wrapper.

In ESM:

```js
console.log(this);
```

prints:

```text
undefined
```

Do not port code that relies on CommonJS top-level `this` without
checking it.

---

# 52. ESM Does Not Have CommonJS Wrapper Variables

In ESM these are not automatically available:

```js
require;
module;
exports;
__filename;
__dirname;
arguments;
```

For example:

```js
console.log(require);
```

does not work simply because the file is ESM.

Instead use:

```js
import ...
```

and:

```js
import.meta;
```

---

# 53. ESM Module Scope

Top-level variables are local to the module:

```js
const secret = "abc";
```

Another module cannot access `secret` unless it is exported.

```js
export const secret = "abc";
```

Then:

```js
import { secret } from "./config.js";
```

This is similar to the module encapsulation idea in CommonJS, but ESM's
scope and bindings are implemented as language-level module environments
rather than a CommonJS wrapper function.

---

# 54. JSON Imports in ESM

Modern Node requires an import attribute for JSON modules:

```js
import config from "./config.json" with { type: "json" };
```

The imported JSON value is provided as the **default export**.

It does not become:

```js
import { port } from "./config.json";
```

Instead:

```js
import config from "./config.json" with { type: "json" };

console.log(config.port);
```

---

# 55. CommonJS JSON vs ESM JSON

CommonJS:

```js
const config = require("./config.json");
```

ESM:

```js
import config from "./config.json" with { type: "json" };
```

For straightforward configuration, another explicit option is:

```js
import { readFile } from "node:fs/promises";

const text = await readFile("./config.json", "utf8");
const config = JSON.parse(text);
```

This gives you explicit file-reading behavior rather than module-loading
behavior.

---

# 56. Using `createRequire()` in ESM

Sometimes an ESM file needs CommonJS-style `require()` behavior.

Node provides `createRequire()`:

```js
import { createRequire } from "node:module";

const require = createRequire(import.meta.url);

const legacyConfig = require("./legacy-config.json");
```

This is useful during migrations and when interacting with code that
expects CommonJS loading semantics.

Do not use it everywhere just to avoid learning ESM.

---

# 57. Top-Level `await`

One of ESM's important capabilities is top-level `await`.

Example:

```js
const response = await fetch("https://example.com/data");

export const data = await response.json();
```

No surrounding async function is required.

This works because ESM evaluation can be asynchronous.

---

# 58. Why Top-Level `await` Affects Dependencies

Suppose:

```js
// db.js
await connectToDatabase();

export const db = getDatabase();
```

Then:

```js
// server.js
import { db } from "./db.js";

startServer(db);
```

`server.js` cannot safely proceed until the dependency's top-level
evaluation has completed.

Conceptually:

```text
db.js
  ↓
top-level await
  ↓
wait
  ↓
db initialized
  ↓
server.js can continue
```

This is why top-level `await` can delay modules that depend on the
waiting module.

---

# 59. Top-Level `await`: Backend Guidance

Use it deliberately.

Good use:

```js
// db.js
await initializeDatabase();

export const db = getDatabase();
```

Potential problem:

```js
// config.js
await someSlowExternalService();
```

Now a large portion of your application's dependency graph may wait
during startup.

The important question is not:

> "Can I use top-level await?"

It is:

> "Should module evaluation depend on this asynchronous operation?"

---

# 60. ESM Module Cache

ESM modules are cached by their resolved URL identity.

If:

```js
await import("./foo.js");
await import("./foo.js");
```

resolves to the same URL, the module is not evaluated from scratch
twice.

Conceptually:

```text
import ./foo.js
      ↓
resolve URL
      ↓
cache miss
      ↓
load/link/evaluate
      ↓
cache

second import
      ↓
same URL
      ↓
cache hit
      ↓
reuse module
```

---

# 61. Cache Identity Can Create Duplicate Instances

These are different:

```js
await import("./foo.js");
await import("./foo.js?x=1");
```

because:

```text
URL A ≠ URL B
```

If `foo.js` contains mutable state, you can accidentally get two
independent instances.

This is especially relevant when debugging:

- loaders
- test runners
- cache-busting mechanisms
- development tooling

---

# 62. Module Namespace Object

This:

```js
import * as mod from "./module.js";
```

gives you a **module namespace object**.

Example:

```js
console.log(Object.keys(mod));
```

It contains the module's exported names.

The namespace object is:

- sealed
- non-extensible
- special
- connected to live export bindings

You cannot add arbitrary exports:

```js
mod.newValue = 123; // rejected
```

---

# 63. Namespace Object and Live Values

Given:

```js
// counter.js
export let count = 0;

export function increment() {
  count++;
}
```

Then:

```js
import * as counter from "./counter.js";

console.log(counter.count); // 0

counter.increment();

console.log(counter.count); // 1
```

The namespace property reflects the current exported binding.

---

# 64. Default Export in Namespace Objects

If:

```js
export default function start() {}
```

then:

```js
import * as module from "./server.js";
```

contains:

```js
module.default;
```

So:

```js
module.default();
```

can access the default export.

Usually, however, direct default import syntax is clearer:

```js
import start from "./server.js";
```

---

# 65. Module Namespace Object Details You Should Know

For advanced debugging:

```js
Object.isSealed(ns); // true
Object.isExtensible(ns); // false
Object.getPrototypeOf(ns); // null
```

Its `Symbol.toStringTag` identifies it as:

```text
Module
```

You do **not** need to memorize property descriptor quirks for normal
backend work.

The practical rule is enough:

> A module namespace object is a read-oriented representation of a
> module's exports, not a normal mutable object.

---

# 66. ESM Loading Internals --- What Actually Matters

Node's ESM implementation contains internal components such as:

```text
ModuleLoader
ModuleJob
ModuleWrap
```

A useful conceptual pipeline is:

```text
import "./bar.js"
      ↓
ModuleLoader
      ↓
resolve URL
      ↓
load source / determine format
      ↓
ModuleJob
      ↓
ModuleWrap / V8 Module
      ↓
link
      ↓
evaluate
```

### Important warning

These are Node internals.

Do not write production application logic that depends on private
internal implementation details.

The value of knowing them is understanding **why** ESM behaves the way
it does.

---

# 67. `ModuleLoader`

Conceptually, the loader coordinates:

- resolution
- loading
- module format detection
- module jobs
- caching
- dependency traversal

For:

```js
import { foo } from "./bar.js";
```

the loader needs to determine what:

```text
./bar.js
```

means and obtain the module represented by that resolved URL.

---

# 68. `ModuleJob`

A `ModuleJob` conceptually tracks a module through:

```text
parse
→ dependency resolution
→ linking
→ evaluation
```

A module's dependencies create a graph of related jobs.

Top-level `await` makes evaluation asynchronous from the job's
perspective.

---

# 69. `ModuleWrap`

`ModuleWrap` is the bridge between Node's loader machinery and V8's
module implementation.

You generally do not need to interact with it directly.

Understand the concept:

```text
Node loader
     ↕
ModuleWrap
     ↕
V8 module system
```

This is where Node's host-specific resolution/loading behavior meets
JavaScript's language-level module machinery.

---

# 70. Cycle Detection Internally

For:

```text
A → B
↑   ↓
└───┘
```

the engine does not simply recursively execute forever.

During instantiation, it can recognize that modules are already being
processed and construct the necessary binding structure.

The real danger is **evaluation order and uninitialized bindings**, not
merely the existence of a cycle.

---

# 71. Custom ESM Loader Hooks

Node supports customization of module loading through loader hooks.

These can be used for specialized scenarios such as:

- custom resolution
- source transformation
- specialized loaders
- tooling

Modern Node has APIs around:

```js
module.register();
module.registerHooks();
```

and CLI mechanisms such as loader-related flags.

### Backend guidance

This is advanced infrastructure territory.

Do not use custom loaders merely to avoid writing normal import paths.

Keep custom loader logic:

- small
- deterministic
- well documented
- carefully tested

---

# 72. Async vs Sync Loader Hooks

An important advanced distinction:

- async hooks registered through `module.register()` operate under a
  different execution model
- synchronous hooks through `module.registerHooks()` run in the
  application thread

This affects assumptions about:

- shared state
- execution context
- synchronous behavior
- configuration
- interaction with application objects

You generally only need this when building tooling or custom
module-loading infrastructure.

---

# 73. Common ESM Errors

## `ERR_MODULE_NOT_FOUND`

Often means:

- wrong path
- missing extension
- package not installed
- incorrect package specifier
- wrong package export target

Example:

```js
import "./utils";
```

when the actual file is:

```text
utils.js
```

Use:

```js
import "./utils.js";
```

---

## `ERR_UNSUPPORTED_DIR_IMPORT`

Often caused by:

```js
import "./utils/";
```

when you expected Node to find:

```text
utils/index.js
```

Use the actual file path.

---

## `ERR_PACKAGE_PATH_NOT_EXPORTED`

You attempted to access a package path that the package's `"exports"`
field does not expose.

Example:

```js
import internal from "some-package/internal/private.js";
```

while the package only exports:

```json
{
  "exports": {
    ".": "./index.js"
  }
}
```

The package is intentionally preventing that deep import.

---

## Missing Named Export / Link-Time `SyntaxError`

If:

```js
import { doesNotExist } from "./module.js";
```

but the target does not export that name, ESM can reject the module
during linking before normal module evaluation.

This is one of the major benefits of static ESM structure.

# 76. A Complete Example

Consider:

```text
project/
├── package.json
├── server.js
├── config.js
└── db.js
```

`package.json`:

```json
{
  "name": "backend-app",
  "type": "module"
}
```

`config.js`:

```js
export const PORT = Number(process.env.PORT) || 3000;

export let requestCount = 0;

export function trackRequest() {
  requestCount++;
}
```

`db.js`:

```js
export async function connectDB() {
  console.log("Connecting to DB...");
}
```

`server.js`:

```js
import { PORT, requestCount, trackRequest } from "./config.js";
import { connectDB } from "./db.js";

await connectDB();

console.log(`Server starting on ${PORT}`);

trackRequest();

console.log(`Requests: ${requestCount}`);
```

# 77. What Happens in That Example?

## Step 1 --- Format detection

Because:

```json
"type": "module"
```

all `.js` files in this package scope are ESM.

---

## Step 2 --- Parse

Node sees:

```text
server.js
 ├── config.js
 └── db.js
```

---

## Step 3 --- Resolve

Node resolves:

```text
./config.js
./db.js
```

to URLs.

---

## Step 4 --- Instantiate

Bindings are created.

For example:

```text
config.js
 ├── PORT
 ├── requestCount
 └── trackRequest

server.js
 ├── PORT        → config.PORT
 ├── requestCount → config.requestCount
 └── trackRequest → config.trackRequest
```

---

## Step 5 --- Evaluate dependencies

`config.js` initializes:

```text
PORT
requestCount = 0
trackRequest
```

`db.js` initializes its exports.

---

## Step 6 --- Evaluate `server.js`

It executes:

```js
await connectDB();
```

Then:

```js
trackRequest();
```

which updates the exported `requestCount` binding.

The importer sees:

```text
requestCount = 1
```

because the import is live.

# 79. Practical Backend Rules

## Rule 1 --- Declare your package type

Prefer:

```json
{
  "type": "module"
}
```

or:

```json
{
  "type": "commonjs"
}
```

Do not leave module format ambiguous in serious projects.

---

## Rule 2 --- Use explicit relative extensions in ESM

Write:

```js
import { db } from "./db.js";
```

not:

```js
import { db } from "./db";
```

---

## Rule 3 --- Use `node:` for built-ins

Prefer:

```js
import fs from "node:fs";
import path from "node:path";
import { readFile } from "node:fs/promises";
```

---

## Rule 4 --- Use static imports when dependencies are known

Prefer:

```js
import { UserService } from "./user.service.js";
```

Use dynamic import when the dependency genuinely depends on runtime
conditions.

---

## Rule 5 --- Remember imports are live bindings

Do not think:

```text
import = copied variable
```

Think:

```text
import = binding connected to exporter
```

---

## Rule 6 --- Treat circular dependencies as a design smell

They can work, but they increase reasoning complexity.

If a cycle causes initialization problems, redesign the dependency
graph.

---

## Rule 7 --- Be careful with top-level `await`

It can make startup depend on asynchronous module evaluation.

---

## Rule 8 --- Understand package `"exports"`

If a package blocks a deep import, do not immediately bypass the
boundary.

The package may intentionally expose only its supported public API.

# 80. Common Migration Mistakes

### Mistake 1

```js
import "./utils";
```

when using ESM.

Fix:

```js
import "./utils.js";
```

---

### Mistake 2

```js
const express = require("express");
```

inside normal ESM.

Fix:

```js
import express from "express";
```

or deliberately create a `require` with `createRequire()` when
necessary.

---

### Mistake 3

```js
console.log(__dirname);
```

inside ESM.

Fix:

```js
console.log(import.meta.dirname);
```

or use URL conversion when appropriate.

---

### Mistake 4

Assuming:

```js
import { count } from "./counter.js";
```

creates an ordinary copied variable.

It does not. It creates a live import binding.

---

### Mistake 5

Assuming circular imports automatically fail.

The cycle itself is not necessarily the failure.

The dangerous part is often:

```text
cycle
  ↓
evaluation order
  ↓
read before initialization
  ↓
ReferenceError
```

---

### Mistake 6

Assuming `export *` includes the default export.

It does not.

---

### Mistake 7

Assuming two different ESM URLs pointing to the same file are
necessarily the same module instance.

They may not be:

```js
import "./foo.js";
import "./foo.js?v=1";
```

# 81. Interview-Level Questions

### Q1. What is the biggest conceptual difference between CommonJS and ESM?

**Answer:** ESM has a statically analyzable module structure. Node can
resolve and link the dependency graph before evaluating module bodies.

---

### Q2. Why are ESM imports called live bindings?

Because the importer is connected to the exporter's binding rather than
receiving an independent snapshot.

---

### Q3. Why does this fail?

```js
import "./utils";
```

Because relative ESM imports normally require explicit file extensions.

---

### Q4. What is the difference between `import` and `import()`?

```js
import x from "./x.js";
```

is a static declaration known during module linking.

```js
const x = await import("./x.js");
```

is dynamic loading performed asynchronously at runtime.

---

### Q5. Can CommonJS use `import()`?

Yes.

Dynamic `import()` can be used as a bridge from CommonJS to ESM.

---

### Q6. Why can ESM circular dependencies work?

Because the loader can instantiate the module graph and create bindings
before evaluation.

---

### Q7. Why can circular dependencies still throw `ReferenceError`?

Because the binding may exist but remain uninitialized when another
module reads it.

---

### Q8. What replaces `__dirname` in ESM?

Modern Node provides:

```js
import.meta.dirname;
```

For broader/manual URL handling:

```js
fileURLToPath(import.meta.url);
```

combined with path utilities.

---

### Q9. What does `import.meta.resolve()` do?

It resolves a specifier relative to the current module and returns its
resolved URL without loading/evaluating the target.

---

### Q10. What is `ERR_PACKAGE_PATH_NOT_EXPORTED`?

It generally means the package's `"exports"` field does not expose the
path you tried to import.

---

### Q11. What is the difference between a named export and default export?

Named:

```js
export { foo };
```

must be imported by its exported name:

```js
import { foo } from "./x.js";
```

Default:

```js
export default foo;
```

is imported with any local name:

```js
import anything from "./x.js";
```

---

### Q12. Does `export *` include default?

No.

---

# 85. The One Mental Model to Keep

Do not memorize dozens of isolated ESM rules.

Remember this:

> **ESM is a statically structured module system where Node can discover
> the dependency graph, resolve modules, create live import/export
> bindings, and link the graph before evaluating module bodies.**

From that, most behavior follows:

```text
Static imports
      ↓
Graph known early
      ↓
Bindings can be linked early
      ↓
Live imports
      ↓
Cycles can be represented
      ↓
But uninitialized bindings can still fail
```

And:

```text
ESM uses URLs
      ↓
Explicit relative paths
      ↓
Explicit extensions
      ↓
URL-based module identity/cache
      ↓
import.meta
```

And:

```text
ESM is not CommonJS with different syntax
      ↓
No automatic require/module/exports
      ↓
Different loading model
      ↓
Different resolution behavior
      ↓
Different interop rules
```

For backend development, the most important skill is not memorizing
Node's internal loader classes. It is being able to look at an ESM
import and predict:

1.  **What format is this file?**
2.  **What does this specifier resolve to?**
3.  **What export is being requested?**
4.  **When will the dependency evaluate?**
5.  **Is the imported binding live?**
6.  **Could a cycle or top-level `await` affect evaluation?**
7.  **What happens to cache identity?**
8.  **Is CommonJS/ESM interoperability involved?**

If you can answer those reliably, you understand ESM at the level that
matters for serious Node.js backend work.
