Node.js CommonJS Module System — Complete Notes

Purpose: A practical, detailed reference for understanding how Node.js CommonJS modules work internally.

Primary source: The supplied Node.js modules document covering require(), Module._load, CommonJS caching, resolution, compilation, extension handlers, module.exports, circular dependencies, and require.resolve().

Scope: This document focuses on the concepts covered by that source. Internal Node APIs are implementation details and can change between Node versions.

1. The Big Picture

When we write:

const math = require("./math");

it is tempting to think:

"Node finds math.js and gives me its functions."

That is directionally correct, but internally a lot more happens.

A useful simplified model is:

require("./math")
       |
       v
Resolve the request
       |
       v
Find the exact target filename
       |
       v
Check CommonJS module cache
       |
       +------ already loaded ------> return cached module.exports
       |
       v
Create a Module object
       |
       v
Put it in the cache BEFORE execution
       |
       v
Load the file
       |
       v
Choose the file-type handler
       |
       v
Read / parse / compile
       |
       v
Execute module code
       |
       v
module.exports
       |
       v
require() returns that value

This single diagram explains most of the CommonJS behavior discussed in this chapter.

2. What Is a CommonJS Module?

A CommonJS module is a JavaScript file loaded using Node's CommonJS loader.

Example:

// math.js

function add(a, b) {
  return a + b;
}

module.exports = add;

Another file can load it:

// app.js

const add = require("./math");

console.log(add(10, 20));

Output:

30

The important relationship is:

math.js
   |
   | module.exports = add
   v
require("./math")
   |
   v
add

The value returned by require() is the current value of module.exports.

3. What require() Actually Does

require() is the synchronous entry point into Node's CommonJS loader.

When called, Node may need to:

  1. Resolve the module request.
  2. Check whether the module is already cached.
  3. Create a Module object if necessary.
  4. Put the module into the cache.
  5. Read the file.
  6. Choose an appropriate extension handler.
  7. Compile JavaScript when necessary.
  8. Execute top-level module code.
  9. Return module.exports.

All of this synchronous work happens before require() returns.

For example:

const helper = require("./helper");

console.log("after require");

If helper.js contains:

console.log("helper executing");

module.exports = {
  value: 10,
};

the output is:

helper executing
after require

Not:

after require
helper executing

because CommonJS require() is synchronous.

4. The Internal Loading Path

The source describes the loading path approximately as:

require(id)
  -> Module.prototype.require(id)
  -> wrapModuleLoad(id, parent, false)
  -> Module._load(id, parent, false)
  -> Module._resolveFilename(id, parent)
  -> check Module._cache
  -> module.load(filename)
  -> return module.exports

These are mostly private Node internals.

Do not treat them as application APIs.

The useful conceptual mapping is:

Internal operationSimple meaning
Module.prototype.require()Entry into the CommonJS loader
Module._load()Coordinates loading
Module._resolveFilename()Determines what the request refers to
Module._cacheStores loaded CommonJS modules
module.load()Loads the resolved file
Module._extensionsSelects how a file type is handled
module._compile()Turns JavaScript source into executable CommonJS code

5. The Local require() Function

Inside a CommonJS file, require is available:

const fs = require("fs");
const helper = require("./helper");

This require is local to the module.

Node supplies CommonJS-specific values through a wrapper function.

Conceptually, Node executes your file like:

(function (exports, require, module, __filename, __dirname) {
  // your module code
});

Therefore these names are available:

exports;
require;
module;
__filename;
__dirname;

They are supplied by the CommonJS module system rather than being ordinary global variables.

6. Why Is require Different in Different Files?

Consider:

project/
├── app.js
├── utils.js
└── services/
    └── user.js

If app.js does:

require("./utils");

the ./ is interpreted relative to app.js.

If services/user.js does:

require("./utils");

that request is relative to services/user.js.

So the same string:

require("./utils");

can resolve to different files depending on which module performs the request.

The parent module matters during resolution.

7. Module Resolution

Before Node can load a module, it needs to answer:

What exact module does this request mean from this location?

For example:

require("./utils");

could potentially resolve to:

utils.js
utils.json
utils.node
utils/index.js
utils/index.json
utils/index.node

The actual resolution rules are more extensive, but the central idea is:

module request
     |
     v
resolution
     |
     v
specific target

For a file-backed CommonJS module, that resolved filename becomes the normal cache key.

8. Relative Requests

Relative requests begin with:

./
../

Examples:

require("./utils");
require("../utils");
require("./config.json");

They are resolved relative to the parent module's directory.

Example:

/home/user/project/src/app.js
/home/user/project/src/utils.js

From app.js:

require("./utils");

can resolve to:

/home/user/project/src/utils.js

9. Bare Package Requests

A package request looks like:

require("express");
require("mongoose");
require("some-package");

These are not relative filesystem paths.

Node constructs a search path containing node_modules directories.

For a module such as:

/home/user/project/src/utils.js

Node may search:

/home/user/project/src/node_modules
/home/user/project/node_modules
/home/user/node_modules
/home/node_modules
/node_modules

The general idea is:

start near the requiring file
        |
        v
look for node_modules
        |
        v
move upward
        |
        v
look again
        |
        v
continue toward filesystem root

10. Built-in Node Modules

Node has built-in modules such as:

require("fs");
require("path");
require("http");
require("net");

These are not ordinary packages that Node has to find in your project's node_modules.

Node checks for built-in modules during resolution.

Example:

const fs = require("fs");

Node recognizes "fs" as a built-in module.

You can also use:

const fs = require("node:fs");

The node: prefix explicitly indicates the built-in module.

Conceptually:

require("fs")
     |
     v
Node recognizes built-in
     |
     v
load built-in

require("node:fs")
     |
     v
explicit built-in request

The source notes that the node: form avoids ambiguity with userland cache tricks and filesystem fallback.

11. Module._resolveFilename

Module._resolveFilename is an internal function responsible for resolving a request to its target.

For example:

require("./utils");

might become:

/home/user/project/utils.js

The exact internal implementation is version-dependent.

For learning purposes, think:

"./utils"
    |
    v
Module._resolveFilename(...)
    |
    v
"/home/user/project/utils.js"

Once this happens, Node knows which module it is dealing with.

12. First Match Wins

During resolution, Node considers candidate paths.

The first valid match wins.

For example, conceptually:

try ./utils
try ./utils.js
try ./utils.json
try ./utils.node
try directory fallbacks

Once an appropriate target is found, resolution stops.

This is why creating multiple possible candidates can create surprising resolution behavior.

13. Directory Resolution

You can require a directory:

require("./myLib");

Suppose:

myLib/
├── package.json
└── lib/
    └── index.js

If package.json contains:

{
  "main": "lib/index.js"
}

the package entry point can be selected using the main field.

Legacy directory fallback can then involve:

index.js
index.json
index.node

Conceptually:

require("./myLib")
        |
        v
directory?
        |
        v
check package.json
        |
        v
usable "main"?
      /     \
    yes      no
     |        |
     v        v
 main      index.js
             |
             v
          index.json
             |
             v
          index.node

14. node_modules Search Paths

Internally Node can construct the search paths for package resolution.

For example:

/home/user/project/src/utils.js

can result in paths like:

/home/user/project/src/node_modules
/home/user/project/node_modules
/home/user/node_modules
/home/node_modules
/node_modules

These paths are associated with the module and can be seen through module.paths.

15. Module._pathCache

Node also maintains an internal path-resolution cache.

Its purpose is different from the main module cache.

Conceptually:

request + lookup paths
        |
        v
path cache
        |
        v
resolved filename

This can avoid repeated filesystem checks during resolution.

Do not confuse:

Module._pathCache

with:

require.cache

They solve different problems.

require.cache​

Caches loaded module objects.

Module._pathCache​

Caches resolution results.

16. MODULE_NOT_FOUND

If Node cannot resolve a requested module, it throws an error whose code is:

MODULE_NOT_FOUND;

Example:

require("./does-not-exist");

This is an important debugging distinction:

resolution failed
      |
      v
MODULE_NOT_FOUND

The error also includes information about the require chain that led to the failure.

17. The CommonJS Module Object

When Node loads a file-backed CommonJS module, it creates a Module instance.

Conceptually:

const module = new Module(filename, parent);

A simplified module object contains fields such as:

{
  (id, filename, exports, loaded, parent, children);
}

The important fields are:

PropertyMeaning
idModule identifier
filenameResolved filename
exportsValue exposed to consumers
loadedWhether module evaluation has finished
parentParent module relationship
childrenModules loaded by this module

18. module.exports

This is the most important property in CommonJS.

Consider:

// math.js

module.exports = 100;

Then:

const value = require("./math");

console.log(value);

Output:

100

Because:

module.exports
      |
      v
100
      |
      v
require("./math") returns 100

If you export an object:

module.exports = {
  add(a, b) {
    return a + b;
  },
};

then require() returns that object.

If you export a function:

module.exports = function greet(name) {
  return `Hello ${name}`;
};

then require() returns the function itself.

19. exports and module.exports

At the beginning of a CommonJS module:

exports === module.exports;

is true.

Conceptually:

exports ───────────────┐
                       |
                       v
                 module.exports
                       |
                       v
                      {}

Both names initially refer to the same object.

This explains why the following works:

exports.greet = function () {
  return "hello";
};

Because you're modifying the same object:

exports
   |
   v
{ greet: function }

module.exports
   |
   └────> same object

20. The exports Aliasing Trap

This does not replace the exported value:

exports = {
  greet() {
    return "hello";
  },
};

Why?

Because assignment changes the local exports variable.

It does not replace module.exports.

Before:

exports ───────┐
              v
        module.exports
              |
              v
             {}

After:

exports
   |
   v
{ greet: ... }


module.exports
   |
   v
{}

And require() returns:

module.exports;

not the local exports variable.

21. Correct Rule for exports

Use:

exports.foo = foo;
exports.bar = bar;

when you want to add named properties to the existing export object.

Use:

module.exports = something;

when you want the module to export a complete value.

Do not normally write:

exports = something;

when your intention is to replace what consumers receive.

22. Named Exports with CommonJS

Example:

// math.js

exports.add = function (a, b) {
  return a + b;
};

exports.subtract = function (a, b) {
  return a - b;
};

Consumer:

const math = require("./math");

console.log(math.add(10, 5));
console.log(math.subtract(10, 5));

The consumer gets:

{
  add: ...,
  subtract: ...
}

23. Exporting One Complete Value

Example:

// greet.js

module.exports = function greet(name) {
  return `Hello ${name}`;
};

Consumer:

const greet = require("./greet");

console.log(greet("Prashant"));

The variable itself is the exported function.

24. Exporting a Class

You can export a class directly:

// database.js

module.exports = class Database {
  constructor(url) {
    this.url = url;
  }

  query(sql) {
    // ...
  }
};

Consumer:

const Database = require("./database");

const db = new Database("mongodb://...");

The exported value is the class.

25. Functions Can Have Properties

In JavaScript, functions are objects.

Therefore:

function greet(name) {
  return `hello ${name}`;
}

greet.version = "1.0.0";

module.exports = greet;

Consumer:

const greet = require("./greet");

console.log(greet("world"));
console.log(greet.version);

The same exported function can be:

called
  +
have properties

This is a useful CommonJS pattern.

26. Module Cache

CommonJS modules are normally loaded once per resolved filename within a process.

Example:

const a = require("./state");
const b = require("./state");

If both requests resolve to the same filename:

/project/state.js

Node normally loads the file only once.

The second request gets the cached module.

27. Same Resolved Filename = Same Cached Module

The important thing is not the literal request string.

The important thing is the resolved filename.

Conceptually:

require("./state")
        |
        v
/project/state.js
        |
        v
cache key

So the rule is:

Same resolved filename → same cached CommonJS module.

Different paths can refer to different modules.

Symlinks, package boundaries, and options such as --preserve-symlinks can affect the resolved path.

28. Shared Export References

Suppose:

// state.js

module.exports = {
  count: 0,
};

Then:

const a = require("./state");
const b = require("./state");

a.count++;

console.log(a === b);
console.log(b.count);

Output:

true
1

Why?

Because both variables point to the same exported object:

       cached Module
             |
             v
      module.exports
             |
       +-----+-----+
       |           |
       v           v
       a           b

There is no cloning.

29. require.cache

You can inspect the CommonJS cache:

console.log(Object.keys(require.cache));

You may see:

[
  "/home/user/project/app.js",
  "/home/user/project/math.js",
  "/home/user/project/utils.js"
]

The values in require.cache are Module instances.

Conceptually:

require.cache = {
  "/project/math.js": ModuleInstance,
};

30. Deleting a Module from the Cache

You can remove a module:

delete require.cache[require.resolve("./config")];

Then:

const config = require("./config");

can load and evaluate the file again.

Example:

const first = require("./config");

delete require.cache[require.resolve("./config")];

const second = require("./config");

The second load can produce a new module/export object.

31. Cache Deletion Does Not Update Existing References

This is critical.

Suppose:

const oldConfig = require("./config");

delete require.cache[require.resolve("./config")];

const newConfig = require("./config");

Now:

oldConfig
    |
    v
old export object


newConfig
    |
    v
new export object

Deleting the cache does not reach into every variable in the application and replace its reference.

Therefore a process can temporarily have two versions of the same module's exports alive.

32. Why Cache Deletion Is Fragile for Hot Reloading

Deleting the cache does not undo side effects.

Suppose the first evaluation does:

setInterval(() => {
  // ...
}, 1000);

or:

eventEmitter.on("event", handler);

or opens a connection:

connectToDatabase();

Reloading the module by deleting require.cache does not automatically undo those things.

You can end up with:

old module
  |
  +-- old timer
  +-- old event listener
  +-- old connection

new module
  |
  +-- new timer
  +-- new event listener
  +-- new connection

Therefore cache deletion is useful for experiments and some development scenarios, but it is not automatically a sound production hot-reload strategy.

33. Why require.cache Uses a Prototype-less Object

The CommonJS cache is represented internally using an object without the normal Object.prototype.

Conceptually:

Object.create(null);

A normal object inherits properties such as:

toString
constructor
hasOwnProperty

A prototype-less object avoids inherited-key collisions.

This is an implementation detail rather than something application code normally needs to reproduce.

34. module.loaded

A module begins loading with:

loaded = false;

After successful evaluation:

loaded = true;

Conceptually:

new Module
    |
    v
loaded = false
    |
    v
load + execute
    |
    v
loaded = true

This distinction matters especially during circular dependencies.

A module can already be in the cache while:

module.loaded === false;

35. Why Node Caches Before Executing

This is one of the most important internal details.

Suppose:

A requires B
B requires A

When A starts:

create A
   |
   v
put A into cache
   |
   v
execute A

Then A requires B:

A
 |
 v
B starts

B requires A:

B
 |
 v
require A

Node checks the cache:

A is already there

Therefore Node can return A's current export state instead of starting A from scratch.

This prevents the loading process from endlessly recursing:

A -> B -> A -> B -> A -> ...

36. Circular Dependencies

A circular dependency exists when modules depend on each other directly or indirectly.

Simple direct cycle:

A -> B
^    |
|    v
+----+

or:

A requires B
B requires A

CommonJS allows this situation, but modules may receive partially initialized exports.

37. Circular Dependency Example

a.js​

exports.fromA = "hello from A";

const b = require("./b");

exports.afterB = "set after B loaded";

b.js​

const a = require("./a");

console.log(a.fromA);
console.log(a.afterB);

Output:

hello from A
undefined

Why?

A executes:

exports.fromA = "hello from A";

So that property exists.

Then A pauses here:

const b = require("./b");

B starts.

B executes:

const a = require("./a");

But A is already in the cache and has not finished.

B therefore gets A's exports as they exist at that moment.

At that moment:

{
  fromA: "hello from A";
}

There is no:

afterB;

yet.

38. Timeline of the Circular Example

This is the easiest way to understand it:

A starts
 |
 | exports.fromA = "hello from A"
 |
 v
A requires B
 |
 v
B starts
 |
 | B requires A
 |
 v
A found in cache
 |
 | A currently has:
 | { fromA: "hello from A" }
 |
 v
B receives that object
 |
 | a.fromA     -> "hello from A"
 | a.afterB    -> undefined
 |
 v
B finishes
 |
 v
A resumes
 |
 | exports.afterB = "set after B loaded"
 |
 v
A finishes

The important idea:

The read happened early, but the reference can remain live.

39. Live Reference After a Circular Dependency

Suppose B gets A's exports object:

const a = require("./a");

At that moment:

a = {
  fromA: "hello from A",
};

Later A does:

exports.afterB = "done";

Because B still references the same object, B can observe the new property if it reads it later.

Conceptually:

B's a
  |
  v
same object
  |
  +-- fromA
  +-- afterB   <-- added later

So there are two different concepts:

early read

and:

same live object reference

40. The More Dangerous Circular Dependency Case

The problem becomes worse when a module replaces module.exports.

a.js​

const b = require("./b");

module.exports = {
  ready: true,
};

Suppose B requires A before A reaches the assignment:

const a = require("./a");

B may receive the original exports object:

{
}

Then A later does:

module.exports = {
  ready: true,
};

A has now replaced the reference.

Conceptually:

B
 |
 v
old exports object
{}


A
 |
 v
new module.exports object
{ ready: true }

B still holds the old object.

41. Why Mutating exports Can Be Safer in a Cycle

Instead of:

module.exports = {
  ready: true,
};

you can keep the same object:

exports.ready = false;

const b = require("./b");

exports.ready = true;

The object remains the same.

Only its properties change.

Conceptually:

same object
   |
   +-- ready: false
   |
   +-- later becomes true

This can avoid a particular class of circular-dependency problems.

However:

The better architectural solution is usually to remove the cycle.

42. Better Solutions to Circular Dependencies

If:

A <-> B

exists, consider:

Option 1: Extract shared functionality​

      common
      /    \
     A      B

Option 2: Dependency injection​

Instead of A directly requiring B, pass B into A.

Option 3: Separate initialization from usage​

Make module initialization independent from operations that require the other module.

Option 4: Lazy require()​

Example:

exports.getB = function () {
  const b = require("./b");
  return b.value;
};

This delays the dependency until the function is actually called.

If the function runs after initialization:

A loaded
B loaded
getB()
  |
  v
require("./b")
  |
  v
cache hit

This can work, but it is a workaround rather than proof that the dependency graph is healthy.

43. Lazy require() and Caching

A lazy require:

function getB() {
  return require("./b");
}

does not necessarily mean B is loaded every time.

After the first successful load:

first getB()
    |
    v
require("./b")
    |
    v
load B
    |
    v
cache B


second getB()
    |
    v
require("./b")
    |
    v
cache hit

The lookup still occurs, but the expensive loading work normally does not repeat.

44. module.children

A module has a children collection describing modules loaded through it.

Conceptually:

app.js
  |
  +-- math.js
  |
  +-- utils.js

app.js can have child module references corresponding to modules it loaded.

This can help investigate module relationships.

However:

module.children is not a complete static dependency graph.

It describes runtime loading relationships, not necessarily every possible dependency in the source code.

45. require.resolve()

require.resolve() uses the module resolution process but stops after finding the target.

Example:

console.log(require.resolve("./utils"));

Possible output:

/home/user/project/utils.js

Compare:

require("./utils");

with:

require.resolve("./utils");

require()​

resolve
  |
  v
load
  |
  v
compile / parse
  |
  v
execute
  |
  v
return exports

require.resolve()​

resolve
  |
  v
return filename

It does not load or execute the module.

46. require.resolve() Is Not an Existence Boolean

This is incorrect:

if (require.resolve("some-package")) {
  // ...
}

because require.resolve() either returns a resolved target or throws.

For optional dependencies, use try/catch:

let optional;

try {
  optional = require.resolve("some-optional-package");
} catch (err) {
  if (err.code !== "MODULE_NOT_FOUND") {
    throw err;
  }
}

The important behavior is:

found
  -> returns resolved target

not found
  -> throws MODULE_NOT_FOUND

47. require.resolve.paths()

require.resolve.paths(request) answers:

Which directories would Node search for this request?

Example:

console.log(require.resolve.paths("express"));

Conceptually:

[
  "/home/user/project/node_modules",
  "/home/user/node_modules",
  "/home/node_modules",
  "/node_modules"
]

For a relative request:

require.resolve.paths("./utils");

the result is based on the calling module's directory.

For a built-in module:

require.resolve.paths("fs");

the result is:

null;

because built-in modules do not use the normal filesystem package lookup chain.

48. require.resolve() with paths

The source also describes:

require.resolve("some-plugin", {
  paths: ["/custom/lookup/path"],
});

This is useful in tooling and plugin systems.

For package names, the supplied path acts as a starting point for the usual node_modules lookup chain.

The package still has to exist somewhere in that resulting lookup chain.

49. Resolution Cache vs Module Cache

These are easy to confuse.

Resolution cache​

Answers:

"Where is this request located?"

"./math"
   |
   v
"/project/math.js"

Module cache​

Answers:

"Have we already loaded this module?"

"/project/math.js"
   |
   v
Module instance

So:

request
  |
  v
resolution
  |
  v
filename
  |
  v
module cache
  |
  v
Module instance

50. Module.prototype.load()

After resolution and cache handling, the Module object's load() method handles the resolved filename.

Conceptually:

module.load(filename);

It:

  1. Sets the filename.
  2. Establishes module lookup paths.
  3. Determines the appropriate extension handler.
  4. Calls that handler.
  5. Marks the module as loaded.

Simplified:

Module.prototype.load = function (filename) {
  this.filename = filename;

  const extension = findExtension(filename);

  Module._extensions[extension](this, filename);

  this.loaded = true;
};

51. Module._extensions

Node has extension handlers for common file types.

The source describes three default handlers:

ExtensionBehavior
.jsRead, compile, execute as CommonJS
.jsonRead, parse JSON, assign result to module.exports
.nodeLoad a compiled native addon

Think:

filename
   |
   +---- .js   -> JavaScript handler
   |
   +---- .json -> JSON handler
   |

The source mentions BOM handling.

55. .node Native Addons

A .node file is a compiled native Node addon.

56. require.extensions

Historically, Node allowed custom extension handlers:

  // read file
  // assign mod.exports
};

This mechanism can still exist, but it is deprecated.

Reasons include:

  • synchronous behavior
  • global mutation
  • difficult composition
  • poor fit with modern ES Modules
  • tooling complexity

Modern systems generally prefer pre-compilation or dedicated loader mechanisms.

58. The CommonJS Wrapper

A simplified CommonJS wrapper is:

(function (exports, require, module, __filename, __dirname) {
  // module source
});

For example, your source:

const x = 5;

module.exports = x;

is conceptually treated like:

(function (exports, require, module, __filename, __dirname) {
  const x = 5;

  module.exports = x;
});

This explains why CommonJS files have access to:

exports
require
module
__filename
__dirname

59. The Wrapper Is a Mental Model

Modern Node versions do not necessarily literally implement the entire process by constructing a JavaScript wrapper string and running it exactly that way.

The source notes that modern Node versions use internal compilation machinery such as:

compileFunctionForCJSLoader

The wrapper remains a useful conceptual model.

The important idea is:

CommonJS source executes in a function-like module scope with the five CommonJS values supplied by Node.

60. Top-level this

The compiled CommonJS function is conceptually called with:

module.exports;

as its this value.

Therefore, at top level in a CommonJS module, conceptually:

console.log(this === module.exports);

can be:

true

This is an implementation detail rather than something you should build application APIs around.

61. Compilation vs Execution

These are separate stages.

Compilation​

Turns source into executable code.

Execution​

Actually runs:

console.log(...)

and:

functionCall();

and:

module.exports = ...

Conceptually:

  |
  v

  |
  v

  |

  |

Compilation by itself does not mean your module body has executed.

62. Top-Level Code Executes During Loading

Suppose:

// module.js

console.log("module started");

function hello() {
  console.log("hello");
}

module.exports = hello;

When:

require("./module");

happens, the top-level statement:

console.log("module started");

runs.

The function declaration does not execute the function:

hello();

because defining a function is different from calling it.

This distinction is useful when thinking about what require() actually executes.

63. What require() Does Not Wait For

require() is synchronous, but asynchronous work started by the module does not become synchronous.

Example:

// module.js

setTimeout(() => {
  console.log("later");
}, 1000);

module.exports = {
  ready: true,
};

When another file runs:

const mod = require("./module");

console.log("after require");

you can get:

after require
later

The module's synchronous top-level code has completed, but the timer is asynchronous.

So the accurate rule is:

require() waits for synchronous module evaluation, not for future asynchronous work started by that evaluation.

64. Why Lazy require() Can Affect Performance

Consider:

app.get("/report", (req, res) => {
  const report = require("./heavy-report-generator");

  res.json(report.generate());
});

If this is the first time the module is required, that request can pay for:

resolve
read
compile
execute
nested dependencies

All synchronously.

Therefore the first request can experience extra latency.

Later requests normally hit the module cache.

65. Startup require() vs Request-Time require()

A common pattern is:

const express = require("express");
const mongoose = require("mongoose");
const report = require("./report");

at startup.

This means module loading happens before the application begins serving requests.

Lazy loading can still be useful when:

  • a dependency is rarely needed
  • a dependency is optional
  • a dependency is expensive
  • loading it at startup is unnecessary

But the first-hit cost should be intentional.

66. Conditional require()

CommonJS allows runtime branching:

let parser;

if (process.env.USE_FAST_PARSER) {
  parser = require("fast-parser");
} else {
  parser = require("slow-but-safe-parser");
}

Only the selected branch is required.

Therefore, assuming both packages exist:

USE_FAST_PARSER = true

fast-parser -> loaded
slow-but-safe-parser -> not loaded

This is one practical reason CommonJS is convenient for optional or conditional dependencies.

67. CommonJS vs Static ESM import

CommonJS:

if (condition) {
  const x = require("./x");
}

is possible.

A static ES Module import:

import x from "./x.js";

does not work as a normal runtime statement inside an arbitrary if block.

ESM uses module linking and can use dynamic:

import("./x.js");

when runtime loading is required.

This document focuses on CommonJS; ESM has a separate module-loading model.

68. Startup Ordering

Because require() is synchronous:

require("./instrumentation");

startApplication();

the instrumentation module's synchronous top-level setup has run before:

startApplication();

executes.

This can matter for:

  • instrumentation
  • APM setup
  • process-level handlers
  • library patching
  • initialization code

The ordering is a direct consequence of synchronous CommonJS loading.

69. require.main

require.main refers to the Module instance associated with the CommonJS entry file passed to Node.

This enables a common pattern:

if (require.main === module) {
  startServer();
}

Example:

function startServer() {
  console.log("Server started");
}

if (require.main === module) {
  startServer();
}

module.exports = {
  startServer,
};

70. Direct Execution vs Being Required

If you run:

node server.js

then:

require.main === module;

is true for server.js.

So:

startServer();

runs.

But if another file does:

require("./server");

then server.js is not the entry module.

Therefore:

require.main === module;

is false.

This allows one file to behave both as:

  1. an executable entry point
  2. a reusable module

71. require.main and ESM

The source notes that if the process entry point is an ES Module, require.main is undefined.

The require.main === module pattern is therefore specifically a CommonJS entry-point pattern.

72. Loading Failure and Cache Cleanup

Node puts a new module into the cache before evaluation.

That raises a question:

What if evaluation fails?

For example:

// broken.js

console.log("starting");

throw new Error("Something failed");

If loading throws, Node removes the failed module from the cache before propagating the error.

Conceptually:

create module
     |
     v
put in cache
     |
     v
load
     |
     X
throws
     |
     v
remove from cache
     |
     v
throw error to caller

This prevents a permanently broken partially loaded module from remaining as the normal cached result.

73. What Happens on a Second Attempt After Failure?

Because the failed module is removed from the cache:

try {
  require("./broken");
} catch (err) {
  // ...
}

try {
  require("./broken");
} catch (err) {
  // loading is attempted again
}

The second attempt can start the loading process again.

The failed evaluation does not normally become a successful cache entry.

74. require() and Side Effects

Because module top-level code executes during loading, modules can have side effects.

Example:

// setup.js

console.log("Setting up application");

process.on("uncaughtException", handler);

module.exports = {
  initialized: true,
};

Simply doing:

require("./setup");

causes the top-level setup code to execute.

This is one reason the synchronous loading contract matters.

75. Module Cache Is Process-local

The CommonJS cache described here belongs to the running Node.js process.

Think:

Node process A
  |
  +-- require.cache

Node process B
  |
  +-- separate require.cache

A module being cached in one process does not mean it is cached in another process.

This distinction matters when using:

  • multiple Node processes
  • PM2 clusters
  • worker processes
  • separate application instances

Remember:

Compile cache means roughly:

Do not use the phrase "module cache" and "compile cache" as if they were the same thing.

78. Main Module Bookkeeping

When Node loads the file passed directly to the node command, the loader knows it is the main module.

Conceptually:

79. Source Maps and Compilation

At the compilation layer, Node can also work with source maps.

80. Shebang Handling

CLI JavaScript files can start with:

83. The Most Important Ordering Detail

The following order is critical:

  ↓

  ↓

  ↓

Not:

  ↓

The early cache insertion is what makes CommonJS circular dependencies behave as they do.

84. Why the Cache Stores the Module Object

The cache stores the Module instance, not merely a frozen snapshot of module.exports.

Conceptually:

require.cache[filename] = module;

Then the module contains:

module.exports;

This matters because the module's export property can change during evaluation.

For example:

module.exports.foo = 1;

module.exports.bar = 2;

The same module object remains associated with the cache.

85. Later module.exports Replacement

The source notes a subtle timing behavior.

Suppose a module changes module.exports asynchronously after its normal evaluation:

module.exports = {
  initial: true,
};

setTimeout(() => {
  module.exports = {
    later: true,
  };
}, 1000);

An earlier caller may already have received:

{
  initial: true;
}

A later require() can potentially read the module's current module.exports.

This can produce different values for old and new consumers.

For predictable CommonJS code:

Assign the final module.exports synchronously during module evaluation.

Avoid designing exports around asynchronous reassignment.

86. Existing References vs Current module.exports

This distinction is crucial.

Suppose:

const first = require("./module");

At that moment:

first ---> export object A

Later the module does:

module.exports = objectB;

Now the module's property is:

module.exports ---> objectB

But:

first ---> objectA

does not magically change.

JavaScript variables contain references/values they were assigned; changing another variable or property does not rewrite every existing reference.

87. module.exports Replacement vs Mutation

Compare:

Mutation​

module.exports.foo = 10;

Existing references to the exported object can observe the new property.

Replacement​

module.exports = {
  foo: 10,
};

The module now points at a different object.

Existing consumers holding the previous object do not automatically switch.

This distinction is especially important in circular dependencies and hot-reload experiments.

You can also use:

require.resolve.paths()

Inspect loaded CommonJS modules:

console.log(Object.keys(require.cache));

Inspect one specific module:

const path = require.resolve("./math");

const cached = require.cache[path];

This can help understand runtime module relationships.

91. Debugging Circular Dependencies

When an imported value unexpectedly becomes:

undefined;

in a CommonJS application, one possibility is a circular dependency.

Trace:

A requires B
B requires C
C requires A

Then ask:

At what point is the value being read?

A module may not have reached the line that initializes that property.

The fastest practical approach is usually to trace the require() chain from the undefined value back to the cycle.

92. Circular Dependency Debugging Example

Suppose:

controllers/user.js
      |
      v
services/user.js
      |
      v
models/user.js
      |
      v
services/user.js

The dependency graph contains a cycle.

Do not merely ask:

"Why is the function undefined?"

Ask:

  1. Which module loads first?
  2. Which module requires the other?
  3. What has module.exports been assigned at that moment?
  4. Has the module finished loading?
  5. Is the code mutating the existing export object or replacing module.exports?

Those questions usually expose the problem.

96. Common Interview Question: "Does require() Execute the Module?"

Answer:

Yes, on the first successful load, Node evaluates the module's top-level code.

Example:

// test.js

console.log("executed");

module.exports = {};

Then:

require("./test");

prints:

executed

A subsequent:

require("./test");

normally returns the cached module and does not execute the module body again.

97. Common Interview Question: "Does require() Give Access to All Variables?"

No.

Suppose:

// module.js

const secret = 123;

function greet() {
  return "hello";
}

console.log(secret);

module.exports = {
  greet,
};

Another module:

const mod = require("./module");

gets only:

{
  greet: ...
}

It does not automatically get:

secret

The module's internal variables remain private unless exported.

This privacy comes naturally from the module wrapper/function scope.

98. Common Interview Question: "If I Require a Module, Does Its Code Run?"

Yes, top-level synchronous code runs during the first load.

For example:

// logger.js

console.log("logger initialized");

function log() {
  console.log("log");
}

module.exports = log;

Calling:

const log = require("./logger");

causes:

logger initialized

to execute.

But:

log();

does not happen unless you explicitly call the exported function.

So distinguish:

module evaluation

from:

calling exported functions

99. Common Interview Question: "Is a Required Object Cloned?"

Normally, no.

Example:

// state.js

module.exports = {
  count: 0,
};

Then:

const a = require("./state");
const b = require("./state");

a.count = 10;

console.log(b.count);

Output:

10

Both references point to the same cached exported object.

100. Common Interview Question: "Why Is exports.foo Working?"

Because initially:

exports === module.exports;

So:

exports.foo = foo;

modifies the object that require() will return.

But:

exports = foo;

only changes the local variable.

101. Common Interview Question: "Why Does Circular Dependency Return Undefined?"

Because the module may be requested while it is still being evaluated.

Example:

A
 |
 v
B
 |
 v
A

When B asks for A, A may only have initialized some exports.

Therefore B can receive:

{
  someValue: ...
}

while another property is still missing.

102. Common Interview Question: "Why Does Node Cache Before Execution?"

Because it enables circular dependencies to terminate.

Without early caching:

A -> B -> A -> B -> ...

could continue indefinitely.

With early caching:

A starts
  |
  v
A cached
  |
  v
B starts
  |
  v
B asks for A
  |
  v
A found in cache

B gets A's current exports.

103. Common Interview Question: "What Is the Cache Key?"

For ordinary file-backed CommonJS modules, the important key is the resolved filename.

Not simply:

"./math";

but something like:

/home/user/project/math.js

Therefore two requests that resolve to the same file normally share the same cached module.

104. Common Interview Question: "require.resolve() vs require()?"

require()​

require("./math");

means:

resolve + load + evaluate + return exports

require.resolve()​

require.resolve("./math");

means:

resolve + return target

It does not execute the module.

105. Common Interview Question: "require.resolve.paths()?"

It shows the directories Node would use to search for the requested module.

Example:

require.resolve.paths("express");

This is especially useful for debugging package resolution.

106. Common Interview Question: "Why Is require() Synchronous?"

CommonJS was designed around synchronous loading.

This provides a simple guarantee:

require()
  |
  v
when it returns, synchronous module initialization is complete

The trade-off is that disk reads, compilation, and top-level execution can block the event loop.

107. Common Interview Question: "Should I Require Heavy Modules Inside Request Handlers?"

Usually, stable dependencies are better loaded during startup:

const heavy = require("./heavy");

rather than:

app.get("/endpoint", (req, res) => {
  const heavy = require("./heavy");
});

The first request to the endpoint can otherwise pay the initial loading cost.

However, lazy loading can be intentional for:

  • rare features
  • optional dependencies
  • expensive dependencies
  • conditionally used functionality

The decision is about where you want to pay the first-load cost.

108. Common Interview Question: "What Happens If Module Loading Throws?"

Node removes the failed module from the CommonJS cache before propagating the error.

This allows a later require() attempt to start the loading process again.

Conceptually:

cache
  |
  v
load
  |
  X
error
  |
  v
remove cache entry
  |
  v
throw

109. Common Interview Question: "What Happens If JSON Changes on Disk?"

Suppose:

{
  "port": 3000
}

is loaded:

const config = require("./config.json");

Node parses and caches the object.

If the file changes afterward, another:

require("./config.json");

normally returns the cached object rather than reparsing the file.

Therefore filesystem changes do not automatically invalidate the CommonJS JSON cache.

second: undefined

Then move:

exports.second = "A second";

above:

const b = require("./b");

and run again.

You should see the difference.

This demonstrates that the order of export initialization matters in a cycle.

119. Practical Experiment: Cycle + Replacement

a.js​

const b = require("./b");

module.exports = {
  ready: true,
};

b.js​

const a = require("./a");

console.log(a);

Observe that B can receive the earlier exports object rather than the later replacement.

This is the exact class of problem caused by replacing module.exports during a cycle.

120. Practical Experiment: Directory Resolution

Create:

myLib/
├── package.json
└── lib/
    └── index.js

package.json:

{
  "main": "lib/index.js"
}

Then:

require("./myLib");

Observe which file is executed.

This demonstrates directory entry-point resolution.

121. Practical Experiment: Conditional Loading

let parser;

if (process.env.USE_FAST === "true") {
  parser = require("./fast");
} else {
  parser = require("./safe");
}

Add:

console.log("fast loaded");

and:

console.log("safe loaded");

to the respective files.

Only the selected branch should load its module.

122. A Better Mental Model for Node CommonJS

Do not think:

"require() is just importing a file."

Use this stronger model:

require() is a synchronous module-loading operation that resolves a request, checks the CommonJS cache, loads and evaluates an uncached module, and returns its module.exports.

Then remember the important exception:

During circular loading, the module may be returned before evaluation has finished, so its exports can be incomplete.

123. The Five Core Objects/Concepts

If you want a compact mental model, focus on these:

1. Request​

"./math";

What the caller asks for.

2. Resolved filename​

/project/math.js

What Node determines the request means.

3. Module object​

Module {
  exports,
  loaded,
  filename,
  children,
  ...
}

The runtime representation of the module.

4. Cache​

require.cache;

Stores loaded CommonJS module instances.

5. module.exports​

The value ultimately returned to the consumer.

                     |      compile / parse
                     |            |
                     |            v
                     |        execute code
                     |            |
                     |            v
                     |      module.exports
                     |            |
                     +------------+
                           |
                           v
                    return exports

And the three rules underneath it:

RULE 1:
require() returns module.exports.

RULE 2:
CommonJS caches modules by resolved filename.

RULE 3:
Modules enter the cache before they finish executing,
which is why circular dependencies can expose partial exports.

Then the exports rule:

exports.foo = value
    -> mutate existing export object

module.exports = value
    -> replace exported value

exports = value
    -> only reassign local variable

And the resolution rule:

require()
    -> resolve + load + execute + return

require.resolve()
    -> resolve only

require.resolve.paths()
    -> show lookup paths

These are the core mechanics behind the CommonJS module system covered by the source.
