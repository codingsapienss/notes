Node.js CommonJS ↔ ES Modules Interop: CJS/ESM Edges & Dual Packages

1. What Is CJS/ESM Interoperability?

Node.js has two module systems:

CommonJS
  require()
  module.exports
  synchronous loading

ES Modules
  import
  export
  parse → link → evaluate
  can be asynchronous

Interop means allowing code using one system to consume code using the other.

You will encounter this constantly in:

  • older Node.js applications
  • modern ESM applications
  • npm dependencies
  • migrations from CJS → ESM
  • libraries supporting both systems
  • monorepos
  • TypeScript projects
  • dual packages

2. The Four Questions That Explain Most Interop Problems

When something involving CJS and ESM behaves strangely, ask these four questions:

1. Direction
   Who is loading whom?

2. Timing
   Does the target ESM graph contain top-level await?

3. Identity
   Did import and require resolve to the same implementation?

4. Shape
   What value/object did the consumer actually receive?

This is the most useful debugging framework in the entire topic.

3. Direction Matters

There are two fundamentally different cases.

ESM → CJS​

ESM
 ↓
import
 ↓
CJS

This is generally the easier direction.

The CJS module's:

module.exports;

becomes the ESM-facing default export.

CJS → ESM​

CJS
 ↓
require() / import()
 ↓
ESM

This is more complicated because require() is synchronous while ESM can require asynchronous evaluation.

Modern Node can synchronously require() an ESM graph only when the entire graph can finish synchronously.

If top-level await exists anywhere in that graph:

require()
   ↓
ESM graph
   ↓
top-level await
   ↓
cannot finish synchronously
   ↓
ERR_REQUIRE_ASYNC_MODULE

Dynamic:

await import("./module.mjs");

remains the broad compatibility path.

4. CJS vs ESM: Fundamental Differences

Concept CommonJS ESM

Import require() import

Export module.exports export

Main loading style Synchronous Static graph + async-capable evaluation

Dependency discovery Runtime Static for import

Cache model Path-oriented CJS cache URL-oriented ESM cache

require Yes No by default

module.exports Yes No

__dirname Yes Use ESM metadata

__filename Yes Use ESM metadata

Top-level await No Yes

Live ESM bindings No equivalent Yes

Interop exists because these systems were designed around different assumptions.

5. Module Format Must Be Determined First

Before discussing interop, Node must decide whether a file is CJS or ESM.

Remember:

.mjs → always ESM
.cjs → always CJS
.js  → nearest package.json "type"

For .js:

{
  "type": "module"
}

means ESM.

{
  "type": "commonjs"
}

or no "type" means CommonJS under normal/default behavior.

This decision happens before Node applies the appropriate module loader behavior.

6. Why File Format Matters for Interop

Consider:

import config from "./config.js";

That line alone does not tell the whole story.

You need to know:

What is config.js?
        ↓
.mjs? → ESM
.cjs? → CJS
.js?  → inspect package "type"

If Node thinks the file is CJS, it uses the CommonJS loader.

If Node thinks it is ESM, it uses the ESM loader.

A large number of "import/export doesn't work" errors are actually wrong module-format classification.

7. ESM Importing CJS

This is the smoother direction.

Suppose:

// config.cjs
module.exports = {
  port: 3000,
  host: "localhost",
};

ESM can do:

import config from "./config.cjs";

console.log(config.port);
console.log(config.host);

The key rule:

The CJS module.exports value becomes the ESM-facing default export.

Conceptually:

CJS

module.exports
      │
      ▼
{ port: 3000, host: "localhost" }
      │
      ▼
ESM default import
      │
      ▼
config

8. Why Default Import Is the Safest Way to Consume CJS

Given:

// library.cjs
module.exports = {
  connect,
  disconnect,
};

Prefer:

import library from "./library.cjs";

library.connect();
library.disconnect();

This directly represents the real CJS export:

module.exports;

It does not depend on Node successfully guessing named exports from CJS source code.

9. Named Imports from CJS

You may sometimes see:

import { readConfig } from "./config.cjs";

with:

exports.readConfig = () => {
  return { port: 3000 };
};

This can work.

But there is an important detail:

CJS does not have ESM named exports.

Node has to detect likely export names from the CJS source code and expose synthetic named exports to ESM.

10. How Node Detects CJS Named Exports

Node uses source analysis through:

cjs-module-lexer

It scans the CJS source without executing it.

For example:

exports.foo = 42;

is easy to recognize.

Likewise:

module.exports.bar = "hello";

can be recognized.

This allows ESM code to write:

import { foo, bar } from "./lib.cjs";

when Node detects those names.

11. CJS Named Export Detection Is Best-Effort

This is critical.

Node is not executing the CJS program to discover its exports.

It is analyzing source patterns.

Therefore, this is problematic:

const methods = ["get", "post", "put"];

methods.forEach((method) => {
  exports[method] = createHandler(method);
});

At runtime the module may contain:

get
post
put

But static source analysis cannot reliably infer all runtime-generated property names.

12. Dynamic CJS Exports

Example:

const name = "connect";

exports[name] = () => {};

or:

Object.assign(module.exports, someObject);

or:

exports[dynamicKey] = value;

These patterns may not produce usable synthetic named exports.

The safe fallback is:

import pkg from "./module.cjs";

pkg.connect();

Then you are reading actual properties from the CJS module.exports object.

13. Important: Synthetic CJS Named Exports Are Not True ESM Live Bindings

Suppose CJS does:

exports.count = 0;

setTimeout(() => {
  exports.count = 10;
}, 1000);

Do not assume:

import { count } from "./counter.cjs";

behaves like a genuine ESM live binding.

The named exports exposed from CJS are based on detected properties and do not provide the same live-binding semantics as real ESM exports.

The default import remains closer to the actual CJS object:

import counter from "./counter.cjs";

console.log(counter.count);

14. ESM → CJS: The Important Shape

For:

// lib.cjs
module.exports = {
  foo: 1,
  bar: 2,
};

Think:

ESM import

import whole from "./lib.cjs";

whole
  ↓
module.exports
  ↓
{
  foo: 1,
  bar: 2
}

This is the most reliable mental model.

15. Dynamic import() of CJS

ESM can also dynamically import CJS:

const mod = await import("./config.cjs");

console.log(mod.default);

The Promise resolves to an ESM-style module namespace.

Conceptually:

mod
├── default
├── "module.exports"
└── detected named exports

The default property represents the CJS module.exports value.

16. The "module.exports" Marker

Modern Node's CJS-to-ESM namespace can also expose:

"module.exports"

as a marker representing the same module.exports value.

You may see:

const mod = await import("./lib.cjs");

console.log(mod.default);
console.log(mod["module.exports"]);

For normal application development, the practical thing to remember is:

default represents the CJS module.exports.

You do not need to build application logic around the marker.

17. CJS Importing ESM

Now reverse the direction:

CJS
 ↓
ESM

This is where timing becomes important.

CJS:

const mod = require("./lib.mjs");

expects:

require()
 ↓
value immediately

But ESM can contain:

await something();

at the top level.

That means the ESM graph may not be synchronously evaluable.

18. Dynamic import() Is the Broad Compatibility Path

From CJS:

async function main() {
  const mod = await import("./lib.mjs");

  mod.start();
}

main();

This works with asynchronous ESM.

The result is the ESM module namespace:

mod
├── named exports
└── default

19. Why Dynamic import() Changes Your CJS Code

Suppose old CJS code is:

const config = require("./config.js");

startServer(config);

With dynamic import:

const config = await import("./config.js");

startServer(config);

you have changed the execution model.

The caller must now be able to wait.

This can propagate upward through your application.

async dependency
      ↓
async loader
      ↓
async startup
      ↓
possibly async initialization API

This is one reason ESM migrations can be architectural rather than purely syntactic.

20. Modern require(esm)

Modern Node supports synchronous require() of ESM when the target ESM graph can finish synchronously.

Conceptually:

// CJS
const utils = require("./utils.mjs");

can work if:

utils.mjs
  ↓
all dependencies
  ↓
NO top-level await

The important restriction is:

The entire ESM dependency graph must be synchronously evaluable.

Not merely the entry file.

21. ERR_REQUIRE_ASYNC_MODULE

Consider:

// async-module.mjs
await setup();

export const ready = true;

Then:

// app.cjs
require("./async-module.mjs");

fails with:

ERR_REQUIRE_ASYNC_MODULE

Why?

require()
  ↓
must return synchronously
  ↓
ESM graph needs to await
  ↓
cannot satisfy synchronous contract

Use:

const mod = await import("./async-module.mjs");

instead.

22. Top-Level Await Can Be Deep in the Graph

This is important.

You might have:

a.mjs
  ↓
b.mjs
  ↓
c.mjs

and only:

// c.mjs
await initialize();

Then:

require("./a.mjs");

can still fail.

Why?

Because a.mjs depends on a graph whose evaluation is asynchronous.

Think:

require(a)
   ↓
a imports b
   ↓
b imports c
   ↓
c has top-level await
   ↓
whole graph becomes async
   ↓
require() cannot synchronously finish

23. What Does require(esm) Return?

When CJS successfully requires ESM:

const mod = require("./utils.mjs");

the normal result is the ESM module namespace object.

So:

export const helper = () => {};
export default function main() {}

can be consumed from CJS as:

const mod = require("./utils.mjs");

mod.helper();
mod.default();

This differs from CJS:

module.exports = function main() {};

where:

const main = require("./main.cjs");

directly receives the function.

24. Special "module.exports" Export from ESM

An ESM module can intentionally specify what CJS require() should receive.

Example:

// point.mjs
export default class Point {}

export { Point as "module.exports" };

Then:

const Point = require("./point.mjs");

can receive:

Point

directly rather than the normal namespace shape.

Why this exists​

It can help an ESM package preserve a familiar CJS-facing API during migration.

Tradeoff​

The CJS caller no longer automatically receives the normal namespace containing all ESM exports.

So use this intentionally, not casually.

25. CJS → ESM: Three Main Paths

Situation Recommended path

Modern Node + synchronous ESM graph require() can work ESM graph has top-level await await import() Older Node / broad compatibility await import()

The key is not:

"Can Node import ESM?"

It can.

The key is:

Can this specific ESM graph satisfy the synchronous contract of require()?

26. Interop Shape Comparison

ESM → CJS​

import pkg from "./pkg.cjs";

Main result:

pkg === module.exports

Conceptually.

CJS → ESM with require()​

const mod = require("./pkg.mjs");

Main result:

mod = ESM namespace object

unless the ESM package intentionally provides the special:

"module.exports"

export.

CJS → ESM with dynamic import​

const mod = await import("./pkg.mjs");

Result:

module namespace object

with:

default
named exports

27. The Dual Package

A dual package publishes both:

CommonJS
+
ESM

For example:

my-lib/
├── dist/
│   ├── cjs/
│   │   └── index.cjs
│   └── esm/
│       └── index.js
└── package.json

The package may expose:

ESM consumer
   ↓
dist/esm/index.js

CJS consumer
   ↓
dist/cjs/index.cjs

This sounds convenient.

But it introduces a major problem.

28. The Dual Package Hazard

Suppose:

ESM
 ↓
dist/esm/index.js

CJS
 ↓
dist/cjs/index.cjs

Those are two different files.

Therefore Node can create:

ESM module instance
+
CJS module instance

Even though both represent the same conceptual package.

29. Why Two Copies Matter

Imagine the package contains:

const state = new Map();

export function getState() {
  return state;
}

If two copies of the package load, you get:

ESM package
 └── Map A

CJS package
 └── Map B

Now:

getState() from ESM
        ≠
getState() from CJS

in terms of shared module-level state.

This can break:

  • singleton patterns
  • connection pools
  • caches
  • registries
  • event systems
  • configuration state
  • class identity

30. The instanceof Symptom

This is one of the clearest signs.

Suppose both package copies define:

class User {}

Then:

ESM copy → User class A
CJS copy → User class B

An object created using class A:

const user = new UserA();

may fail:

user instanceof UserB;

even though both classes came from the "same package."

They are not the same runtime class object.

They came from different module instances.

31. Why Caches Do Not Automatically Merge Them

CommonJS and ESM have different module-loading/cache machinery.

Conceptually:

CJS
 ↓
CJS cache
 ↓
resolved filesystem path

ESM
 ↓
ESM loader
 ↓
resolved URL

If:

CJS → index.cjs
ESM → index.js

there is no reason for Node to treat them as the same module implementation.

Different files mean different module instances.

32. The Real Problem Is Not "Dual Package"

Publishing both formats is not automatically bad.

The problem is:

same conceptual library
        ↓
different runtime implementations
        ↓
different module instances
        ↓
duplicated state / identity

A stateless library may tolerate this.

A stateful library may not.

33. Strategy 1 --- Keep the Package Stateless

If the library mainly exposes:

export function add(a, b) {
  return a + b;
}

two copies are usually much less dangerous.

There is no important shared module-level state.

This is one reason functional/stateless library design can simplify dual packaging.

34. Strategy 2 --- One Implementation + Thin Wrapper

A stronger strategy is:

one canonical implementation
        ↓
other format = wrapper

For example:

ESM implementation
        ↑
CJS wrapper

Modern Node can allow a CJS wrapper to synchronously require a synchronous ESM implementation:

// index.cjs
module.exports = require("../esm/index.js");

Now both entry points can converge on the same underlying ESM implementation.

35. Why This Can Be Better

Instead of:

ESM → implementation A
CJS → implementation B

you get:

ESM ────────────────┐
                    ↓
              implementation
                    ↑
CJS wrapper ────────┘

There is one real implementation.

This reduces duplicated module-level state.

The caveat is that the ESM graph must support synchronous require(esm) and the resulting namespace/value shape must be acceptable to CJS consumers.

36. Strategy 3 --- Shared State Module

Sometimes you must keep separate entry files.

You can centralize important state:

CJS entry ──────┐
                ↓
           shared-state
                ↑
ESM entry ──────┘

Both entry points use the same internal state module where the module systems can share that dependency safely.

This is more complicated than a single implementation + wrapper, but can solve state duplication when separate public entry formats are unavoidable.

37. Strategy 4 --- ESM Only

If your supported environment allows it, publishing only ESM is the simplest architecture.

Advantages:

  • one module system
  • one implementation
  • simpler build
  • simpler exports
  • fewer interop edge cases
  • no dual-build state hazard

Tradeoff:

  • older CJS consumers may need migration
  • some consumers may need dynamic import()
  • older Node support may be lost

For applications, this decision is much easier because you control the application.

For libraries, consumer compatibility matters.

38. Applications vs Libraries

Application​

Usually:

Pick one format
+
use it consistently

For a modern Node application:

{
  "type": "module"
}

and use:

import ...
export ...

Dependencies can still be CJS.

Node handles the package-level interop.

Library​

You need to think about:

  • who consumes the package
  • supported Node versions
  • CJS consumers
  • ESM consumers
  • statefulness
  • package exports
  • build outputs
  • entry-point identity

This is where dual-package design matters most.

39. Conditional Exports

The package "exports" field can route consumers differently.

Example:

{
  "exports": {
    ".": {
      "import": "./dist/esm/index.js",
      "require": "./dist/cjs/index.cjs"
    }
  }
}

Conceptually:

import "my-lib"
       ↓
"import" condition
       ↓
dist/esm/index.js

and:

require("my-lib")
       ↓
"require" condition
       ↓
dist/cjs/index.cjs

40. Why "exports" Is Important

It does two jobs.

1. Conditional routing​

Different consumers can get different entry points.

2. Package encapsulation​

Only declared public paths are available through package specifiers.

Example:

{
  "exports": {
    ".": "./dist/index.js"
  }
}

Then:

import "my-lib";

works.

But:

import "my-lib/internal/secret.js";

can fail with:

ERR_PACKAGE_PATH_NOT_EXPORTED

41. Conditional Export Order Matters

Conditions are checked in order.

Example:

{
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/esm/index.js",
      "require": "./dist/cjs/index.cjs",
      "default": "./dist/esm/index.js"
    }
  }
}

The ordering is meaningful.

Think:

top
 ↓
first matching condition
 ↓
selected target

42. Important Conditions

You may encounter:

types
node
module-sync
import
require
default

import​

Used for ESM import resolution.

require​

Used for CJS require() resolution.

default​

Fallback.

node​

Node-specific condition.

module-sync​

Useful when one synchronous ESM implementation can serve both import and require paths.

types​

Primarily for type tooling.

Custom conditions​

Can be enabled with Node's condition mechanisms.

43. module-sync

This condition is particularly relevant to modern dual packages.

Conceptually:

{
  "exports": {
    ".": {
      "module-sync": "./dist/esm/index.js",
      "import": "./dist/esm/index.js",
      "require": "./dist/cjs/index.cjs"
    }
  }
}

module-sync can let both import and require consumers use the same synchronous ESM implementation.

But:

Use it only if the target ESM graph contains no top-level await.

Otherwise a CJS require() path can fail with:

ERR_REQUIRE_ASYNC_MODULE

44. Subpath Exports

You can expose more than the root package:

{
  "exports": {
    ".": {
      "import": "./dist/esm/index.js",
      "require": "./dist/cjs/index.cjs"
    },
    "./utils": {
      "import": "./dist/esm/utils.js",
      "require": "./dist/cjs/utils.cjs"
    }
  }
}

Consumers can then use:

import { helper } from "my-lib/utils";

or:

const { helper } = require("my-lib/utils");

45. "main" vs "exports" vs "module"

"main"​

Traditional Node package entry point:

{
  "main": "./dist/index.cjs"
}

"exports"​

Modern package API and conditional routing:

{
  "exports": {
    ".": "./dist/index.js"
  }
}

"module"​

Often used by bundlers.

Node does not use "module" as its own package-resolution mechanism.

For modern Node libraries, understand:

exports

as the important package API mechanism.

46. Building a Dual Package

A common project structure:

src/
└── index.js

dist/
├── esm/
│   └── index.js
└── cjs/
    └── index.cjs

package.json

Build tools such as:

  • tsup
  • unbuild
  • esbuild

can produce both formats.

The package then maps consumers to the appropriate build.

47. Why .cjs Matters in a "type": "module" Package

Suppose:

{
  "type": "module"
}

Then:

index.js → ESM

Therefore a CJS build should normally use:

index.cjs

not:

index.js

Otherwise Node will treat it as ESM under that package scope.

This is a common dual-build mistake.

48. Testing a Dual Package

Do not test only one entry point.

Test:

ESM consumer → package
CJS consumer → package

Check:

  • exports
  • default export
  • named exports
  • runtime behavior
  • errors
  • singleton behavior
  • class identity
  • state sharing

A package can have a perfect ESM build and a broken CJS build.

49. Export Shape Tests

For example, ESM:

import * as esmExports from "../dist/esm/index.js";

CJS:

import cjsExports from "../dist/cjs/index.cjs";

Then compare intended export names.

Do not blindly compare namespace metadata such as:

default
module.exports

because these are interop-related representations, not necessarily your public API.

50. Test Runtime Behavior Too

Matching export names is not enough.

Test:

const user = createUser();

and verify that:

  • behavior matches
  • state behaves correctly
  • errors match
  • classes behave correctly
  • initialization occurs once where expected

The goal is not just:

same keys

but:

same public contract

51. TypeScript Adds Another Layer

If using TypeScript, Node's runtime rules still matter.

Important settings include:

module
moduleResolution

and:

package.json → type
file extensions
package.json → exports

With Node-aware configurations such as:

node16
nodenext

TypeScript follows Node-style module rules more closely.

The key lesson:

TypeScript's compiler configuration cannot magically override Node's runtime module semantics.

52. The __esModule Convention

You may encounter:

Object.defineProperty(exports, "__esModule", {
  value: true,
});

This often comes from transpilers such as Babel or bundlers.

Historically, tools used this marker to communicate:

"This CommonJS object came from transpiled ESM."

This helped tools decide how to interpret:

exports.default

53. Do Not Confuse __esModule with Native Node ESM

Native Node ESM/CJS interop does not fundamentally use:

__esModule

to decide what the default export is.

For native CJS imported by ESM:

default = module.exports

The __esModule convention mainly exists for compatibility with tooling/transpiled ecosystems.

Do not build new application architecture around it.

54. Common Error: ERR_REQUIRE_ESM

Historically, CJS code doing:

require("./module.mjs");

could get:

ERR_REQUIRE_ESM

on runtimes that did not support synchronous require(esm).

Modern Node versions can support synchronous ESM when the graph is appropriate.

If you encounter this error:

1. Check Node version
2. Check whether require(esm) is available
3. Check whether the target is ESM
4. Consider dynamic import()

55. Common Error: ERR_REQUIRE_ASYNC_MODULE

Meaning:

require()
    ↓
ESM graph
    ↓
top-level await
    ↓
cannot synchronously finish

Fix:

const mod = await import("./module.mjs");

or redesign the ESM graph so it does not require top-level await.

56. Common Error: ERR_REQUIRE_CYCLE_MODULE

This can occur when synchronous CJS → ESM loading encounters an immediate CJS/ESM cycle.

Example:

// a.mjs
import "./b.cjs";
// b.cjs
require("./a.mjs");

The synchronous bridge cannot safely establish this immediate cycle.

Possible solutions:

  • move one load behind a function
  • use dynamic import()
  • extract shared code into a third module
  • redesign the dependency direction

57. Common Error: ERR_PACKAGE_PATH_NOT_EXPORTED

Example:

import internal from "my-lib/internal/private.js";

while:

{
  "exports": {
    ".": "./dist/index.js"
  }
}

does not expose that subpath.

The correct solution is generally:

import something from "my-lib";

or use an officially exported subpath.

Do not depend on package internals simply because you can find the file in node_modules.

58. Common Error: Named Export Not Found

Suppose CJS has:

Object.assign(module.exports, dynamicObject);

and ESM tries:

import { helper } from "./lib.cjs";

Node may not detect helper.

Use:

import pkg from "./lib.cjs";

pkg.helper();

The important difference:

named import
    ↓
depends on static CJS export detection

default import
    ↓
gets module.exports

59. Common Error: Cannot use import statement outside a module

This usually means Node classified your file as CJS even though it contains:

import ...

Check:

file extension
nearest package.json
"type"

Possible fixes:

rename to .mjs

or:

{
  "type": "module"
}

60. Common Error: module is not defined in ES module scope

If:

module.exports = ...

runs in ESM, you can get:

ReferenceError: module is not defined in ES module scope

Why?

ESM does not provide the CommonJS wrapper variables:

require
module
exports
__filename
__dirname

Convert the file to ESM or explicitly use createRequire() when a real CJS require is necessary.

61. Default Export Confusion

CJS:

module.exports = function greet() {
  return "hello";
};

ESM:

import greet from "./greet.cjs";

greet();

works naturally.

But:

import { greet } from "./greet.cjs";

does not mean:

"give me module.exports"

It means:

"give me a named export/property called greet"

The CJS module did not export:

exports.greet = ...

It exported the entire function as:

module.exports = ...

62. A Simple Mapping to Remember

For CJS:

module.exports = X;

think:

ESM default → X

For:

exports.foo = Y;

think:

ESM may expose named export → foo

but remember that named detection is best-effort.

63. Debugging Interop: Fixed Order

Do not randomly modify imports until the error disappears.

Use this sequence.

Step 1 --- Direction​

Ask:

ESM → CJS?
CJS → ESM?

Step 2 --- Format​

Check:

.mjs
.cjs
.js
package.json "type"

Step 3 --- Timing​

If CJS uses:

require("...");

ask:

Does the ESM graph contain top-level await?

Step 4 --- Export Shape​

Ask:

Is the target:
CJS module.exports?
ESM namespace?
default export?
named export?

Step 5 --- Package Exports​

Inspect:

"exports"

Does the package expose the path?

Step 6 --- Identity​

Check whether:

import

and:

require

resolve to the same actual implementation file.

If not, investigate the dual-package hazard.

64. Debugging CJS Export Detection

From ESM:

const ns = await import("./module.cjs");

console.log(Object.keys(ns));

If you see mostly:

default
module.exports

and your expected named exports are missing, Node likely did not detect the CJS export patterns.

Then prefer:

import pkg from "./module.cjs";

and access:

pkg.someFunction;

65. Debugging Conditional Exports

Suppose:

{
  "exports": {
    ".": {
      "import": "./dist/esm/index.js",
      "require": "./dist/cjs/index.cjs"
    }
  }
}

An ESM consumer and CJS consumer may intentionally resolve differently.

Check from ESM:

console.log(import.meta.resolve("my-lib"));

From CJS:

console.log(require.resolve("my-lib"));

If the results differ, you may have two implementations.

66. Debugging Duplicate Module Instances

A useful experiment is to put initialization logging inside the package:

console.log("my-lib initialized");

Then use both:

import "my-lib"

and:

require("my-lib")

If the package is being loaded through two different builds, you may see initialization twice.

Then inspect the actual resolved paths.

67. The Internal Bridge: Conceptual View

Node does not magically convert one module system into the other.

It uses translation/facade mechanisms.

For ESM → CJS:

ESM import
    ↓
CJS target
    ↓
CJS loader executes module
    ↓
module.exports
    ↓
ESM-facing facade

For CJS → ESM:

CJS loader
    ↓
ESM target
    ↓
ESM loader
    ↓
parse/link/evaluate
    ↓
namespace object

This explains why the two directions have different rules.

68. CJS Translator and Synthetic Named Exports

When ESM imports CJS, Node needs to know the names available before the ESM import can be linked.

So it roughly does:

read CJS source
      ↓
analyze likely exports
      ↓
create ESM-facing names
      ↓
evaluate CJS
      ↓
populate facade

This is why:

CJS named exports

are not equivalent to:

real ESM named exports

They are a compatibility mechanism.

69. Why the Lexer Does Not Execute CJS

Imagine:

if (process.env.MODE === "production") {
  exports.prod = createProd();
} else {
  exports.dev = createDev();
}

The loader cannot safely execute arbitrary application code merely to discover export names.

So it analyzes source.

That makes the process:

  • predictable
  • relatively cheap
  • safe from executing application logic during name discovery

But it means dynamic export construction cannot be perfectly understood.

70. CJS → ESM require() Conceptual Flow

When supported:

const mod = require("./app.mjs");

conceptually:

Module._load()
      ↓
resolve target
      ↓
determine ESM format
      ↓
ESM loader
      ↓
parse graph
      ↓
resolve dependencies
      ↓
link
      ↓
evaluate
      ↓
check synchronous completion
      ↓
return namespace

If top-level await exists:

evaluation becomes async
      ↓
require cannot wait
      ↓
ERR_REQUIRE_ASYNC_MODULE

71. import() vs require() During Interop

require()​

const mod = require("./x");

Characteristics:

  • synchronous
  • CommonJS loader entry
  • can load supported synchronous ESM
  • cannot handle asynchronous ESM graphs

import()​

const mod = await import("./x");

Characteristics:

  • asynchronous
  • enters ESM loader
  • works with ESM
  • can handle top-level await
  • returns a module namespace

This distinction should be automatic in your reasoning.

72. Why ESM-Only Packages Used to Break CJS Apps

Suppose an old CJS application had:

const chalk = require("chalk");

Then a newer version of the dependency becomes ESM-only.

Now:

CJS application
      ↓
require("chalk")
      ↓
ESM package

Historically this could produce:

ERR_REQUIRE_ESM

The CJS application had choices:

pin older package
OR
migrate to ESM
OR
use dynamic import()
OR
use a compatible version/runtime

Modern Node's require(esm) reduces this problem for synchronous ESM, but the async/top-level-await limitation remains.

73. Dual Package Design: The Decision Tree

If you are publishing a library, ask:

Does the library need CJS support?
          │
          ├── No
          │    ↓
          │  ESM only
          │
          └── Yes
               ↓
        Does it have important module-level state?
               │
               ├── No
               │    ↓
               │  Dual builds are simpler
               │
               └── Yes
                    ↓
             Can one implementation serve both?
                    │
                    ├── Yes
                    │    ↓
                    │  Prefer one implementation + wrapper
                    │
                    └── No
                         ↓
                  Carefully centralize state
                  and test identity

74. What Not to Do

Do not assume:

same npm package name
=
same runtime module instance

Do not assume:

CJS named exports
=
ESM named exports

Do not assume:

require(esm)
=
dynamic import()

They have different timing/entry semantics.

Do not assume:

two build outputs
=
one module

They can produce two independent module instances.

75. Practical Rules for Backend Developers

Rule 1​

If possible, keep an application on one primary module system.

Rule 2​

When ESM imports CJS, prefer the default import unless you have a clear reason to rely on detected named exports.

Rule 3​

When CJS loads ESM, use:

await import(...)

if the graph may contain top-level await or broad runtime compatibility matters.

Rule 4​

Understand "exports".

It controls which package paths and conditions consumers can access.

Rule 5​

If a dual package has state, think about duplicate instances.

Rule 6​

When debugging, compare actual resolved paths.

Rule 7​

Do not rely on private Node internals for application architecture.

76. Practical Rules for Package Authors

  1. Declare "type" clearly.
  2. Use explicit .cjs for CJS files inside a "type": "module" package.
  3. Prefer "exports" for modern package entry-point control.
  4. Test both import and require.
  5. Test all public subpaths.
  6. Decide whether CJS/ESM consumers should receive the same implementation.
  7. Avoid duplicated module-level state where possible.
  8. Document supported Node versions.
  9. Keep export shapes consistent.
  10. Treat CJS named-export detection as compatibility behavior, not a replacement for proper ESM exports.

77. A Realistic Dual Package Example

Project:

my-lib/
├── src/
│   └── index.js
├── dist/
│   ├── esm/
│   │   └── index.js
│   └── cjs/
│       └── index.cjs
└── package.json

Package:

{
  "name": "my-lib",
  "type": "module",
  "main": "./dist/cjs/index.cjs",
  "exports": {
    ".": {
      "import": "./dist/esm/index.js",
      "require": "./dist/cjs/index.cjs"
    }
  },
  "files": ["dist"]
}

Consumers:

ESM​

import { createClient } from "my-lib";

CJS​

const { createClient } = require("my-lib");

This is a standard dual-package shape.

The remaining design question is:

Are these two entry points two implementations, or two routes into one implementation?

That determines how serious the dual-package hazard is.

78. One-Implementation Dual Package

A better architecture when feasible:

                    ┌── ESM consumer
                    │
ESM implementation ─┤
                    │
                    └── CJS wrapper

Rather than:

ESM implementation ← ESM consumer

CJS implementation ← CJS consumer

The first model reduces duplicated runtime state.

79. Why Stateless Libraries Are Easier

Consider:

export function add(a, b) {
  return a + b;
}

If loaded twice:

copy A
copy B

there is little observable difference.

But consider:

const connections = new Map();

export function registerConnection(id, connection) {
  connections.set(id, connection);
}

Two copies mean:

connections A
connections B

Now one side cannot see registrations made by the other.

This is the core practical danger.

80. Interop and Singleton Patterns

Be careful with patterns like:

export const singleton = new SomeManager();

They assume:

module evaluates once

If your package can be loaded through two build outputs:

ESM singleton
CJS singleton

you now have two managers.

This can cause subtle bugs that are much harder to diagnose than a simple import error.

81. Interop and Class Identity

Likewise:

export class Request {}

loaded twice creates:

RequestA
RequestB

Then:

request instanceof RequestB;

can be false for an object created by:

new RequestA();

even though both classes came from the same conceptual library.

When you see surprising instanceof failures, investigate duplicate package/module loading.

82. Interop and Event Emitters

A library might create:

export const emitter = new EventEmitter();

If loaded twice:

emitter A
emitter B

Listeners registered on A will not automatically receive events emitted through B.

This is another common manifestation of duplicated module state.

83. Interop and Connection Pools

A backend package might initialize:

export const pool = createPool();

If the package is loaded twice, you might unintentionally create:

Pool A
Pool B

Consequences can include:

  • excess DB connections
  • duplicate initialization
  • confusing shutdown behavior
  • separate caches
  • inconsistent configuration

This is why stateful dual packages require much more care.

84. A Useful Debugging Experiment

If you suspect two copies:

console.log("library initialized", import.meta.url);

on the ESM side.

For CJS:

console.log("library initialized", __filename);

Then compare the output.

If you see:

/project/dist/esm/index.js
/project/dist/cjs/index.cjs

you know you have two implementations loaded.

85. Interop Checklist

When integrating a CJS/ESM dependency:

□ What module system does my application use?
□ What module system does the dependency use?
□ What does package.json "type" say?
□ Are .mjs/.cjs/.js involved?
□ Am I using import or require?
□ Is dynamic import needed?
□ Does the ESM graph contain top-level await?
□ What is the target's export shape?
□ Are CJS named exports statically detectable?
□ Does package.json have "exports"?
□ Which conditional export branch is selected?
□ Could import and require resolve to different files?
□ Does the dependency have module-level state?
□ Could two instances be loaded?

For fast debugging, remember:

87. Interview Questions

Q1. What happens when ESM imports CJS?​

The CJS module is loaded through the CommonJS loader. Its module.exports value is exposed as the ESM default export, while Node may expose synthetic named exports based on static source analysis.

Q2. Why are CJS named exports unreliable?​

Because Node detects them by analyzing CJS source patterns rather than executing the module to discover runtime-generated properties.

Q3. What happens when CJS requires ESM?​

On modern Node, synchronous ESM can be loaded through require() if the entire graph can finish synchronously. Otherwise use dynamic import().

Q4. Why does top-level await matter?​

Because require() is synchronous. If the ESM graph needs asynchronous evaluation, require() cannot wait and throws ERR_REQUIRE_ASYNC_MODULE.

Q5. What is the dual package hazard?​

A package's ESM and CJS entry points can resolve to different files, causing the package to be evaluated twice and producing separate module-level state and class identities.

Q6. How can you reduce the dual package hazard?​

Possible approaches:

  • one canonical implementation + wrapper
  • shared state module
  • stateless package design
  • ESM-only package

Q7. What does "exports" do?​

It controls the public package surface and can route consumers to different files based on conditions such as import and require.

Q8. What is the difference between "main" and "exports"?​

main is the traditional package entry point. exports is the modern mechanism for defining package entry points, subpaths, conditions, and encapsulation.

Q9. What is __esModule?​

A compatibility convention used by transpilers/bundlers. It is not the fundamental native Node rule for CJS → ESM default interop.

Q10. How would you debug a strange CJS/ESM error?​

Start with:

direction
→ module format
→ timing
→ export shape
→ exports map
→ resolved identity

88. Hands-On Labs

Lab 1 --- ESM Imports CJS​

config.cjs:

module.exports = {
  port: 3000,
};

main.mjs:

import config from "./config.cjs";

console.log(config.port);

Observe that the default import represents module.exports.

Lab 2 --- CJS Imports ESM​

utils.mjs:

export function add(a, b) {
  return a + b;
}

main.cjs:

const mod = require("./utils.mjs");

console.log(mod.add(2, 3));

Run on a Node version that supports synchronous require(esm).

Lab 3 --- Top-Level Await Breaks require()​

async.mjs:

await new Promise((resolve) => setTimeout(resolve, 1000));

export const ready = true;

main.cjs:

require("./async.mjs");

Observe:

ERR_REQUIRE_ASYNC_MODULE

Then change to:

(async () => {
  const mod = await import("./async.mjs");

  console.log(mod.ready);
})();

Lab 4 --- CJS Default Export​

lib.cjs:

module.exports = {
  foo: 1,
  bar: 2,
};

main.mjs:

import lib from "./lib.cjs";

console.log(lib);

Understand:

lib === module.exports

conceptually.

Lab 5 --- CJS Named Export Detection​

Try:

exports.foo = 42;

Then:

import { foo } from "./lib.cjs";

Now try a dynamic pattern:

const key = "foo";

exports[key] = 42;

Observe the difference.

Lab 6 --- Duplicate Package State​

Create two files that each define:

const state = new Map();

export { state };

Load the conceptual package through two different build outputs and compare:

stateA === stateB;

Understand why separate implementations create separate state.

Lab 7 --- Class Identity​

Create:

export class User {}

Load two copies from different files.

Then:

const a = new UserA();

console.log(a instanceof UserA); // true
console.log(a instanceof UserB); // false

This makes the dual-package hazard concrete.

Lab 8 --- Conditional Exports​

Create a package with:

{
  "exports": {
    ".": {
      "import": "./esm/index.js",
      "require": "./cjs/index.cjs"
    }
  }
}

Load it from:

ESM
CJS

and inspect which files are executed.

89. Final Mental Model

When you see:

import pkg from "some-package";

think:

1. Determine my module format
        ↓
2. Resolve package
        ↓
3. Apply "exports"
        ↓
4. Select import condition
        ↓
5. Determine target format
        ↓
6. Load target
        ↓
7. If CJS:
       module.exports → default
       detected names → synthetic named exports

When you see:

const pkg = require("some-package");

think:

1. CJS loader starts
        ↓
2. Resolve package
        ↓
3. Apply "exports"
        ↓
4. Select require condition
        ↓
5. Determine target format
        ↓
6. If ESM:
       check synchronous graph
        ↓
       top-level await?
          ├── yes → ERR_REQUIRE_ASYNC_MODULE
          └── no  → namespace / "module.exports"

90. The Most Important Takeaway

Do not think:

"CJS and ESM are just two syntaxes for modules."

Think:

They are two different module-loading systems with a compatibility bridge between them.

That bridge has four dimensions:

                 INTEROP
                    │
       ┌────────────┼────────────┐
       ↓            ↓            ↓
   DIRECTION      TIMING       SHAPE
                                  │
                               IDENTITY

And the practical rules are:

ESM → CJS
  ↓
default ≈ module.exports

CJS → ESM
  ↓
require() only when graph is synchronous
  ↓
otherwise dynamic import()

Dual package
  ↓
different entry files
  ↓
potentially different module instances
  ↓
duplicate state / class identity

"exports"
  ↓
controls which implementation consumers receive

Debugging
  ↓
direction
→ timing
→ identity
→ shape

If you understand those relationships, you do not need to memorize every Node interop edge case. You can reason through most real-world CJS/ESM problems.
